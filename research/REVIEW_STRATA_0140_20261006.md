# Strata v0.1.40 审查：可借鉴项与对我们的影响

日期：2026-10-06。对象：本地 `strata/Strata`，`v0.1.39`（`6f32ec0`，T19 实测版本）→ `v0.1.40`（`1735d64`），345 个提交，274 个文件，+30,605 / −1,918 行。
结论：**发布路径（T17 → R041 → T20）不受影响，也压缩不了**。有两项设计值得纳入阶段 C 与后置卡（卡D15、卡D09），其余与 NVFP4 单卡 offload 无关。不需要重跑 T19。

## 2. 可借鉴的两项

### 2.1 卡D15：置换「延迟生效 + 异步推进」

现行卡D15 设计：置换只在两个解码步之间、拷贝流同步之后执行。这会让解码在置换时等待拷贝完成（Strata 实测约 4.6 ms/窗口，RTX 2060 SUPER，PCIe 3.0 x8）。

Strata 0.1.40 的做法：第 k 个窗口发起置换拷贝，到第 k+lag 个窗口才切换映射；拷贝在辅助线程推进。我们的情况更简单：缓存命中与未命中走同一个 GPU 内核，置换不改变数值，所以不存在 Strata 那样的可复现性问题，只需借它「不阻塞解码」的部分。

建议（不改变卡D15 验收）：在卡D15 增加可选子项「置换延迟一步生效」，默认关闭，作为 T21 的第 4 个臂。预计 +0.5–1 人日。

### 2.2 卡D09 / T03b：在上一轮消息边界存检查点

T03b 第一步发现：已知轮次的成功快照全部为 0。卡D09（多锚触发点，后置，5–8 人日）要解决的正是 Agent 编辑场景下「最后一条消息变了，最近的检查点太远」的问题。

Strata 的做法是一条简单、已验证的策略：在上一轮消息边界多存一个检查点，只对「前缀 ≥ 8192、尾段 ≤ 1024」的请求生效。其历史数据（与块大小改动混合，非单独收益）：首次编辑 17.2 s → 11.5 s（−33%），复用前缀 22,016 → 32,831 token；普通冷 8K 请求多约 0.2 s。

我们的对应数据：E2-R009 编辑回放平均 3.78 s，升序热回放 3.17 s，差距正是这类边界未命中造成的。

建议：卡D09 启动时，以这条策略作为第一版设计，替代原来更复杂的多锚方案，预计把 5–8 人日压到 3–4 人日。卡D09 仍为后置，不进本期发布。

## 3. 对我们的影响

| 方面 | 影响 |
|---|---|
| 发布路径与时间 | 无。T17、R041、T20 不依赖 Strata |
| 阶段 C | 卡D15 可增加一个可选子项（+0.5–1 人日），有望改善 T21 的解码收益 |
| 后置卡 | 卡D09 设计可简化，约省 2–4 人日 |
| 竞争差距 | 0.1.40 的性能改进集中在 MTP、i-quant 内核和 AMD。我们测的是冻结自适应、无 MTP 的 71.9 tok/s；新版在同一配置下的变化未测。按用户决定不重跑 T19 |
| 论文 | 相关工作可补一句：Strata 0.1.40 以消息边界检查点处理 Agent 编辑场景 |
