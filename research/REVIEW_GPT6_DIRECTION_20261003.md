## 0. 结论

**方向可以作为总纲，方法论可以照单采用，但有四处要调整，另有一件事需要你决定。**

1. **采用**：范围冻结、强基线和归因规则、不人为制造瓶颈、数值门、按到达过程测服务能力、配对 A/B、留出验证、影子模式，以及论文模块表。这些和我们现在的轮次方法一致，有几处比我们更严，应当并入。
2. **调整一：数据换成第 1 代实测。** 两份稿子引用的是已经过时的数字（第 1 节）。
3. **调整二：先过「四卡驻留」这道门，再定多卡论点。** 按检查点算下来，TP4 下每张卡能驻留 81–100% 的专家，卸载区间基本消失；TP2 只有 33–46%（第 2 节）。方向稿把这列为风险，但没有计算。

## 2. 多卡的前提要先过一道门

### 2.1 按检查点算出的每卡显存账

检查点逐类大小（从 safetensors 文件头统计，共 123.53 GiB）：

| 类别 | 大小 | TP 下的处理 |
|---|---|---|
| 路由专家 | 63.28 GiB | 按卡均分 |
| PLE / N-gram 表 | 47.75 GiB | 留在主存，不上卡 |
| GDN（36 层线性注意力） | 3.89 GiB | 可切：key 头 16、value 头 48，都能被 4 整除 |
| MTP | 2.51 GiB | 不用 |
| 超连接等其他 | 1.19 GiB | 视实现，可能整份复制 |
| lm_head、embed_tokens | 各 1.18 GiB | 按词表切 |
| 全注意力（12 层，含 indexer） | 1.15 GiB | q 头 24 可切；**KV 头只有 2 个，TP4 时每个 KV 头要复制给两张卡** |
| 视觉 | 0.84 GiB | 纯文本时可以不加载 |
| 共享专家、路由器 | 0.44、0.12 GiB | 可切、复制 |

按单卡实测口径（空闲 23.11 GiB，`--memory-ratio 0.88`，可用约 20.3 GiB），每卡专家能驻留的比例如下：

| 配置 | 1 路 48K | 2 路 64K | 8 路 32K |
|---|---|---|---|
| 单卡 | 12–14% | 9–11% | 4–6% |
| TP2 | 41–46% | 38–43% | 33–38% |
| TP4 | 97–100% | 91–100% | 81–92% |

- 区间的两端分别是「视觉权重加载、超连接整份复制」和「视觉不加载、超连接也切分」两种假设。
- **这套算法在单卡上和实测对得上**：算出 12%，实测 3149 个槽，即 12.8%。
- 单卡 8 路 32K 时，KV 约 6.2 GiB，专家空间只剩约 2.5–3.8 GiB，已经贴近层优先预填双缓冲所需的下限（两层共 1024 个槽，约 2.6 GiB）。

### 2.2 含义

- **TP4 在常态负载下基本不再卸载。** 只有在峰值、总上下文很长时，KV 才会挤掉一部分专家，这时驻留率约 81–92%。方向稿第 6.1 节说过：「若 TP=4、目标负载下专家全部可驻留……应将其作为强基线和工程成功。」按这张表，这种情况很可能就是事实。那么「主存卸载 MoE 的多 GPU 协同执行」在 1×TP4 上就没有多少研究空间，研究问题只存在于以下几种情形：
  - 2×TP2：每组仍有一半以上的专家要卸载；
  - TP4 在高状态压力下：KV 和专家互相争显存；
  - 4×TP1：四张卡同时从主存搬专家，共享主存带宽（STREAM 实测 46.6–110.8 GB/s，而四卡各自按 24.3 GB/s 搬，合计约 97 GB/s）。
- **TP4 是否装得下，取决于复制项和工作区这些细节**：KV 头复制、超连接、视觉、CUDA Graph、临时工作区。所以门 G0 必须用真实分配器的数字来核算，不能只看上表的估算。
- **这个模型做 TP 的工程量很大**：上游固定版本 `qwen4_exp` 只支持 TP=1；KV 头只有 2 个；有超连接和 indexer 两种非标准结构；PLE 表在主存上，需要每卡取数或广播；4090 不支持 P2P，NCCL 只能经过主存中转，正好和专家搬运抢同一条 PCIe 和同一份主存带宽。

### 2.3 门 G0（不占 GPU，先做）

由开发 agent 按实际加载路径，逐张卡列出权重分片、复制项、KV、GDN 状态、CUDA Graph、工作区和安全余量，给出 TP2、TP4 在三种负载下的驻留率。

- 如果 TP4 常态驻留率 ≥95%：多卡部分的论文主张改为「TP4 消除卸载后的剩余瓶颈」，或者把研究集中在 2×TP2 和高状态压力区间。
- 如果驻留率明显更低：方向稿的多卡论点成立，照原计划推进。

## 3. 单卡阶段的核心问题要换

### 3.1 实测的一阶效应：成本按专家流遍数计

- 每个预填段都会把整个专家池（63.46 GiB）从主存搬一遍，约 2.6–2.9 s，和段里有多少 token 基本无关。
  - 4096 分块的冷 32K 要搬 8 遍，约 21 s；层优先只搬 1 遍，加上计算约 6.1–6.6 s。
  - 真实 Agent 轨迹里，重算 663 token 只要 2.62–2.69 s，重算 176 token 却要 5.19 s，因为后者被锚封顶切成了两段。
- 因此，按 token 预算切块的常规调度（为了保护其他会话的字间隔而把预填切小）在卸载 MoE 上代价极大：每多切一块，就多搬一遍 68 GB。

### 3.2 建议的单卡核心问题（H0）

> **在主存卸载 MoE 上，以「专家流遍数」作为调度的成本单位，能否同时降低 Agent 轮次的首 token 和其他会话的停顿？**

对应的机制都是「协调多个请求共用同一份共享资源（PCIe 和主存带宽）」，和方向稿的总纲一致，而且到 TP 组时可以直接扩展：

1. **每轮只搬一遍**：锚点快照放在同一遍预填里取，不再为锚点多切一段（即报告里的 D12）。
2. **多请求共用一遍**：两个会话的预填如果在同一时间窗口内到达，就合进同一遍专家流（即原计划 D7）。先测现状：调度器今天会不会把两条新请求放进同一个预填批次。
3. **遍内插解码**：在一遍预填的层边界插入其他会话的解码步，代替按 token 切块（即原计划 D6）。
4. **按遍数准入**：短后缀只搬它路由到的专家（即报告里的 D13）。

### 3.3 协议稿的 H1、H2、H3 怎么处理

- **H1（前序预填是否增加后续成本）**：保留，但降为附带测量。协议稿 E1 的三个配对条件（不插入、等时长空等、真实预填）和恢复后 1、8、32 步的窗口设计得很好，直接并进 E1-R005。需要给 D0 补逐步的缺失数和 H2D 计数。如果测出来的后续成本很小，就按协议稿第 4.3 节的规则从控制器里去掉。
- **H2、H3（状态感知的预测和策略）**：放到 H0 的机制已经验证之后再做。预测的「状态」应当以遍数和驻留为主，而不是泛泛的长度和批大小。

### 3.4 查新要补的两项

方向稿的相关工作表里缺少两项，它们和 H0 最接近：

- **Layered Prefill**：方向稿列了，但只当作「层间插解码」。它的出发点正是「按 token 分块会让 MoE 重复加载专家权重」，只不过针对的是显存内的 HBM 流量。我们的差异要落在主存卸载（PCIe 比 HBM 慢约两个数量级）、跨请求共用一遍、GDN 检查点切段这几个具体约束上。
- **FlexGen**：用之字形块调度把权重搬运分摊到大批量上。思路相近，但它面向离线吞吐。我们面向在线 Agent 的首 token 和停顿。

在差异写清楚之前，不宣称 H0 是首创。

## 4. TP 的数值门要重新定义

- 我们现在的规则是：无损改动必须和父轮逐位一致。
- TP 改变了归约顺序，**TP-n 不可能和 TP1 逐位一致**。方向稿第 6.2 节也承认这一点，但又要求「继续保留既定数值门，不自行替换为小题集质量相近」。这两条放在一起执行不了。
- 建议 TP 的门由三部分组成：
  1. **TP-n 自身可重复**：同树、同配置、temp0，两次运行逐位一致。
  2. **相对 TP1 的分歧受限**：首个分歧位置上前两名 token 的 logit 差低于阈值，阈值用 TP1 自身「批形状不同」造成的分歧来标定。
  3. **60 题质量门**：差距在噪声范围内。

  第 1 项必须通过，第 2、3 项一起判定。

## 5. 需要你决定：四卡怎么组

| | 真正 TP（1×TP4 或 2×TP2） | 4 个单卡实例 + 共享主存专家池 + 会话亲和路由 |
|---|---|---|
| 工程量 | 大：`qwen4_exp` 的 TP、KV 头复制、超连接、PLE、没有 P2P 的 NCCL | 小：主要是路由和共享专家池 |
| 冷 32K 首 token | TP4 不用搬专家，量级上可能到几秒以内（未测，只是量级） | 和单卡相同，约 6 s |
| 常态 2–4 路，每路解码 | TP4 显著高于单卡（未测） | 每卡 1 路时约 37–40 |
| 峰值 8 路，每路 >30 | TP4 高驻留下有希望 | 每卡 2 路，推算每路 21–23，**达不到** |
| 论文多卡部分 | 1×TP4 卸载基本消失，研究要放在 2×TP2 或高状态压力区间 | 四卡共享主存带宽和跨卡准入 |

方向稿把「真正的 TP，不用多个 TP1 实例替代」写成了既定的工程目标；我们之前的四卡计划（计划文档第 4 阶段）写的是右列。两者都说得通，**峰值 8 路每路 30 tok/s 这条线只有 TP4 有希望达到**，代价是几周的 TP 工程量和 G0 的装载风险。
