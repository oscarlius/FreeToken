## 摘要

（草稿，随轮次更新）主存卸载 MoE 推理时，GPU 只缓存一小部分专家，其余专家每次用到都要经 PCIe 从主存搬运。我们在一张 RTX 4090（24 GB）上服务 Qwen3.8-Flash-Next NVFP4：68 GB 专家池常驻主存，GPU 只缓存约 13% 的专家；目标负载是约 10 个 Agent 会话。

测量显示，预填的成本主要不由 token 数决定，而由「专家池被完整搬运了几遍」决定：每一遍约 2.6–2.9 s，和这一遍里有多少 token 基本无关。冷 32K 按 4096 分块预填要搬 8 遍，首 token {{r:E1-R001.cold32k_4096.ttft_s}} s；层优先只搬 1 遍，加上上游预填内核后为 {{r:E1-R001.cold32k_layer_major.ttft_s}} s，输出与父轮逐位一致。在一条 12 轮的真实 Agent 轨迹上，每轮首 token 只落在约 2.6 s 和约 5.3 s 两档，分别对应搬一遍和搬两遍，而和重算多少 token 无关。

据此，我们提出以专家流遍数作为调度的成本单位（H0），包括四个机制：每轮只搬一遍、多个请求共用一遍、在一遍之内的层边界插入其他会话的解码、短后缀只搬它路由到的专家。本文给出这些机制的设计、推算和验证协议；机制本身的实测结果待第一阶段完成。

## 1. 引言

### 1.1 问题与负载

- 单卡加主存专家池：每 token 激活 480 个专家（48 层 × top-10），未命中的专家要经 PCIe 搬运。
- Agent 负载：长上下文、多轮、带工具调用和思考段、中途编辑、多会话并发。
- 体验线：单会话 64K 窗口，首 token ≤ 10 s，持续解码 > 30 tok/s；常态 2–4 路同时生成，峰值 8 路。
- FreeToken 原论文针对单请求和单 NUMA 节点，没有覆盖多会话、Agent 轮次和本机的双路 CPU。

### 1.2 研究问题

**总纲（项目层面）**：共享资源约束下，主存卸载 MoE 的低延迟协同执行。多个请求共享同一条 PCIe 和同一份主存带宽时，如何安排专家的驻留、搬运和执行顺序，减少真正阻塞首 token 和后续 token 的等待。

**第一阶段核心问题 H0（单卡）**：在主存卸载 MoE 上，以专家流遍数作为调度的成本单位，能否同时降低 Agent 轮次的首 token 和其他会话的停顿？

- 反证条件：在相同检查点、数值路径、显存预算和工作负载下，按遍数调度不比调优后的按 token 预算调度更好；或者收益只是把等待转移给了其他会话。

**附带问题 H1**：一次预填是否让之后的解码变慢（专家缓存被冲掉、状态挤占显存等）？作为 E1-R005 的附带测量（第 7.2 节）。如果后续成本很小，就不进入调度器。

**后续问题 H2、H3**：状态感知的成本预测和策略。在 H0 的机制验证之后再做；预测的「状态」以遍数和驻留为主。

**多卡问题**：先完成每卡显存账（第 10 节的门 G0），再决定多卡部分研究什么。

## 2. 背景与相关工作

### 2.1 FreeToken 的机制

- 主存专家池是唯一真相，GPU 上按（层，专家）整槽管理 LRU 缓存。
- 预填用整层双缓冲：GPU 算第 $l$ 层时，PCIe 搬第 $l+1$ 层的全部专家。
- 解码时 $m$ 个未命中按 $q^\star \approx m\,B_P/B_H$ 分成「搬进缓存」与「CPU 原地计算」两组并行。
- 整个解码步装进一个 CUDA Graph，路由相关控制在 GPU 上。

本文继承这些机制，不把它们当作本文的贡献。

### 2.2 与 KTransformers 的关系

KTransformers 让 CPU 用 AMX 计算路由专家。本机 Xeon Silver 4310 没有 AMX，KT 只能退到 avx2 后端，约 3K 输入就显存不足。用统一公式看，KT 是 FreeToken 在「放置固定、所有未命中交给 CPU」下的特例。详见 `_shared/PAPER_COMPARE_KT_FT_20261003.md`。

### 2.3 模型结构

- 48 层：36 层 GDN 线性注意力（key 头 16，value 头 48）；12 层全注意力（q 头 24，**KV 头 2**，head_dim 256，带 indexer 的 QSA 稀疏注意力）。hidden 2560，词表 248,320，层间有超连接。
- 每层 512 个路由专家、top-10，另有 1 个共享专家。每个专家 $3 \times 2560 \times 640$ 参数，NVFP4 下 2,772,480 字节；48 层合计 63.46 GiB。
- 第 2 层有 PLE（N-gram 嵌入，钉在主存）。

## 4. 性能模型

### 4.1 遍数成本

一个预填段指一次完整的层循环。层优先下，第 $l+1$ 层专家的搬运和第 $l$ 层的计算重叠：

$$
T_{seg}(n) \approx \max\!\Big(\frac{P(1-h)}{B_P},\ C(n)\Big) + t_0
$$

$P$ 为专家池字节（63.46 GiB），$h$ 为这一段里已在 GPU 上的专家比例，$C(n)$ 为 $n$ 个 token 的计算时间。Agent 轮次的后缀通常只有几十到几千 token，$C(n) \ll P/B_P$，所以 $T_{seg} \approx P/B_P$，约 2.6–2.9 s，与 $n$ 基本无关。一轮被切成 $k$ 段时：

$$
T_{turn} \approx k \cdot \frac{P(1-h)}{B_P} + \sum_{j=1}^{k} C(n_j)
$$

两个推论：

- 按 token 预算切块（为了保护其他会话的字间隔而把预填切小）在卸载 MoE 上代价很大：每多切一段，就多付一遍 $P/B_P$。冷 32K 按 4096 分块是 8 遍，约 22.9 s。
- 同一遍里多算一些 token 只多 $C$，本机约 0.2 s/千 token。所以多切一段只有在省下的后续重算超过约 13K token 时才划算。

### 4.2 冷预填（第 1 代重拟合）

层优先加 #578 后，每层计算（约 131 ms）慢于每层搬运（约 59 ms），冷预填受计算限制：

$$
T(N) \approx 0.068N + 0.107N + 0.0002N^2 + 0.2
$$

$N$ 以千 token 计，单位秒；第一项是 MoE，后两项是非 MoE（注意力、GDN、PLE 等）。由 E1-R001 的 32K 和 64K 拟合，埋点开。按这个式子，冷启 ≤ 10 s 的上限约 49–53K token；64K 时非 MoE 占 63–67%。

### 4.3 解码

$$
t_{step}(B, L) \approx t_0 + kL + t_{req}(B-1) + B\,\frac{m\,S_{tok}}{BW}
$$

$S_{tok}$ 为每 token 全失误字节（1.331 GB），$BW$ 为未命中专家的处理带宽。本机拟合 $t_0 = 13.1$ ms，$k = 0.032$ ms/千 token，$t_{req} = 5.3$ ms（第 0 代拟合，第 1 代待 E1-R005 后重拟合）。

## 6. Agent 轮次：遍数决定首 token

### 6.1 回放

- 轨迹：{{r:E1-R003.runtime_batch7.trace.rounds}} 轮，其中 {{r:E1-R003.runtime_batch7.trace.tool_rounds}} 轮带工具调用，每轮都有思考段；提示最长 {{r:E1-R003.runtime_batch7.trace.max_prompt_tokens}} token。
- 「热进程」在已经跑过一遍的服务里重放，每轮都能命中上一轮留下的前缀；「冷进程」是新起一个服务再重放，第 0 轮全量计算，之后仍会命中同一进程里前面轮次留下的前缀，只是命中点不同。
- 热进程每轮重算 token：{{r:E1-R003.replay_warm.recompute_tokens}}；首 token：{{r:E1-R003.replay_warm.turn_ttft_s}} s；均值 {{r:E1-R003.replay_warm.ttft_mean_s}} s，最大 {{r:E1-R003.replay_warm.ttft_max_s}} s。
- 冷进程每轮重算 token：{{r:E1-R003.replay_cold.recompute_tokens}}；首 token：{{r:E1-R003.replay_cold.turn_ttft_s}} s。
- D0：每个预填段搬运 {{r:E1-R003.d0.h2d_gib_per_segment}} GiB 专家。

### 6.2 现象：两档首 token

- 首 token 只有约 2.6 s 和约 5.2 s 两档。每个预填段不论多少 token，都要把专家池搬一遍；5.2 s 就是搬了两遍。
- 决定首 token 的是被切成几段，而不是重算多少 token：同一条轨迹里，重算 663 token 只要一遍，重算 176 token 却被切成两段。

### 6.3 归因：预填锚封顶（待 E1-R008 确认）

- 切成两段几乎可以确定来自我们自己 D3 的「预填锚封顶」：为了在锚点位置留下 GDN 状态快照，预填在锚点处被切开。它挂在生产命令带着的 `--enable-special-token-ckpt` 上。
- 证据：所有重算段都远小于 4096，排除了预填块长上限；同一轮在热进程里只需重算 45–52 token 时是一段，在冷进程里重算 176–372 token 时变成两段，更长的那段包含了锚点。
- 在卸载模式下，锚封顶对短后缀是净亏损：切一刀固定多付一遍搬运；不切的代价只是下一轮可能多重算一些 token（第 4.1 节，盈亏点约 13K token）。

### 6.4 机制一：每轮只搬一遍（D12）

- 第一步（E1-R008）：同一条轨迹，锚封顶开、关各回放一次，保留快照功能，只关掉切段。推算：首 token 均值 {{p:E1-R008.agent12.turn_ttft_mean_s}} s，最大 {{p:E1-R008.agent12.turn_ttft_max_s}} s，两段轮次 {{p:E1-R008.agent12.two_segment_turns}} 个。判定 {{v:E1-R008}}。
- 第二步：在一遍预填之内取锚点快照。从 GDN 的分块扫描里直接取出锚点位置的状态，不为锚点多切一段；由上游 #577 的 host bank 存储。中途编辑的命中需求也由这一步满足。

### 6.5 机制四：短后缀按路由搬运（D13，计划）

（推算：后缀只有 $n$ 个 token 时，一层里被用到的专家比例约为 $1-(1-10/512)^n$。按路由独立估算，64 token 约 72%，首 token 约 1.8 s；19 token 约 31%，约 0.9 s；300 token 以上基本全部用到，没有收益。实际路由有相关性，用到的专家会更少。这条轨迹的热进程里约一半轮次只需要重算 ≤ 64 token，均值可到约 2.0 s。）

### 6.6 正确性

- 确定性门 {{v:E1-R003}}：第 {{r:E1-R003.runtime_batch7.warm_vs_cold_first32_mismatch_rounds}} 轮，热进程和冷进程回放的前 32 个 token 不一致；分歧全部在思考段，正文前缀一致。
- 可能是数值路径不同（快照恢复的 GDN 状态和一次算完在浮点上有微小差别），也可能是状态缺陷。按第 3.5 节先测「重算对重算」，再看 logit 差。

## 7. 多会话：共用一遍与遍内插解码（计划）

### 7.1 基线（E1-R005，待测）

- 两路不同上下文同时解码，每路推算 {{p:E1-R005.multi_ctx_b2.decode_tps_per_route}} tok/s；同提示对照 {{p:E1-R005.same_prompt_b2.decode_tps_per_route}} tok/s。同提示并发会让各路路由几乎相同，高估多会话吞吐。
- 冷 32K 预填期间，其他会话最长停顿推算 {{p:E1-R005.stall_cold_prefill.other_max_gap_s}} s；Agent 轮次预填期间 {{p:E1-R005.stall_turn_prefill.other_max_gap_s}} s。
- 两个短后缀轮次同时到达：测现状是合进同一遍，还是排队搬两遍。

### 7.2 附带测量 H1：前序预填的后续成本

- 只用一个解码请求 A 和一个预填请求 B。把 A 推进到可重复的逻辑位置和缓存初态，分别运行三个条件：不插入 B、等时长空等、真实执行 B 的预填。
- 诊断量：

$$
\Delta_H=\sum_{i=1}^{H}t_i^{\text{after real prefill}}-\sum_{i=1}^{H}t_i^{\text{after matched idle}}
$$

- $H$ 取 1、8、32，事先固定。只统计 A 恢复后的 $H$ 步，不含 B 的预填本身。同时记录额外 H2D、缺失数、状态占用和 GPU 时钟；耗时差不能单独证明缓存被冲掉。
- 如果 $\Delta_H$ 相对单步时间很小，H1 不进入调度器。

### 7.3 机制二：多请求共用一遍（D7）

- 两个预填在同一时间窗口内到达时，合进同一次层循环：每层专家只搬一次，两个请求的 token 一起算。
- （推算：两个短后缀轮次同时到达，排队时第二个的首 token 约为 2 × 2.7 s；共用一遍约 2.7 s 加上多出的计算。）
- 代价：先到的请求要等窗口关闭。窗口长度由首 token 时限决定。

### 7.4 机制三：遍内插解码（D6）

- 在一遍预填的层边界插入其他会话的解码步，代替按 token 切块来保护字间隔。每隔几层插一次，由停顿目标决定。
- 插入的解码步有自己的未命中专家（每 token 约 292 MB），要和预填的整层搬运抢 PCIe，需要让关键传输优先。
- （推算：其他会话最长停顿 ≤ 1 s 时，预填方首 token 约多 0.2 s。）

### 7.5 按遍数准入

- 新请求到达时，决定加入当前这一遍还是等下一遍；以「还要搬几遍」和各请求的首 token 时限作为判据。

## 10. 多卡：每卡驻留分析与协议（不含性能）

### 10.1 为什么先算显存账

项目总纲要求真正的 TP。若 TP4 下每张卡几乎能驻留全部专家，卸载区间就基本消失，多卡部分的研究问题会随之改变。所以先算每卡显存账，再定多卡论点。

### 10.2 估算（按检查点文件头，未用分配器核实）

口径：每卡可用约 20.3 GiB（空闲 23.11 GiB × `--memory-ratio 0.88`）；非专家权重按第 2.3 节的类别切分或复制；KV 按实测分配反推每 token 约 25.4 KB，TP4 时 2 个 KV 头要复制给两张卡；区间两端分别对应「视觉加载、超连接整份复制」和「视觉不加载、超连接也切分」。

| 配置 | 1 路 48K | 2 路 64K | 8 路 32K |
|---|---|---|---|
| 单卡 | 12–14% | 9–11% | 4–6% |
| TP2 | 41–46% | 38–43% | 33–38% |
| TP4 | 97–100% | 91–100% | 81–92% |

校验：同一口径在单卡上算出 12%，实测专家槽 3149 个，为 12.8%。

### 10.3 含义

- TP4 在常态负载下基本不再卸载。多卡部分的研究问题只存在于：2×TP2（每组仍有一半以上专家要卸载）；TP4 在高状态压力下（KV 和专家互相争显存）；4 个单卡实例共享主存带宽。
- 四卡同时整池预填约需 97 GB/s 主存读，本机交错 STREAM 为 {{r:E0-R000.bandwidth.stream_interleave_gbs}} GB/s。
- 这个模型做 TP 的工程约束：上游固定提交 d3512b4 的 `qwen4_exp` 只支持 TP=1；KV 头只有 2 个；有超连接和 indexer 两种非标准结构；PLE 表在主存；4090 不支持 P2P，NCCL 经主存中转，和专家搬运抢同一条 PCIe 和同一份主存带宽。

### 10.4 门与协议

- **G0**：按实际加载路径逐卡核算权重分片、复制项、KV、GDN 状态、CUDA Graph、工作区和安全余量。TP4 常态驻留 ≥ 95% 时，多卡部分改为研究「TP4 消除卸载后的剩余瓶颈」，或集中在 2×TP2 和高状态压力区间；明显更低时，按总纲推进。
- **TP 数值门**：TP 改变归约顺序，不可能和单卡逐位一致。门由三部分组成：TP-n 同配置两次运行逐位一致（必须通过）；相对单卡的首个分歧位置上前两名 token 的 logit 差低于阈值，阈值用单卡自身「批形状不同」造成的分歧标定；60 题质量差距在噪声范围内。后两项一起判定。
- **顺序**：硬件到位后，先实现并测量调优后的普通 TP2，再对照新策略，随后扩展 TP4。重新测量分片就绪、真实通信、主存争用和逐卡显存，不把单卡带宽乘以卡数。普通 TP 已能满足业务时，直接承认其效果。
- 1×TP4、2×TP2 是比较配置；4 个单卡实例是对照。

## 11. 正确性与鲁棒性

- 固定一条认证执行组合；未知组合不自动降精度或换后端。
- 实验功能只有关闭、影子、启用三种模式，默认关闭。
- 专家槽用引用计数保护，正在使用的槽不得被覆盖；KV 和 GDN 的有效位置必须配对。
- 取消和异常：`tests/scheduler` 有 2 例 abort_inflight 失败，父轮已存在，已归因到 D3 在解码热路径上无条件读锚点字段。
- 确定性：见第 6.6 节。30 分钟稳定性待测。
