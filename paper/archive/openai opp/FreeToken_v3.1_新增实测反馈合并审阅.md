## 2. 总体判断

### 2.1 保留的主线

H0 继续是：在主存卸载 MoE 上，以专家流遍数和 PCIe 时间预算作为调度成本，能否改善 Agent 轮次的首响应及其他请求的生成体验。

当前资料对下列命题有支持：

1. 4096 分块与层优先下的冷 32K 具有不同搬运遍数；#578 的公开内核收益仍归上游。
2. 真实 Agent 回放中存在一档、两档 TTFT；短后缀的 token 数本身不能解释全部差异。
3. 当前整层加载路径中的短请求地板，与完整专家流的 H2D 工作量及耗时相符。
4. 两个不同上下文请求同时生成的真实表现尚待 E1-R005；21–23 和 35–42 tok/s 均不是实测。
5. hybrid 的负结果只针对已测执行器、绑核与配置，不能扩大为所有 hybrid 路径均不可行。

这些判断不依赖“第二遍一定由 D3 造成”。H0 的机制效果仍待强基线对照，不能仅靠测量与公式宣布已经突破。

### 2.2 必须撤回的解释

v3.1 §6.4 把 5.43 s 对 2.80 s 作为开关因果证据，并向摘要、D12 和附录传播。用户补充反馈明确说这条在 19:22 已撤回。这组数据不再作为“关开关消除第二遍”的有效证据。

前次审阅中，我也将该开关对照列作支持调查额外切段的数值记录。现随新反馈撤回它的因果用途，不继续计算或报告约 48% 的“去锚切段收益”。

## 3. 五次读数能说明什么，不能说明什么

用户补充记录：相同提示、检查点开着连续运行：

| 试次 | TTFT（秒） |
|---|---:|
| 1 | 5.864 |
| 2 | 2.950 |
| 3 | 2.944 |
| 4 | 2.942 |
| 5 | 2.940 |

复算：后四次均值 **2.944 s**，中位数 **2.943 s**，极差 **0.010 s**；第一次比后四次均值多 **2.920 s**。

**可以作出的判断**：检查点一直开启，也可以出现约 2.94 s 的读数；原单点对照没有隔离首次执行、前缀状态等因素，不能识别开关的独立效果。

**不能直接作出的判断**：全部差异已被证明是前缀缓存；D3 对任何冷请求都不会造成额外切段；第一次多出的 2.920 s 必定是一遍实际 DMA。

重复请求可能改变前缀命中、实际重算长度、专家驻留、执行准备状态。只有总耗时，不能唯一识别原因。也存在一个与当前读数兼容的假设：D3 仅在未命中或特定锚点状态下切段，后续前缀命中后不再触发。它不是结论，但不能被同开关连续重复排除。

应把 Grok 所说“前缀还没建起来”记录为本地诊断意见；若原始日志已有命中量、段数和切段原因，则补入后再升级证据状态。

## 5. E1-R008：只加强现有实验，不增加框架模块

### 5.1 先回收已有工件

先把 19:22 撤回条目和五次运行的 request ID、代码提交、提示 token IDs、前缀命中、实际重算、段数与 H2D 对齐。若已有工件足够，不为“再跑一次”重复消耗资源。

段数必须来自执行事件，不得由 `round(TTFT / 2.8)` 反算，再用于证明 TTFT 由段数决定。

### 5.2 四格对照

| 前缀状态 | 切段开启、快照机制保留 | 仅关闭切段、快照机制保留 |
|---|---|---|
| 引擎已准备、目标前缀未命中 | A-cold | B-cold |
| 引擎已准备、预置可比较的有效前缀 | A-warm | B-warm |

这是建议协议，不是声称已有清缓存或状态注入接口。若没有可靠的前缀隔离能力，使用独立进程和相同的准备序列建立对照，并记录无法完全匹配的状态。不能用 A 的第一次请求与 B 的第若干次请求比较。

重复采用独立状态重建与配对顺序；同进程连续四个热请求不能当成四次独立冷态实验。有限样本先用于诊断，推断稳定收益需要按观测波动增加重复。

“保留快照开关”不等于“保留同样的快照能力”。必须记录可用检查点的位置、数量、状态类型与后续恢复行为。若关闭切段导致某个快照不再产生，需明确它是联合改变，不能将所有收益归为单一切段优化。先证明哪些目标可在不新增大范围机制的情况下保持一致。

### 5.3 最小新增记录（沿用 D0 与轮次 JSON）

建议字段按现有命名映射，不要求重建数据平台：

- 配置：提交、权重哈希、实际路径、进程 ID、请求顺序、切段状态、快照配置。
- 请求：token IDs 哈希、输入长度、命中前缀、实际重算量、检查点位置。
- 每段：序号、起止位置、切段触发原因、H2D 与 D2D 字节、执行开始/结束。
- 输出与状态：首模型 token、首业务事件、保存/恢复检查及下一轮有效命中。

H2D 时间要区分设备实际传输与主机提交；组件忙碌时间不能简单相加。首轮不能统一扔掉：引擎准备、前缀未命中、专家驻留分别记录。

### 5.4 结果如何判读

| 观察 | 合理结论 |
|---|---|
| 等价前缀状态下，A 两段、B 一段；A 的额外段记录为锚点触发，H2D 同步下降，状态正确 | 支持 D3 在这类条件下产生额外遍数；不能外推为所有第二档的唯一原因 |
| A/B 冷态都两段、热态都一段 | 不能归因于切段开关；继续看缓存与其他切段原因 |
| A/B 段数和字节相同，但 TTFT 不同 | 不能宣称“少一遍”；调查编译、执行准备、计算或等待等其他项 |
| B 首轮变快，但后续检查点缺失、重算增加或状态错误 | 不是无代价消除开销；单列跨轮代价，状态错误不能通过 |
| 本机没复现原两档 | 保留原记录，标记当前条件未复现；不人为制造原结论 |

## 6. 额外需要收紧的现有表述

### 6.1 不用“与 token 数无关”替代“token 数不足以解释”

§4.2 和 §8 已记录冷 32K 的计算主导情况。H0 的遍数成本视角应限于对应执行路径与资源条件。约 16K 的计算/搬运交叉点也是当前冷预填模型下的估计，不应直接用于不同已有上下文长度、不同恢复路径的后缀。

§6.2 的 3.50 s 不能因为落在两档之间就算模型解释成功。它应作为残差个案，检查 H2D、计算、准备和等待。模型必须允许存在未解释样本。

### 6.2 D14 的 35–42 tok/s

仍是由旧系数得到的两个理想资源情景，不是实测、置信区间或已经证明可实现的硬上界。19.4 ms 来自整体剩余项，未完全确认为可被另一路搬运覆盖的 GPU 工作。

算术上，1000/24=41.67，1000/28.2=35.46。若 28.2 ms 情景仍只占 24 ms 传输，理论 PCIe 利用率约 85.1%，所以“所有情景都必须 100% 占满、都完全没预填余量”也应收紧。该余量并不保证可供预填使用，仍受依赖、缓存和执行边界限制。

保留 D14 为候选，等 R005/R007 时间线决定，不因上界数字好看就拆图、复制工作区或引入新数值路径。

### 6.3 D6 的放大公式

`T' = T / (1-r*t_step)` 是固定步长、串行插入且忽略额外切换成本的情景估计；它不是系统总时间的无条件上界。出现缓存扰动、图切换和恢复成本，真实时间也可能更大。

### 6.4 正确性措辞

§6.8 的 3/12、4/12 是“本组样本的自比不一致比例”，不能叫“每轮假失败率”。差异是否无害尚未定位。自由生成比较可以触发调查，但不能单独定位错误或建立等价；继续保留四层检查和 `kept_pending_gate`。

### 6.5 hybrid 负结果

§9.1 对负结果的适用范围和诊断支线定位正确。仍应把“固定延迟主导”“屏障与被抢占线程导致”标为待服务时间分解验证的机理假设。6.7 MB/3.75 ms 的低等效带宽本身不能唯一识别原因。
