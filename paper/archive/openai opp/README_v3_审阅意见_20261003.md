## 4. 必须修改的核心问题

### R1｜§4.1：先重叠、后相加，成本模型不一致

**原文位置**：L241–259。

单段公式使用 `max(P(1-h)/B_P, C(n)) + t0`，随后多段公式却使用 `kP(1-h)/B_P + ΣC(n_j)`。如果 `C` 仍是完整计算成本，第二式重复计算了已经被隐藏的部分。

**建议修正**：在保留原近似假设下写为：

\[
T_{turn}\approx T_{queue}+\sum_{j=1}^{J}\left[\max\left(\frac{V_j}{B_{P,j}},C_j\right)+\delta_j\right]+T_{emit}.
\]

`V_j` 是该段实际 H2D 字节；`δ_j` 是流水启停、依赖及其他未被前项覆盖的暴露成本。层间计算不均匀时，仅取总搬运与总计算的 max 还可能低估流水气泡，需用 trace 校准。

如果原多段公式故意表示“完全不重叠”的串行情景或粗略上界，应明确这样标注，不能当同一重叠模型的点预测。

**相关修正**：额外检查点的 14–16K 盈亏阈值不能作为一般结论。转为比较“保存新增暴露成本”与“将来实际省下的 TTFT”。例如，按照本稿自身的带宽地板模型，后缀由 10K 降为 1K 仍可能各需一遍，省了计算量却未省时间；反之，省去一个段边界可能直接省下一遍。

### R2｜摘要、§4.4、§4.6、§13：83 token/s 不能证明两路各 30 不可达

**原文位置**：L29–33、L295–341、L369–379、L748–756。

83.26 是按当前缺失流量计算的 PCIe 条件性总量上界。两路各 30 合计 60，低于这一值。按原稿自己的字节参数，60 token/s 对应 17.51 GB/s，小于 24.3 GB/s；在这个仅含传输的预算中，预填比例不高于约 27.94% 时，该必要条件仍未排除两路目标。

这**不证明**单卡实际可以达到目标；它只说明 PCIe 守恒本身不足以证明“不可能”。

每路 21–23 来自另一个更强假设的串行模型：B=2 时非传输成本约 19.424 ms，传输约 24.020 ms，总计约 43.444 ms。文中同时承认这些系数来自第 0 代、未在第 1 代重拟合，且 5.3 ms 的 GPU 增量是从端到端差额估计，尚缺独立组件归因。

**建议替换**：

> 在当前串行成本近似、当前未命中率及参数不变的条件下，预测两路不同上下文每路约 21–23 token/s，尚无实测支持达标。PCIe 字节预算单独尚未排除两路各 30 的可能性，应由 E1-R005 与路由/H2D 计数确定实际瓶颈。

“CPU 必须补 18–34 GB/s”“hybrid 是唯一单卡杠杆”“只有 TP4 有希望”都应降为条件性候选，不能用同一未验证模型排除减少实际传输、改进 GPU 执行或其他资源组织。

**CPU 18 GB/s 不应成为充分验收门**：即使单独测得这一带宽，也没有证明与 PCIe 同跑时仍有相同能力、固定交接足够低、缓存行为不变或数值门通过。应测联合执行与端到端两路结果。

### R3｜§4.4：物理预算要按实际字节定义

文中公式可作为简化情景，但真正的传输守恒应在同一窗口与同一链路计量边界内，统计实际完成的 H2D 字节：

\[
V_{prefill}+V_{decode}+V_{other}\le\int_0^T B_{available}(t)dt.
\]

需要处理窗口边界的在途请求/在途传输，避免将窗口内生成的 token 与窗口外已加载权重混算。合批共享的唯一专家只计真实 DMA 一次。

`L*≈233` 的简单情景可以保留，但更一般的对照量应为：

\[
L^*_{traffic}=\frac{\text{一次预填的实测 H2D 字节}}{\text{该负载下每个输出 token 的平均实测 H2D 字节}}.
\]

不应把 byte/token 固定为所有上下文、并发与缓存配置的常数。CPU 分流、D2D、跨请求共享及实际策略改变后都应重测。

### R4｜§4.6、§5.3：非 MoE 8.1–9.7 秒，不能推出 MoE 再快也不够

**原文位置**：L369–375、L414–420。

原稿记录非 MoE 8.1–9.7 s，MoE 4.34 s，却断言冷 64K 进入 10 s “必须压非 MoE”。在这个分项相加近似下：

- 非 MoE 为 8.1 s 时，MoE 预算还有 1.9 s；4.34 降到 1.9 约需 2.28 倍提速。
- 非 MoE 为 9.7 s 时，剩余仅 0.3 s，所需提速约 14.47 倍，工程难度显然不同。

这只是使用原稿分项值的条件性算术，不是收益预测；实际还需扣除采样/发送等开销，并检查 MoE 加速后是否暴露更多搬运时间。

**建议替换**：

> 非 MoE 已占主要比例，优先拆分注意力、GDN、PLE 等暴露成本最有价值；现有数据尚不足以证明仅改进 MoE 在原理上不可能达到 10 秒。

同理，约 52.8K 是拟合模型在固定配置下的阈值，不是服务器的永久“冷启上限”。

### R5｜§4.5：无限合批模型不能解释真实服务的无界负载

**原文位置**：L343–365。

表中假定常数服务时间 D=2.66 s、无限合批容量，不计运行槽。原文已经披露这些限制，但正文仍写“合批把首 token 限制在 2D 以内，与负载无关”，并将其映射为上游实际能力。

**问题**：当合批容量有限，或已有解码占据运行槽，等不进下一批的请求会跨多个遍。纯反例：批容量 2、五个请求同到，即使没有其他开销，第五个也至少在第三批结束，约 3D=7.98 s，而不是 ≤2D。

同样，“一遍 16K 以下计算可隐藏”不表示任意个短请求相加仍 ≤16K；真实批次还有不同上下文的注意力、状态与工作区成本。

**建议**：保留该表为“无限容量、恒定批服务时间的理想化仿真”，不得称为有限系统的稳定性或 P95 保证。为现有脚本补有限批容量、实际 token 预算、decode 让出时间和状态准入；使用真实到达回放补充泊松情景。

单请求各一遍的 M/D/1 均值按公式可复现为 2.864、3.142、4.172、7.914 s，与表中近似相符；这不验证 P95、无限合批实现或真实部署。

“主动等待窗口在泊松到达下无益”仅是特定一阶、目标函数及低负载分析，不能写为一般证明。原稿自己指出，省下一遍对现存 decoder 还有价值；有这种外部收益时，评价目标已不同。

### R6｜§3.5、§6.8、§10.4：状态层门不能替代正确性准入

**原文位置**：L215–219、L564–568、L717–721。

同配置重复回放出现 3/12、4/12 正文不同，说明当前复现与判定方法有问题。它不自动证明这些差异全是无害“噪声”，也不能仅因为变体差异少于自比差异，就降低对恢复路径的要求。

**建议保留分层检查，但不替换原质量标准**：

1. **存储传输等价**：同一已生成状态的保存前副本与恢复后副本逐位比较，排除复制、别名、位置和生命周期错误。
2. **完整续算状态**：比较全部相关状态及元数据，不只 GDN；包括实际实现所需的 KV、有效长度、位置、卷积/PLE 等状态（仅在确实存在时），保证对应同一合法前缀。
3. **同输入数值检查**：在固定后续 token 的条件下比较恢复与参考计算的 state、logits，定位差异；自由生成差异不应先改变后续输入再拿来直接比较内部状态。
4. **端到端行为检查**：保留生成、工具调用、取消/回收等任务测试。用前三层解释差异，不用前三层免除这一层。

PyTorch 官方说明数学等价计算、不同批处理/平台可能不逐位相同。因此，发现分歧应定位原因；不能声称这些运行天生必须逐位相同，也不能将“可能有舍入差异”当作具体恢复 bug 不存在的证明。[S2]

TP 的“首处分歧 top-2 logit 很接近 + 60 题差距在噪声内”不是充分无损证明：top-2 接近不排除其他数值错误，60 题也不是完整质量边界。属于未来验收策略变更，需单独明确；第一阶段不要静默采纳为已认证标准。

对于 #577，当前正确状态应继续是 `kept_pending_gate`，不是因为速度收益显著就升级为通过。

## 6. 带宽定义与多卡部分的边界

### R12｜§2.1、§4.4、§9.1：不可混用 STREAM 与专家处理带宽

原文把 B_H 重新明确为“主存总带宽”，再将 STREAM 46.6/110.8 代入可用 CPU 带宽判断。但本次核对 FreeToken 原论文 §3.2，其文字定义为 **host-side expert-processing bandwidth**，并在简化剩余带宽模型中使用它。[S1]

因此，建议分别记录：STREAM 测得的原始内存基准、CPU 专家核独占有效处理率、CPU 与 DMA 同时运行时的两条实测完成率。q* 可作为近似基线，B_H 的物理含义和测量方式必须透明。

`STREAM - 独占PCIe` 不能在没有联合实测时成为严格 CPU 预算，更不能由此推出“只有绑 node1 才有物理空间”。线程布局、页面放置、任务颗粒和实际核路径都需实测。

hybrid 下降87%值得保留为重要负结果。每层差额折算1.8GB/s可作诊断，但不能据此唯一确认固定延迟。文中已将自旋屏障/抢占解释标为推断，这一点保留；继续用服务时间分解与绑核对照定位，不先重写执行器。
