# FreeToken 论文方向评审与主线收敛

日期：2026-10-03  
性质：研究方向决策建议；不是实测报告、原创性证明或性能承诺。  
处理：独立新增，不覆盖原测算、研究章程和工程修订方案。

## 1. 决策

保留工程总目标：同一份 Qwen3.8-Flash-Next-NVFP4、真正 TP=2/4、多用户访问、降低端到端 TTFT、提高每用户生成速度。不用多个 TP=1 实例替代真正的 TP，也不以增加总吞吐替代每用户性能。

调整论文定位：上一版“多 GPU 协同推理与多用户低延迟服务”可以保留为项目总纲，但尚不是足够集中的论文贡献。更早的“状态依赖干扰调度”保留为候选成本因素，不单独承担全部业务目标。

建议候选论文方向：

> **共享资源约束下，主存卸载 MoE 的多 GPU 低延迟协同执行。**

核心问题：多个请求在共享主存和互连的 TP 组上执行时，如何协调专家分片的驻留、搬运及执行顺序，减少真正阻塞首 token 和后续 token 的等待？

这里“协同”必须对应可实现、可对照的机制，不能只有一个联合优化公式。当前建议优先探索组级共享资源执行器：用同一组的完成时间和请求时限评价动作，而不是每个 rank 各自追求局部带宽或利用率。

**现阶段能决定的是研究主线及验证方法；不能宣布新机制已经成立，也不能保证四卡、八路、每路超过 30 token/s 与冷 64K 十秒首响应已经可以同时满足。**

## 2. 已有证据及其边界

### 用户材料

`PROJECTION_PERF_PLAN_20261003.md` 的范围说明：当前单卡 RTX 4090，目标 4×4090；约十个 Agent 会话，常态 2–4 路同时生成、峰值 8 路；阶段体验线为 64K、首个有用 token ≤10 秒、持续解码 >30 token/s。[F1]

同文件第 2 节记录：专家池约 68.14 GB；单卡专家槽与 KV 共同预算约 9.29 GiB；C1 约 38.28 token/s；混合负载他人最大字间隔约 16.69 秒。[F1]

这些是上传文档报告的数据。本次没有访问服务器、取得完整原始 trace 或复测内部工作树。并发差异来自缓存、共享带宽还是计算竞争，不能仅根据这些汇总数确定。

### 论文及代码

FreeToken 原论文已有共享专家缓存、整层双缓冲、按带宽分配缺失专家、混合模型状态复用与弹性内存管理。[S1]

固定提交 `d3512b43affe981465e03ee28cbd88f49c39b9aa` 的 `qwen4_exp/weight.py` 仍对 TP>1 抛出 `qwen4_exp weight loading supports TP=1 only`。该事实限定于此固定版本，不代表所有模型和之后的分支。[S2]

官方路线图列出了单机多 GPU TP。因而“补上 TP 支持”是重要工程能力，但论文贡献不能依赖上游暂时没有完成这一功能。[S3]

| Achieving Cloud-Grade SLOs | 本地少卡、分布式预填充、SmallEP、共享权重、节点内预填充/生成分离 | 本地多用户、多 GPU、共享权重与服务目标本身 [S5] |
| MoE-Infinity | 多 GPU 专家并行、NUMA 相关专家分配与各 GPU 缓存/I/O 管理 | 多卡专家缓存或 NUMA 布局本身 [S6] |
| Layered Prefill / SLOWeave | 按层交错执行、按下一 token 时限选择预填充块 | 层间插解码、动态分块本身 [S7][S8] |
| ExpertPlex | 跨阶段专家共享、持久化执行、rank 与通信干扰问题 | 单纯宣称“联合考虑执行与通信” [S9] |

这次核查不构成穷尽性的原创性检索。候选差异必须落实到：**现有方法为什么在我们的实际约束下失效，新机制如何处理这一失效，以及相同硬件上的实验证据。**

不能以“已有系统暂不支持同一模型”证明没有竞争方法；也不能将其他系统换格式、换模型后的结果混入同权重性能比较。

## 4. 候选科学问题

### 4.1 TP 不自动让全机专家搬运字节数除以卡数

在理想的等分 TP 中，假设一个缺失专家大小为 S、所有分片都需要、每片只传一次，k 张卡各传 S/k，全组仍传 S。

因此，多卡性能改善可能来自：独立传输路径的并行、更大有效专家驻留、更多计算资源，或更好的重叠；不能仅由“每卡分片变小”推出全机主存压力按 k 倍下降。

这是分片字节守恒的推理，不是新的理论贡献。实际是否有复制、对齐膨胀、缓存差异、主机中转等，需要按路径测量。

### 4.2 局部快不等于整个 TP 组快

对一个确实需要等待所有分片结果的归并边界，可用以下关系组织诊断：

\[
T_{\text{boundary}}\approx \max_r T_{\text{ready},r}+T_{\text{comm,exposed}}.
\]

各 rank 的 ready 时间使用共同起点；communication 只计未被重叠隐藏的部分，不重复加入等待。它不是完整模型的精确预测式。

例：在其他依赖不变的假设下，一个分片 8 ms 就绪，另一个 16 ms 就绪；只把前者优化到 4 ms，不会把这个归并边界提前到 4 ms。数字仅为示例。

更重要的是，各 rank 的 ready 时间并不独立：不同任务可能共享主存、CPU 执行资源、PCIe 上游或主机中转路径。具体共享关系必须由实际拓扑确定。

**不能预设一定存在严重慢 rank。** 若路由、缓存、分片和拓扑足够对称，额外协调的收益可能很小。对称场景必须作为控制组，不能故意破坏缓存来制造问题。

### 4.3 前序动作是否给后续请求增加额外工作

预填充或会话恢复可能改变专家缓存，进而影响后续生成；这保留了原研究章程中的问题。但“后续多出来多少成本”必须通过干预实验分解，不能直接把总延迟差归因于缓存。[S1][F1]

该因素先作为候选输入：如果在目标场景中影响小，就从控制器中移除，不为了维护旧题目强行保留。

## 5. 首版机制边界

首版只研究一个组级执行器。输入包括当前已知路由与驻留、可用缓冲、实际共享带宽、任务依赖和请求阶段；输出是有限的合法执行选择。

候选动作是：安排已确定缺失分片的传输与计算次序；在等总预算下短期保留确有价值的专家分片；在安全边界选择下一个预填充单元或生成批次。

CPU 分担不是主线必要前提。先在合格数值路径上研究；不能为了启用更多资源默认加入 w4a8 路径。

不在首版加入每 token 改 TP 宽度、在线重分片全部状态、任意 kernel 抢占、跨机器调度、新量化、MTP、复杂强化学习控制器或通用异构硬件支持。

TP 分组在一次实验/一次启动中固定。`1×TP4`、`2×TP2` 是需要比较的配置；`4×TP1` 是对照，不替代 TP 交付。

组级协调必须保留集体通信顺序和图捕获契约。NCCL 对捕获与启动在参与 rank 间的一致性有明确要求，不能把各卡独立的 Python 队列视为可任意交错。[S11]

## 6. 两个必须前置的风险检查

### 6.1 四卡后是否还处于大量专家卸载区间

不能把当前单卡缺失率和内存分配原样外推到四卡。也不能只因为专家池小于总显存，就判断所有专家可常驻。

每个 rank 都要核算：专家分片、其他常驻权重、KV、GDN、CUDA Graph、临时工作区和安全余量。TP 分片、复制项目和批大小决定各项大小。

需要分别识别全部专家可驻留、部分驻留、高状态压力下频繁卸载三种运行区间。在真实负载下出现哪一种，就按哪一种评价。

若 TP=4、目标负载下专家全部可驻留，而且调优后的普通 TP 已满足需求，应将其作为强基线和工程成功。不得人为缩小显存制造卸载问题，再据此宣称改进部署表现。控制显存实验可以研究敏感性，但必须明确标注为控制实验。

### 6.2 严格一致性是否允许预期并行路径

同权重、同量化位宽、不改专家选择，不自动保证浮点逐位一致。不同计算分组及归约顺序可能改变结果，PyTorch 官方对此有明确说明。[S10]

继续保留既定数值门，不自行替换为小题集质量相近。先测 TP 分片重构、局部计算、归并、最终 logits、长续写与状态恢复；若严格一致需要额外约束，也要计入性能成本。

原文件明确 w4a8 CPU 分支与逐位一致不同，相关收益单列。[F1：第 8 节]

## 7. 决定是否扩大投入的四组实验

| 实验 | 具体输出 | 要决定的问题 |
|---|---|---|
| 运行区间图 | TP=1/2/4 与不同上下文/并发下的逐卡内存、缺失流量与通信占比 | 目标部署是否真的受卸载主导 |
| 正确、调优的普通 TP 基线 | 相同权重的双卡最小原型，逐步到完整引擎；完整计时与数值门 | 不加新算法时能走到哪里 |
| 共享资源干扰干预 | 相同缓存初态、请求、数值路径和总预算；只改变协调策略；记录分片就绪、H2D、主存与归并等待 | 协调消除的是不必要工作/等待，还是仅转移延迟 |
| 多用户端到端对照 | 内容不同的请求、冷/热/恢复、长预填充＋生成、外部到达率控制 | TTFT与逐用户速度的可达到范围是否扩大 |

沿用现有 D0、E1-R005、E1-R007 等计时与路由输出，不重新建立一套重复看板。

可先使用原模型一个代表性层的双卡 TP 原型降低实现范围，但层级原型不是完整模型正确性或端到端性能验收。单卡模拟与离线 trace 可以帮助筛选，不能代替真实双卡/四卡的通信和争用测量。

## 8. 比较与归因规则

最关键的比较不是“单卡 FreeToken vs 我们四卡版本”，而是：

1. 同样四卡、同样权重与资源预算的调优普通 TP。
2. 在该 TP 上分别调好的现有缓存、分块和排队机制，再作简单组合。
3. 加入候选组级执行器的新版本。

公开算子移植、正确性修复对所有适用基线共同生效。硬件增量、工程修复和新算法收益分开归因。

先固定一种 TP 分组对照算法，再比较不同分组。不能用 TP 组变更带来的收益冒充调度算法收益。

以独立到达过程测试服务能力，保持输出预算、精度、上下文和质量门相同。合格请求比例的分母包括所有到达；拒绝、超时、排队到测量结束仍未完成的请求必须保留。

同时报告客户端 TTFT、每路生成速度、干扰期输出间隔、总吞吐、失败和内存峰值。首个模型 token 与首个有用业务事件分开。

固定每路速度要求比较 TTFT，或固定 TTFT 要求比较每路速度及合格吞吐；不能只展示一个加权总分。某一请求更快、另一请求更慢，本身是折中，不是证明效率提升。

若各路确实同时持续生成且都要超过 30 token/s，四路总量必要条件是超过 120 output token/s，八路是超过 240。登记会话数或工具等待中的会话不应混入这个并发计算。

## 9. 工程成功和论文成功分别裁决

工程：TP=2/4、多人访问和完整状态生命周期正确实现。  
性能：同一最终版本、规定工作负载下，TTFT和每用户生成达到约定改进或目标。  
研究：提出的机制解释了真实现象，并在同硬件强基线、简单组合及留出负载中获得可归因收益。

业务性能改善不必全部由同一个论文创新产生。冷长输入算子优化、检查点修复继续推进，并作为论文公平比较的基础。

仅支持 TP 不是论文完成；仅跑过一台机器一个测试点不代表一般规律。第一阶段不更换主模型。后续要主张可推广性，应有同模型多个真实配置/负载的留出验证；条件允许再补第二个兼容模型或另一节点，明确不是拿小模型替代本机业务验收。

理论部分应优先讨论资源与依赖约束、何时需要协调、何时退化为简单策略，以及控制成本，而不是为追求公式数量强行证明全局最优。`max-rank` 关系和 q* 的简单代数扩展本身不构成创新证明。

## 10. 冻结方向的规则

主线按本决策执行，不因单次性能波动继续换题。只有以下证据才触发重新评审：目标配置没有预设瓶颈；新机制被强基线或简单组合消除收益；相关工作已经用同等机制覆盖同等条件；数值、内存或实现接口约束使关键机制不适用。

遇到这些结果，优先采用更简单有效的方案改善实际服务，再重新界定研究贡献；不包装成新名称，也不制造人为瓶颈。

**最终建议：保留四项业务目标，收敛一个候选机制，先取得正确 TP 与共享资源关键路径的实证，再决定扩大实现范围。**
