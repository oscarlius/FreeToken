# FreeToken 第一阶段范围冻结与单卡验证协议

日期：2026-10-03  
状态：研究与开发协议；不是已经实现的功能清单，也不是实测结果。  
范围：现有一张 RTX 4090、当前主存条件、同一份 Qwen3.8-Flash-Next-NVFP4 检查点。

## 1. 本次决定

总体研究方向不改变：研究共享资源约束下，主存卸载 MoE 的低延迟协同执行，最终覆盖真正的 TP 多卡和多用户服务。

第一阶段只验证单卡上的基础机制，不同时开发多格式、多架构、多 GPU 执行和复杂状态迁移。以一个真实运行配置为中心，建立从现象、归因、预测到小范围在线干预的证据链。

前一版“多模型、多表示”的完整设计保留为未来讨论材料，不作为第一阶段的开发任务。暂不建设独立通用插件平台、统一中间表示或跨格式转换系统。未修改任何已有文档或源码。

### 支持范围冻结

| 维度 | 第一阶段约束 |
|---|---|
| 检查点 | 当前已跑通的同一份权重，记录文件清单与哈希 |
| 表示 | 只认证该检查点现有的 NVFP4 执行路径；原有 BF16 等非专家张量保持原样，不强制全模型 4-bit |
| 内核 | 固定实际运行的后端与打包布局，由本机日志确认，不凭模型名称推断 |
| 硬件 | 1×4090；CPU、主存、NUMA、PCIe、线程与软件版本全部记录 |
| 并行 | TP=1；不在单卡上宣布 TP=2/4 性能通过 |
| 用户 | 两路不同内容的请求作为核心混合负载；四路按真实容量做扩展或过载实验 |
| 上下文 | 保留 64K 业务目标和既有长上下文回归；先核实实际可分配状态容量，不把配置上限当作通过验收 |
| 研究改动 | 先测量与影子决策，再在已有安全边界启用一个执行决策点 |
| 暂不纳入 | 新增 FP8/GGUF/EXL3 原生适配、自动转码、MTP、新 CPU 数值路径、动态 TP 宽度、任意层抢占 |

上游已有的其他模型和量化代码不需要删除；它们不进入本阶段的认证范围。不要为了本阶段而复制、重写或永久分叉全部上游模块。

## 2. 多格式问题的事实与决策

vLLM 官方量化文档列出 AWQ、GPTQ、FP8 等多个方案，并给出硬件兼容矩阵；不能说 vLLM 只支持一种格式。[1] ExLlamaV3 的量化主线集中于 EXL3，同时支持多个模型架构。[2]

本项目选择窄范围，不是因为其他框架都只能支持一种格式，而是因为当前研究资源和验收范围需要可控。

第一阶段只新增两类必要信息：

1. **运行配置清单**：检查点、实际算术、后端、布局、软件版本、资源预算和通过的测试范围。
2. **测量记录约定**：阶段、实际字节数、已知依赖、时间戳、状态有效位置和实验条件。

同格式的新模型也不自动兼容：架构、路由和状态可能不同。未来新增一种真实组合时，再根据第二个实现的具体差异抽取共同接口；不提前为所有想象中的格式建立插件层。

未知组合应明确拒绝或标记未认证，不能静默转换、降低精度或更换数值路径。也不把“多格式全部转 NVFP4”设成默认方案：转换的质量、打包成本和兼容性仍需单独验证。

## 3. 单卡能够验证的科学问题

FreeToken 原论文已有整层双缓冲、共享专家缓存、带宽分工和前缀状态复用；第一阶段继承这些基础，不把它们重新命名为本项目创新。[3]

### H1：前序动作是否改变后续成本？

同样一个生成请求，在长预填充前后，是否有稳定、可解释的额外 H2D、缓存缺失、同步或状态恢复成本？

反证：控制缓存初态、状态预算、工作量和运行环境后，额外成本很小，或者主要由其他已知因素解释。

### H2：状态信息是否比长度与批大小更有预测价值？

比较只使用提示长度、批大小的简单模型，与增加实际专家驻留、已知缺失字节、执行阶段及队列状态的模型。

反证：新增状态在留出轨迹上不改善预测或决策，或者测量成本抵消收益。

### H3：利用这些信息是否真正改善服务？

在同一数值路径、资源预算和工作量下，状态感知策略能否胜过调优后的固定策略和不考虑后续代价的自适应策略？

反证：简单组合达到相同效果，或者新策略只是把等待转移给另一用户。

这些结果可以支持多 GPU 研究的基础机制，但不能证明多 rank 协调、NCCL 正确性、拓扑扩展收益或 TP=4 性能。

## 4. 实验步骤

### E0：冻结基线并分解执行

沿用已有 D0、E1-R000、E1-R005、E1-R006、E1-R007 以及 S1-lite/S1 的记录体系，不另建一套重复看板。

在用户文件 `PROJECTION_PERF_PLAN_20261003.md` 中，分支、旧测量与现有套件分别见第 5 行、27–36 行和 213–232 行。旧数字是用户文档记录，未经本协议复测，不作为新版本基线。

记录：

- 请求到达、准入、实际未缓存 token 数、模型首 token、首个业务有用事件、每个输出 token 和结束时间。
- 专家路由数量、唯一专家、唯一缺失专家、H2D 实际字节；避免把重复路由误计为重复拷贝。
- Prefill、Decode、GPU 算子、搬运、同步、CPU 线程、KV/GDN 恢复及临时峰值。
- 图捕获/JIT、缓存初态、GPU 温度与时钟、主存分配策略、后台负载。

分开两种采集：低开销计数用于正式性能测试；短窗口详细 profiling 用于解释原因。Nsight Systems 支持 NVTX 和限定采集区间，官方也提示部分图节点、事件与内存采集有明显开销。[4]

不能把重叠的 CPU、GPU 和 DMA 忙碌时间相加作为端到端耗时。不要逐层插入全设备同步来制造一个已经改变了的瓶颈。

正确性修复和已有公开内核优化先分别验证；通过后作为后续所有策略的共同强基线，不计入新调度方法的独占收益。

### E1：分离当场等待与后续恢复成本

这是首个核心机制实验。主试验先只使用一个生成请求 A 和一个预填充请求 B。

1. 通过固定 warm-up 与输入前缀，把 A 推进到可重复的逻辑位置和缓存初态；不要为了实验先开发完整主存会话迁移层。
2. 分别运行“不插入 B”“等时长空等待”“真实执行 B 预填充”三个条件。
3. 比较 A 恢复后的相同后续工作。机制试验可固定后续 token 或回放路由；它与自由生成的业务试验分开标记。
4. 记录恢复后 1、8、32 步的时间、H2D 和缓存缺失变化。预先固定观察窗口，避免看到结果后挑选最有利的窗口。
5. 对真实 B 的 KV/GDN 内存占用另做记录；诊断试验尽量保持相同总状态预算，区分“专家被访问挤出”与“额外状态挤占容量”。

定义一个用于诊断而非全局优化的量：

\[
\Delta_H=\sum_{i=1}^{H}t_i^{\text{after real prefill}}-\sum_{i=1}^{H}t_i^{\text{after matched idle}}
\]

两组必须在相同 A 逻辑位置上比较，区间只统计恢复后的 H 步，不包含插入预填充本身的时间。结果可以为正，也可以为负；负值可能提示预热收益。

耗时差不能单独证明缓存污染。必须同时核对额外 H2D、专家驻留、状态占用、时钟、队列和图状态。等时长等待也可能影响功耗与时钟，需观测而不是假定完全等价。

运行时预测不能读取下一层尚未产生的路由；固定轨迹回放和离线参考可知道未来，但不得当作可部署算法。

### E2：先评估预测和决策，不立即控制引擎

在候选合法执行动作上采集成本。按完整 Agent 轨迹/文档分训练、校准和留出集，不能把同一轨迹的相邻 token 随机拆到训练与测试两边。

比较：

- 简单模型：长度、批大小、静态参数。
- 状态模型：额外使用已知缓存、实际工作字节、当前队列等。

预测误差与决策收益分别报告。一个模型可能时间预测有偏，但仍能正确排序；也可能平均误差很小，却在临界动作上作出错误选择。

影子模式只记录“会选择什么”，不改变请求执行。影子结果不能作为真实加速证明。离线最优参考只代表已枚举候选中的参考，不宣称全局最优。

模型在实验前冻结；校准变化产生新版本，再通过新留出样本验证。不得在同一测试集反复调到满意后称泛化。

### E3：只上线一个最小执行决策点

第一版候选动作限定为：在已有、可验证的调度安全边界，继续推进预填充或执行已有生成批次。候选仍遵守依赖、状态有效位置和原数值路径。

第一版不同时动态改量化、选内核、切 TP 宽度、迁移会话和替换缓存算法。预填充分块候选先使用既有合法配置；不预设任意层都能返回调度器。

若本地当前路径在整段预填充结束前没有安全返回点，应先完成边界正确性原型，并单独测量额外开销。不要把“理论上想在层间切换”当作已经存在的接口。

统一比较三类策略：

| 策略 | 用途 |
|---|---|
| 调优后的固定策略 | 排除仅优于默认参数 |
| 只考虑当前成本/时限的策略 | 排除只靠一般动态调度取得的收益 |
| 增加后续恢复代价的候选策略 | 检验本研究新增信息是否有用 |

三组必须使用相同检查点、内核、总内存预算和工作负载。新策略不允许读取测试未来路由。将测量、建模与控制开销计入最终结果。

这只是候选机制，能否形成论文创新还需要独立相关工作对照；不能因为在 FreeToken 上新增了策略就宣布首次提出。

## 5. 最小工作负载矩阵

| 负载 | 主要目的 |
|---|---|
| 单请求冷 8K、32K；64K 容量通过后回归 | Prefill 曲线、TTFT、临时峰值 |
| 单请求纯 Decode，固定上下文与输出预算 | 原始每步成本与任何回退 |
| 两个真实不同上下文共同 Decode | 并发工作量、每用户速度、专家重合 |
| 一个长 Prefill + 一个 Decode | 首个核心干扰实验 |
| 已命中前缀 + 16/512/2048 token 后缀 | 重算量与整层加载启动成本 |
| 真实 Agent 的编辑、取消、重试和恢复 | 状态正确性与服务稳定性 |

四路实验作为扩展和容量检查，不预先承诺四路均满足 30 token/s。不要只修改提示头部来冒充不同内容。

现有配置若只分配了 49,152 token 的状态池，就不能直接宣称能同时驻留两路 32K。可以先选两路 16K 做机制实验，并清楚说明范围；两路 32K 必须先完成真实资源准入验证。不能在运行中静默缩短用户请求。

核心对照使用自然可用的内存预算。额外缓存容量、线程、NUMA 扫描属于敏感性实验，所有策略使用同样条件；不得通过人为压缩资源制造主结果。

## 6. 统计、质量与服务指标

### 统计

微基准使用可重复的配对实验，随机或交错安排 A/B 顺序，记录热状态；具体重复量根据预试验噪声和预先确定的最小有意义收益制定。两次请求不足以支撑稳定的 P95。

按请求或完整会话汇总，不把相关的逐 token 样本当成独立用户。尾部指标、置信区间和原始样本量同时给出，不只报告最快一轮。

正式容量实验包含外部控制到达率的回放；另保留真实 Agent 的闭环回放，并明确两者目的不同。不能只靠前一请求完成后才发下一个请求的压测隐藏排队。

### 指标

- 客户端 TTFT 包括排队；另记引擎首 token 和业务首个有用事件。
- 单请求 Decode 速度使用 `(输出 token 数 - 1) / (末 token 时间 - 首 token 时间)`；只有一个 token 时该项为不可计算，不填写零或无限大。
- 总吞吐使用共同墙钟窗口内的真实输出 token 数；不把每用户均值相加代替。
- 记录干扰期间的生成速度、P95 token 间隔、最长停顿及每用户分布。
- SLO 达标率的分母保留所有到达请求；未完成、拒绝、超时分开列出。达标吞吐与达标比例分别报告。
- 边界请求、测试末尾未完成请求和热身排除规则在跑前固定。

主结果比较“相同每用户速度约束下的 TTFT”和“相同 TTFT 约束下的每用户速度/合格服务量”。只改善最长停顿不能写成持续生成速度提升。

单请求原始 Decode 若没有减少任何真实工作或暴露等待，调度本身不一定能加速它。已有算子优化继续作为工程线推进，但不把它的收益重复归到新调度方法。

### 质量与状态

先确认基线自身重复性，再使用同一参考执行条件评估改动。覆盖完整续写、工具调用结构、批次形状、分块边界、前缀恢复、取消和资源回收。

同权重、同位宽并不保证不同批处理与归约方式逐位一致；PyTorch 官方文档明确提示这类差异。[5] 因此遵守已确定的一致性标准，不用小题集分数接近代替。

当前资料中标为 w4a8 的 CPU 路径不进入严格一致性的核心对照。未来若需要该路径，单独立项，不偷偷作为策略回退。

原论文 §5 包含 Experimental Setup、Main Results、Breakdown and Cross-Hardware Analysis，后者包括预填充流水、专家缓存轨迹回放与跨平台结果。[3]

完整性是保持问题、方法、实验与边界的闭环。第一阶段手稿是单卡机制验证报告，不是多 GPU 与跨硬件结论均已完成的最终论文。

多张同型号 4090 到位后首先得到的是扩展实验。跨 GPU 架构仍需不同硬件；同机调整线程或功耗不能替代。

## 8. 限制故障面的工程规则

1. 实验功能只有关闭、影子、启用三种清晰模式；默认关闭。这里是拟议配置语义，不声称 FreeToken 已有对应命令行参数。
2. 固定一条认证执行组合。未知组合不得自动降级精度或更换后端。
3. 保留原基线启动环境。必要时停机并重启原基线恢复，不承诺带复杂状态的瞬时热回滚。
4. 使用内核/传输事件和引用计数验证生命周期；正在使用的专家槽不得被覆盖，KV/GDN 有效位置必须配对。
5. 异常、取消和部分失败要有显式记录与资源释放，不能把请求丢弃后算成功。
6. 不同时改读取器、量化路径、调度和内核。修复与研究改动分开提交和验收。
7. 阶段稳定后，每次只新增一个维度：先在同一模型/格式上扩展 GPU 数，再考虑第二个模型或格式。
8. 性能优势不存在时，保留更简单的实现。增加支持项不作为成功指标，认证组合可靠性才是。

## 9. 阶段出口与转入多卡

阶段出口要求：

- 现象可以重复，且存在支持或否定假设的详细证据。
- 状态模型在留出负载上具有预测或决策价值；没有价值则停止该额外机制。
- 最小在线策略在相同约束下胜过强基线，或者明确报告未取得净收益。
- 数值、状态、取消和资源回收通过；新增测量和控制成本被计入。
- 原始数据、配置、脚本、预测版本和失败记录可追溯。
- 没有用缩上下文、变精度、丢请求、换小模型或不公平资源预算制造收益。

保留原 TTFT 和生成速度业务目标，不保证第一阶段单卡就满足所有峰值容量要求。没有达到目标不自动推翻方法；达到目标也不自动证明新增机制必要。

硬件到位后的顺序：保留当前检查点与格式，先实现并测量调优后的普通 TP=2，再对照新策略；随后扩展 TP=4。重新测量分片就绪、真实通信、主存争用和逐卡内存，不将单卡带宽简单乘以卡数。普通 TP 已能满足业务时，直接承认其效果，不人为制造难题。

## 10. 当前应交给开发 Agent 的最小任务

本轮不启动多格式适配或大规模调度重构，只交付：
