## 摘要

主存卸载 MoE 推理时，GPU 只缓存一小部分专家，其余专家一旦用到，就要从主存经 PCIe 搬运。我们在一张 RTX 4090（24 GB）上服务 Qwen3.8-Flash-Next NVFP4：路由专家共 63.46 GiB，常驻主存；GPU 只缓存约 12.8% 的专家槽。目标负载是约 10 个 Agent 会话。

FreeToken 原文已经指出两点：预填几乎会激活整个专家集合，一次预填要把专家池完整搬一遍。在此基础上，本文有三项主要工作。

**测量。**
- 冷 32K 首 token 降到 6.5–6.6 s，输出与父轮逐位一致。对照基线分两种口径：
  - 相对 4096 分块的 21.5 s。
  - 相对已调优的生产 8192 分块，约 13.0 s。
  - 其中层优先（D1）把 8 遍搬运变成 1 遍。13.8 → 6.5 s 这一段来自上游预填内核 #578（未合并的公开 PR），按本文归因规则不计入本文贡献。
- 在两条真实 Agent 轨迹和一组探针上，短后缀轮次的首 token 主要落在「一遍 ≈2.7–2.9 s」和「两遍 ≈5.3–6.0 s」两档；重算 token 数不足以解释这些差异。逐段 H2D 记录支持「当前整层加载路径下，每个请求至少一遍专家流」。
- 第二遍的触发条件，开关层面已有配对证据：在三组「提示首次出现」的独立进程配对里，开启锚点检查点比关闭多 2.6–2.9 s（约一遍）；在已命中前缀的重复请求上，两者相差 ≤ 0.08 s。把这一遍具体归因到 D3 的切段（而不是同一开关下的其他行为），要等逐段原因记录和只关切段的 E1-R008。
- 状态层：bank 恢复路径的存储与搬运逐位正确，但恢复后续算出的状态与整段重算不逐位相等；同配置两次整段重算的状态和 32 token 输出都逐位相同。所以 #577 不是逐位无损，是否可接受要用独立标定的容差判定（§6.8）。

**模型。** 我们用本机实测校准了一个带宽/算力模型，并在「当前每 token 未命中字节不变」的条件下推出两个量：
- $L^\*=E/(k\,m)\approx 233$：一轮输出超过约 233 个 token 时，这一轮解码搬运未命中专家所耗的 PCIe 时间，就超过了它的一遍预填。
- PCIe 链路给出的解码总量**条件上界**约 $83(1-u)$ tok/s，$u$ 为预填占用 PCIe 的时间比例。

这两个量是**必要条件**，不是可达性证明：

- **两路每路 30 tok/s**：只需 17.5 GB/s，PCIe 预算本身不排除它。「每路 21–23」来自传输与计算串行相加的模型。如果两路解码错开相位，让一路的搬运与另一路的计算重叠，由旧系数得到的理想情景为每路约 35–42 tok/s（不是实测，也不是已证明的上界）。
- **峰值 8 路**：要求每 token 未命中字节降到约 101 MB（现为 292 MB）。在当前缓存条件下看不到途径，更可能需要多卡。

**机制。** 我们提出以「专家流遍数」和「PCIe 时间预算」作为调度的成本单位，并对照上游代码说明各机制的现状、改动挂点和代价：每轮只搬一遍、多请求共用一遍、遍内插解码、短后缀按路由搬运。其中「同一调度时刻的多请求共用一遍」和「一遍之内取单个状态快照」上游已有，本文不把它们算作贡献。

## 1. 引言

### 1.1 问题与负载

- 单卡加主存专家池。每 token 激活 480 个专家（48 层 × top-10），未命中的专家经 PCIe 搬运。
- Agent 负载的特点：长上下文、多轮、带工具调用和思考段、中途编辑、多会话并发。
- 体验线：
  - 单会话 64K 窗口，首 token ≤ 10 s，持续解码 > 30 tok/s。
  - 常态 2–4 路同时生成，峰值 8 路。

### 1.2 与 FreeToken 原文的关系

FreeToken（Yang 等，UC Berkeley 等，arXiv 2608.16157）是本文的基础系统，以下机制均继承自原文，**不算作本文贡献**：

- 主存专家池是唯一真相，GPU 上的 LRU 专家缓存可被 CUDA Graph 捕获。
- 整层双缓冲预填。
- 解码时按带宽在 PCIe 与 CPU 之间分配未命中专家。
- 语义锚点处的线性层状态检查点。
- 弹性显存管理。

原文 §2.1 已写明「一次预填会把几乎整个专家池搬过 PCIe」；§5.3 测得每个 8192 token 预填块耗时 1.19–1.22 s，恰好是在 PCIe 5.0 上把 64.4 GB 专家池搬一遍的时间。**因此，「预填成本按遍数计」作为现象不是本文的发现。**

原文没有回答、而本文研究的是这个现象的后果：

1. 在 Agent 轮次上，遍数如何决定首 token（第 6 节）。
2. 多会话共享一条 PCIe 时，预填遍数和解码未命中如何分配同一份时间预算（第 4.4、4.5 节）。
3. 以遍数为成本单位，哪些调度机制有效、代价多大（第 7 节）。

原文的评测包含会话长到 56–65K token、带并发子 Agent 的负载（W3），所以「64K」和「有并发」本身不是本文的新场景。原文没有做的是：

- 把多会话之间共享 PCIe 的时间预算和调度作为研究对象。
- 双路 NUMA：其服务器实验限制为 6 线程，并绑到 GPU 所在节点。

### 1.3 研究问题

**总纲（项目层面）**：在共享资源约束下，实现主存卸载 MoE 的低延迟协同执行。

## 2. 背景

### 2.1 FreeToken 的解码分流

设某层有 $m$ 个未命中专家，每个专家 $S$ 字节。PCIe 带宽为 $B_P$。$B_H$ 按原文 §3.2 的定义，是**实测的主机侧专家处理带宽**（host-side expert-processing bandwidth）。原文假设 DMA 与 CPU 计算读的是同一个主存子系统，所以 PCIe 跑满时 CPU 只剩 $B_H-B_P$。

把 $q$ 个专家搬进缓存，其余 $m-q$ 个在 CPU 上原地计算，两路并行。令两路用时相等：

$$
\frac{qS}{B_P}=\frac{(m-q)S}{B_H-B_P}\ \Longrightarrow\ q^\star=m\,\frac{B_P}{B_H}
$$

第 2 版草稿没有定义 $B_H$，第 3 版误写成「主存总带宽」，这里按原文改正。$B_H$ 是一个测出来的处理速率，不等于 STREAM：

- STREAM 是原始内存基准。
- 「CPU 专家核独占时的处理率」与「CPU 和 DMA 同跑时两路各自的完成率」应分别实测。
- 剩余带宽模型只是近似基线。

### 2.3 与 KTransformers 的关系

KTransformers（SOSP 2025）让 CPU 用 AMX 计算路由专家。本机 Xeon Silver 4310 没有 AMX，KT 只能退到 avx2 后端，约 3K 输入就显存不足。

用第 2.1 节的式子看，KT 是 FreeToken 在「放置固定、所有未命中交给 CPU（$q=0$）」下的特例。详见 `_shared/PAPER_COMPARE_KT_FT_20261003.md`。

### 2.4 模型结构

- 48 层：36 层 GDN 线性注意力（key 头 16，value 头 48）；12 层带 indexer 的 QSA 稀疏全注意力（q 头 24，KV 头 2，head_dim 256）。

- 每层 512 个路由专家、top-10，另有 1 个共享专家。每个专家 $3\times2560\times640$ 参数，NVFP4 下 2,772,480 字节。
- 每 token 全失误字节 $S_{tok}=480\times2.77\ \text{MB}=1.331$ GB。
- 第 2 层有 PLE（N-gram 嵌入，钉在主存）。

| CPU | 2 × Xeon Silver 4310（每路 12 核，AVX-512F + VNNI，无 AMX）。NUMA 编号交错：node0 是偶数号 CPU，node1 是奇数号 CPU |

STREAM 只绑 node1 时反而高于交错，说明交错放置的专家池有一半要跨 UPI 读取。这对 CPU 路径（第 9.1 节）是重要约束。

### 3.3 轮次方法

- 一轮 = 代码版本 + 启动命令 + 模型 + 运行状态，跑固定套件，给出判定（kept / reverted / rejected / blocked）。
- 基础代码换代时开新一代（epoch），只在同一代内比较增量。
- 一轮只改一个变量。首 token 两轮取慢的一轮，解码取均值。预期收益 ≤ 5% 的项按 ABAB 跑四次。跨轮比较丢掉重启后的第一枪：第一枪偏慢 13–16%。
- 每一轮事先给出推算区间；实测偏离点估计 20% 以上时，先修正模型，再进下一轮。
- 起服务前必须断言 `freetoken.__file__` 指向预期 worktree，并通过单写者门（无监听、无显存占用、无其他批次进程）。这两道门在 E1 中各拦下过一次错误（第 9.3 节）。

### 3.4 归因规则

- 正确性修复和已有的公开内核优化（如 #578、#577）先单独验证，之后作为所有策略的共同强基线，不计入新调度方法的收益。
- 新策略与三类基线比较：调优后的固定策略；只看当前成本和时限的策略；加入遍数成本的策略。三者使用相同的检查点、内核、显存预算和负载。
- 不人为压缩资源来制造瓶颈；缓存容量、线程、NUMA 属于敏感性实验。
- 测量、建模和控制的开销计入最终结果。不把重叠的 CPU、GPU、DMA 忙碌时间相加。

### 3.5 数值门

- **单卡无损改动**：与父轮 temp0 输出逐位一致，覆盖全文、切块边界和每遍 H2D 字节。
- **改变执行路径的改动**（例如用快照恢复状态代替整段重算）：自由生成的输出层比较在 12–21K token 尺度上无法作为判据（第 6.8 节），但这**不降低**正确性要求。准入分四层，前三层用来定位差异，不能免除第四层：
  1. **存储传输等价**：同一状态的保存前副本与恢复后副本逐位相等，排除复制、别名、位置和生命周期错误。
  2. **完整续算状态**：比较所有续算所需的状态及元数据，包括 GDN、KV、有效长度、位置、卷积/PLE 窗口等实际存在的部分，确认它们对应同一合法前缀。
  3. **固定后续 token 的数值检查**：用相同的后续 token 序列，比较恢复路径与参考路径的 state 和 logits，定位首个差异层。
  4. **端到端行为**：生成、工具调用、取消与回收的任务测试。
- **当前进度（#577 恢复路径，第 6.8 节）**：
  - 第 1 层：通过，逐位一致。
  - 第 2 层：不逐位相等；同配置整段重算的跨进程基线为 0。
  - 第 3、4 层：未做。
  - 状态保持 `kept_pending_gate`。
- **容差必须独立标定**：不能用被检验路径自己的实测偏差（恢复 − 重算）当容差，否则检验必然通过。容差应来自一个**已知合法**的计算顺序变化：
  - 例如同一树上整段重算改用另一种子块大小。
  - 再把恢复路径的逐层误差曲线与这个参照曲线对照。
  - 最终在第 3 层用固定后续 token 的 logits 判定。
- **按项目先例**：E0-R007（子块 8192）同样改变计算顺序、破坏逐位一致，判为 rejected。恢复路径若按「非逐位但可接受」放行，属于验收标准的变更，需要明确记录，不能静默放宽。
- **多卡**的数值门见第 10.4 节。

### 3.6 测试套件与指标

- **套件**：
  - S1-lite：冷 32K 两轮（换前缀）、短上下文解码、确定性门。
  - S1：S1-lite 加 64K、Agent 回放、两路不同上下文并发、停顿测试、60 题、30 分钟稳定性。
  - S2：10 会话 Agent 回放，记录达标率（首 token ≤ 10 s 且解码 ≥ 30 的轮次占比）。
- **首 token**：客户端首 token 包含排队；另记引擎首 token 和首个业务有用事件（正文口径）。冷首 token 必须换前缀。
- **解码**：单请求解码 = $(n-1)/(t_{last}-t_{first})$。总吞吐用共同墙钟窗口内的真实输出 token 数计算，不把每路均值相加。
- **达标率**：分母保留所有到达请求；未完成、拒绝、超时分开列出。
- **Agent 回放**分三种口径，结论不能混用：
  - 升序热回放：同一进程重放已跑过的轨迹，几乎全命中。
  - 倒序真冷回放：先跑最长一轮，再跑它的前缀。
  - 编辑回放：`--edit-at-idx`。

## 4. 性能模型

### 4.1 遍数成本

一个预填段指一次完整的层循环（一次 `forward_batch`）。层优先模式下，第 $l+1$ 层专家的搬运和第 $l$ 层的计算重叠：

$$
T_{seg}(n)\approx \max\!\Big(\frac{P(1-h)}{B_P},\ C(n)\Big)+t_0
$$

- $P$ 为专家池字节（68.14 GB）。
- $h$ 为这一段里已在 GPU 上、可走 D2D 的专家比例。
- $C(n)$ 为 $n$ 个 token 的计算时间。

搬运一项为 $P/B_P=2.80$ s，实测每遍 2.86 s〔E1-R001 D0〕。只要 $C(n)<P/B_P$，计算就藏在搬运后面；本机对应约 16K token。

一轮被切成 $J$ 段时，与单段使用同一个重叠模型：

$$
T_{turn}\approx T_{queue}+\sum_{j=1}^{J}\Big[\max\!\Big(\frac{V_j}{B_P},\,C_j\Big)+\delta_j\Big]+T_{emit}
$$

- $V_j$ 为第 $j$ 段实际的 H2D 字节。
- $\delta_j$ 为流水启停、层间不均匀造成的气泡和其他暴露成本，需要用 trace 校准。
- 层间计算不均匀时，只取总搬运与总计算的 max 会低估气泡。

（第 3 版在这里写成了「$k$ 遍搬运加上全部计算」，与单段的重叠模型不一致，那只是完全不重叠时的上界。）

**推论 1（按 token 切块的代价）**：每多切一段，就多付一遍 $V_j/B_P$。冷 32K 按 4096 分块是 8 遍，推算约 22.9 s，实测 21.1–24.6 s〔E1-R001〕。

**推论 2（是否为保存状态多切一段）**：要比较两样东西：

- **现在的代价**：多切一段带来的暴露成本，在短后缀时约为一整遍。
- **将来的收益**：将来实际省下的首 token。

在重叠模型下，同一遍内多算的 token，在该段计算超过搬运（约 16K token）之前不增加时间。所以多切一段只有在下面两种情形下才划算：

- 它让将来的某一轮**少付一遍**。
- 它省下的重算量大到让计算超过搬运。

后缀从 10K 降到 1K，如果两者都只需一遍，就省了计算却没省时间。第 3 版的「14–16K 盈亏点」只是这个条件在加法近似下的一个特例。

### 4.2 冷预填（第 1 代重拟合）

层优先加 #578 后，每层计算约 131 ms，慢于每层搬运约 59 ms，冷预填受计算限制〔REPORT_E1 §2.2〕。N 以千 token 计，单位秒：

$$
T(N)\approx 0.068N + 0.107N + 0.0002N^2 + 0.2
$$

第一项是 MoE，后两项是非 MoE（注意力、GDN、PLE 等）。

- 32,064 token 推算 6.02 s，实测 6.07–6.60 s。
- 65,412 token 推算 12.50 s，实测 12.43–14.08 s。
- 令 $T\le10$ 解得 $N\le52.8$K。这是当前配置下的拟合阈值，不是永久上限。
- 64K 时非 MoE 占比：模型内约 64%，实测约 65–69%。

**适用范围**：MoE 系数直接来自 D0 计时（2.22 s / 32.8K）。非 MoE 的线性项和平方项由 32K、64K 两个点定出，**自由度为 0**，所以上面的「推算对实测」只是拟合一致性，不是验证。验证要用留出点（8K、16K、48K），列为待测。

### 4.3 解码

$$
t_{step}(B,L)\approx t_0+kL+t_{req}(B-1)+B\,\frac{m\,S_{tok}}{BW}
$$

- 第 0 代拟合：$t_0=13.1$ ms，$k=0.032$ ms/千 token，$t_{req}=5.3$ ms（来源：`PROJECTION_PERF_PLAN_20261003.md`，未在第 1 代重拟合）。
- $m=0.2193$ 时，每 token 搬 292 MB；当 $BW=B_P$ 时约需 12.0 ms。
- 32K 单路推算 38 tok/s，实测 36.6–39.8 tok/s〔E1-R001〕。

**假设**：

1. 这是**串行模型**：同一步内，未命中传输与其他计算相加，不重叠。这与当前实现相符：整步一张 CUDA Graph，批内各请求同步推进，层内只有命中专家的计算能与缺失拷贝重叠，每层约 30–50 µs。它不是执行结构的物理必然（第 4.4 节 (3)）。
2. 各会话路由独立且专家选择均匀，未命中相加。由 Astro 评审的复用比估算，$B=2$ 时 $R_B\approx1.01$。这是简化模型的对照值，不是实测。
3. $m$ 不随会话数变化。多个会话分享同一个缓存时 $m$ 可能升高。
4. $t_{req}=5.3$ ms 是从端到端差额估计的，还没有分解到组件。

同提示并发会让各路路由几乎相同，从而高估多会话吞吐：同提示 2 路合计 63.34 tok/s、4 路合计 96.57 tok/s〔E0-R000〕。这组数字不能当作多会话能力。

### 4.4 PCIe 时间预算（本文推导）

单卡卸载时，预填的整池搬运和解码的未命中搬运共用一条 PCIe。

**一般形式**：在同一窗口、同一链路的计量边界内，按实际完成的 H2D 字节计：

$$
V_{prefill}+V_{decode}+V_{other}\ \le\ \int_0^T B_{avail}(t)\,dt
$$

- 窗口边界上的在途请求和在途传输要单独处理。
- 合批共享的专家，只按实际 DMA 计一次。

**简化情景**：把字节写成「遍数 × 每遍字节」和「token 数 × 每 token 未命中字节」，带宽取常数 $B_P$：

$$
\underbrace{N_{pass}\cdot\frac{P(1-h)}{B_P}}_{\text{预填遍}}+\underbrace{N_{tok}\cdot\frac{m\,S_{tok}}{B_P}\cdot(1-\phi)}_{\text{解码未命中}}\ \le\ T
$$

$N_{pass}$ 为窗口内的预填遍数，$N_{tok}$ 为解码 token 数，$\phi$ 为交给 CPU 原地计算的未命中比例；$\phi=0$ 即 offload 模式。

「每 token 未命中字节」不是常数：它随上下文、并发数、缓存配置、CPU 分流、D2D 和跨请求共享而变，策略改变后要重测。由简化情景得到下面三个量。

**(1) 一遍预填等价于多少个解码 token。**

$$
L^\*=\frac{P}{m\,S_{tok}}=\frac{E}{k\,m}=\frac{512}{10\times0.2193}\approx 233
$$

一轮输出超过 233 个 token 时，这一轮解码搬运所耗的 PCIe 时间就超过了它的一遍预填。这是 $h=0$、无 CPU 分流、当前失误率下的简化值。一般情形用实测量：

$$
L^\*_{traffic}=\frac{\text{一次预填的实测 H2D 字节}}{\text{该负载下每个输出 token 的平均实测 H2D 字节}}
$$

真实输出长度尚无完整统计（回放只取前 32 或 200 个 token）。已知的下界是：回放中正文比首个思考 token 晚 3.4–4.8 s，按约 37 tok/s 折算，每轮在正文之前已有约 130–180 个思考 token〔E1-R003-v5〕。

**如果**每轮输出超过约 233 token，那么在多会话容量上，解码未命中就是 PCIe 的主要消耗，遍数调度只能省下预填那一部分。E1-R005 应统计每轮完整输出长度来检验这一条件。

**(2) 链路给出的解码总量条件上界。** 设预填占用 PCIe 的时间比例为 $u$，则：

$$
R_{max}=(1-u)\,\frac{B_P}{m\,S_{tok}}\approx 83\,(1-u)\ \text{tok/s}
$$

这是所有会话加起来、在「每 token 未命中字节为 292 MB」条件下的**必要条件**，不是可达值。对照两个目标：

- **峰值 8 路，每路 30（合计 240 tok/s）**：要求每 token 未命中字节 ≤ 24.3 GB/s ÷ 240 ≈ 101 MB，即失误率从 21.9% 降到约 7.6%，而且这时预填已没有 PCIe 余量。8 个会话共享一个只装下 12.8% 专家的缓存，看不到达到这个失误率的途径。所以这个目标更可能需要多卡，但它不是逻辑上的不可能。
- **两路，每路 30（合计 60 tok/s）**：只需 $60\times0.292=17.5$ GB/s < 24.3 GB/s。在预填占比 $u\le28\%$ 时，链路预算**不排除**这个目标。

**(3) 两路每路 30 tok/s：串行与重叠两种执行结构。** 链路预算只是必要条件，能否达到取决于传输和计算是否重叠。$B=2$、32K 上下文时，非传输部分约为 $13.1+1.0+5.3=19.4$ ms，两路未命中传输约 24.0 ms：

| 执行结构 | 步长 | 每路速度 | 说明 |
|---|---|---|---|
| 串行（当前实现，第 4.3 节） | 19.4 + 24.0 = 43.4 ms | 约 23 tok/s | 「每路 21–23」中，23 为本式点值，21–23 为轮次库 E1-R005 的推算区间 |
| 串行，补 CPU 带宽 | 要求传输项 ≤ 13.9 ms | 30 | 未命中处理带宽需 ≥ 42.0 GB/s（$m$=0.2193）或 ≥ 58.4 GB/s（$m$=0.3047，hybrid 实测失误率），即 CPU 侧补 17.7–34.1 GB/s |
| **错相位重叠**（理想上界） | max(19.4, 24.0) = 24.0 ms；两路各自发射时 max(2×14.1, 24.0) = 28.2 ms | 约 35–42 tok/s | 两路错开半步，A 搬运时 B 计算；PCIe 接近占满，预填几乎没有余量 |

几点说明：

- 第 3 版写「hybrid 是唯一的单卡杠杆」，这是错的。错相位重叠不需要 CPU，而且直接属于 H0 的「按 PCIe 时间预算编排」，应列为候选机制（第 7.5 节）。它在当前代码中不容易实现，因为整步是一张 CUDA Graph、批内同步推进。表中重叠一行是上界，有三点假设：
  - 单路内部「路由 → 搬运 → 计算」有数据依赖，无法自我重叠，重叠只能来自两路错相位。
  - 两路若各自独立发射，非传输的固定开销各付一次（每路约 14.1 ms），上界从 41.6 降到约 35.5 tok/s。
  - 24.0 ms 情景要求 PCIe 无气泡占满；28.2 ms 情景下传输只占约 85%，但剩下的余量受依赖与执行边界约束，不保证能给预填用。
  - 19.4 ms 是整步剩余项的拟合值，尚未确认其中有多少是能被另一路搬运覆盖的 GPU 工作。所以 35–42 tok/s 是由旧系数得到的两个理想情景，不是实测、置信区间或已证明的硬上界。

  未扣除两路之间的气泡和资源争用。
- CPU 路径的可行性不能用「STREAM 减去 PCIe」直接判断：$B_H$ 是实测处理率（第 2.1 节）。STREAM 交错 46.6、只绑 node1 110.8 GB/s 只能作为量级参考。真正的判据是 CPU 与 PCIe **同时运行**时两路各自的完成率，以及两路端到端的速度。
- 所有这些数都依赖串行模型的系数：第 0 代拟合，$t_{req}$ 尚未分解。所以都要由 E1-R005 的实测和路由/H2D 计数来确定实际瓶颈。

### 4.5 多会话的遍数排队（本文推导）

**这是理想化仿真**：服务时间取常数 $D\approx2.66$ s（短后缀一遍〔E1-R003〕），轮次按泊松过程以速率 $\lambda$ 到达。它**不是**有限系统的稳定性或 P95 保证。

比较两种策略，结果由 20 万次到达的仿真得出（`scripts/pass_queue_model.py`）。「每请求各搬一遍」列与 M/D/1 解析式吻合，误差在 1% 以内。下表中合批容量不设上限。有限容量表用的是 10 万次到达、另一个随机种子，同一格与本表可差约 3%：

| $\lambda$（轮/s） | 每请求各搬一遍：首 token 均值 / P95 | 同一时刻合批：均值 / P95 | 合批时预填占 PCIe | 合批时解码余量（tok/s） |
|---|---|---|---|---|
| 0.05 | 2.86 / 4.49 s | 2.83 / 4.31 s | 13% | 72 |
| 0.10 | 3.14 / 5.23 s | 3.00 / 4.80 s | 26% | 62 |
| 0.20 | 4.16 / 8.68 s | 3.29 / 5.04 s | 47% | 44 |
| 0.30 | 7.87 / 20.1 s | 3.51 / 5.11 s | 64% | 30 |
| ≥ 0.376 | 不稳定（$\lambda D\ge1$） | ≤ 4.0 / ≤ 5.2 s | → 100% | → 0 |

读法：

- **在无限容量、常数服务时间的理想化下，合批把首 token 限制在约 $2D$ 以内。** 这个结论依赖三个前提：
  - 合批容量无限。
  - 批内总计算仍藏在搬运后面（总量约 16K token 以内；真实批次还有不同上下文的注意力、状态和工作区成本）。
  - 没有运行槽限制。

  容量有限时，等不进下一批的请求会跨多个遍。最简单的反例：容量 2、五个请求同时到达，第五个要等到第三批结束，至少 $3D\approx8.0$ s。有限容量的仿真结果（均值 / P95，单位 s）：

  | 每遍容量 | $\lambda$=0.3 | $\lambda$=0.5 | $\lambda$=0.8 |
  |---|---|---|---|
  | 1（即各搬一遍） | 8.08 / 20.5 | 不稳定 | 不稳定 |
  | 2 | 3.71 / 5.62 | 4.79 / 8.42 | 不稳定 |
  | 4 | 3.52 / 5.12 | 3.79 / 5.19 | 4.09 / 5.46 |
  | 无限 | 3.52 / 5.12 | 3.77 / 5.16 | 3.93 / 5.18 |

- 上游已经实现「同一时刻排队的请求合成一遍」（第 2.2 节），受 token 预算限制。所以这一列描述的是**上游已有行为**在理想条件下的表现，**它不是本文的新机制**。真实系统还要补三样东西：实际的 token 预算、解码占用的运行槽、真实到达回放。
- **合批解决首 token，但把问题转移到了解码。** 负载升高时，预填遍占满 PCIe，其他会话的解码余量趋于 0。单卡多会话的真正约束是第 4.4 节的预算。
- **主动等待窗口**（等 $W$ 秒再发车，凑更多请求）：在泊松到达、只计首 token、一阶近似下几乎无益。这不是一般证明。一阶分析如下：
  - 窗口让首个请求多等 $W$。
  - 窗口内再来一个请求的概率约为 $\lambda W$，它能省下约 $D-W$。
  - 净收益为正的条件是 $\lambda(D-W)>1$，它要求 $\lambda D>1$（必要条件）。但这已经是排队自然合批的过载区。
  - 例外有两种：突发到达，例如子 Agent 同时发起请求；以及省下的一遍能换来其他会话的解码 token，这时省下一遍的价值约为 $233$ 个解码 token。
- 还有一条模型之外的现实约束：生产配置 `--max-running-requests 2`。10 个会话中至多 2 个处于运行态，其余会话的准入受 KV 容量限制。这一层由 D8（主存会话层）和多卡解决，不属于遍数调度。

| Agent 轮次首 token ≤ 10 s | 两条轨迹的非冷轮次在 2.6–6.1 s | 当前预填路径的实现地板约 2.7 s | 两条轨迹上低于 10 s；单会话，多会话未测，不等于业务首响应已验收 |
| 其他会话的停顿 | 第 1 代未测；第 0 代实测最长 16.69 s | 推算约等于预填时长 | **未达标，未验收** |
| 单会话解码 > 30 tok/s | 36.4–39.8 tok/s | 无未命中时约 71 tok/s | 已达成 |
| 两会话同时解码，每路 > 30 | 未测；串行模型推算每路 21–23 | 链路预算不排除；需要 CPU 补带宽，或者错相位重叠（第 4.4 节 (3)） | 未测，有条件的候选路径 |
| 峰值 8 路，每路 > 30 | — | 每 token 未命中字节要降到约 101 MB（现为 292 MB） | 当前条件下看不到途径，更可能需要多卡（第 10 节） |
| 约 10 会话驻留 | 运行槽 2 | KV 和运行槽限制 | 需 D8 或多卡 |

**冷 64K 的说明**：在分项相加近似下，非 MoE 取 8.1 s 时，MoE 只要从 4.34 s 降到约 1.7–1.9 s，就能进 10 s，所以这不是逻辑上不可能。但 64K 的 MoE 按每 token 约 4.72 GFLOP 计约为 309 TFLOP。

- 压到 1.7–1.9 s 需要 163–182 TFLOPS，已是 4090 BF16 峰值（约 165 TFLOPS）的 99–110%。
- 1.7 与 1.9 的差别在于是否扣除拟合常数 0.2 s。
- 非 MoE 取 9.7 s 时，MoE 预算只剩 0.1–0.3 s，需要峰值的 6–19 倍。所以在冻结的数值路径下，**实践上**要先拆分并压缩注意力、GDN 和 PLE 的暴露成本。

**结论**：

- H0 直接作用于首 token 和停顿。首 token 在两条单会话轨迹上已低于 10 s；停顿在第 1 代没有实测，不能算达标。
- 多路每路速度和冷 64K 两项还没达标，H0 对它们有间接作用：省下的遍数会还给解码的 PCIe 预算；错相位重叠属于同一套预算思路。但它们都不是 H0 已经证明的收益。

### 6.3 地板：每个请求至少一遍

**现象**：

- T2 中，只重算 1 个 token 的轮次，首 token 仍为 2.67–2.68 s（A/B/C 三臂）和 2.95 s（臂 D，稳定慢约 0.25 s，原因未查明）〔E1-R003-v4/v5〕。
- 首 token 地板探针（`ft_probe_floor2.py`，按首个带内容事件计）〔E1-R003-floor，E1–E4〕：
  - 400 字符请求（单块）：冷启和命中都在 2.85–2.95 s，四格（两种预填模式 × 开关）相同。
  - 20,000 字符请求：层优先冷 3.05–3.10 s、命中 2.77–2.80 s；4096 分块冷 5.79–5.80 s。**与预填模式有关**：一遍对两遍。
  - 所以「与预填模式无关」只对单块的短请求成立。

**本文的归因：地板是「每个请求至少一遍专家流」。** 它是**当前预填执行路径的实现地板**，不是模型或硬件的物理下限：按需搬运（第 6.7 节）可以低于它。

1. **代码路径**：前缀匹配故意留下至少 1 个 token（`cache.py:96`），预填对任何长度都整层搬运（`moe.py:347-384`）。所以完全命中的请求也要付一遍。
2. **数值吻合**：地板 2.8–2.9 s 与 $P/B_P=68.14/24.3=2.80$ s 吻合，与 D0 实测每遍 2.86 s 吻合。
3. **随块数翻倍**：分块（4096）模式下 20,000 字符（约 5K token，两块）冷启为 5.79–5.80 s，正好两遍；层优先下同一请求为 3.05–3.10 s，一遍。一个与预填无关的固定开销不会随块数翻倍。
4. **D0 直接证据**：短段计算 2.2 ms，整段 2.79 s，搬运 57.7–63.5 GiB〔E1-R003 D0〕。

E0-R008 的「整段重发」（13,181 token 中命中 13,120）为 2.69 s，也是这个地板。

**与 `RESULTS_E1` 解读的分歧**：`RESULTS_E1` 第 6 条（19:23 定稿）把它记为「每请求固定成本，与提示长度、命中、预填模式、开关都无关」，并推论「所有 FT 的 TTFT 读数都含这 2.87 s」。

- 「与预填模式无关」只对单块请求成立，20,000 字符请求在两种模式下是 3.1 对 5.8 s。
- 把它当作可叠加的固定开销，与第 3 条及第 4.1 节的重叠模型不符：层优先冷启受计算限制，这一遍搬运藏在计算后面，不能从冷 32K 的 6.5 s 里扣掉 2.8 s。
- 多消息请求多出的一遍，见第 6.4 节的四格数据；它不是消息条数本身的代价。

最终裁定只需从现有工件里核对一条：取一个 `recomputed=1` 请求，看它的 D0 每遍 H2D 字节是否约为 63 GiB。

探针第一版把首个 SSE 事件（空 `role` 增量，约 0.01 s）当成首 token，读数作废。

### 6.4 第二档：开关层面的配对证据与待闭合的机制归因

**已知事实**：

- 上游的 `--enable-special-token-ckpt` 只在解码期取快照，不切预填（`scheduler.py:126-134、908-909`）。我们的第 1 代树在同一开关下加入了 D3 的「预填锚封顶」（提交 e92fdf5 / cd450be）。所以在本树上，这个开关同时控制「解码期快照」和「预填按锚点切段」两件事。
- 轨迹上，是否切段与后缀里有没有锚点相关，与后缀长短无关：T1 冷进程里重算 176 token 时是两段，热进程里重算 45 token 时是一段；T2 编辑趟里重算 291 token 是两段，重算 415 token 是一段。这个关联性观察的段数来自 D0 记录，切段原因尚未逐段记录。

**开关四格**：同一棵树（e1r003）、层优先或分块、独立进程，按相同的准备顺序发送同一组探针。「冷」指这条多消息提示在本进程**第一次出现**；「热」指同一提示的第 2–5 次重复（已命中前缀）。两批的提示形状不同：batch14/16 为 7 条消息、约 3.5K token；batch17 为 13 条消息、约 7.0K token。冷格差值跨两种形状复现。

| 格 | 开关开 | 开关关 | 差 | 来源 |
|---|---|---|---|---|
| 冷，层优先（batch14/16） | 5.43 s | 2.80 s | +2.63 s | E1-R003-floor E1（batch14）/ E2（batch16） |
| 冷，分块（batch16） | 5.73 s | 2.90 s | +2.83 s | E1-R003-floor E3/E4 |
| 冷，层优先（batch17） | 5.864 s | 3.054 s | +2.81 s | E1-R003-ckpttax T1/T2，rep0 |
| 热，层优先（batch17，各 4 次） | 2.940–2.950 s | 2.941–2.955 s | ≈ 0 | 同上，rep1–4 |
| 单条消息（batch17，各 5 次） | 2.862–3.095 s | 2.865–3.080 s | ≈ 0 | 同上 |

**执行事件**（各臂 `serve.log` 的预填记录，段数取自执行事件，不由 TTFT 反推）：

| 批次与提示 | 冷格，开 | 冷格，关 | 热格（两臂） |
|---|---|---|---|
| batch14/16，7 条消息（两臂的已缓存前缀都是 64 token） | 两段：2,816 + 640 | 一段：3,456 | — |

**读法**：

- 三组冷配对的差值均为 +2.6–2.9 s，与一遍专家流（2.80 s）相符。这三组来自两个批次、两种预填模式；热格无差。
- 结论（开关层面，段数与耗时相互印证）：在本树上，开启该开关时，**含未缓存锚点的首次请求被切成两段、多付约一遍；已命中的重复请求只有一段**。冷格每格只有 1 个样本（三组复现）；另外，每臂的第一个冷请求同时也是该进程第一次走分段路径，这一混杂无法排除。Agent 的每个新轮次，后缀恰好是首次出现的新消息，属于前一种情形。
- **对 19:22 撤回的处理**：`RESULTS_E1` 于 19:22 依据 batch17 撤回了「开关税」，并改判为「开关在首 token 上没有可测代价（≤ 0.08 s）」，合并审阅也据此要求撤回因果解释。但那次撤回只比较了「开」臂自己的首次（5.864 s）与重复（2.94 s），然后用 5 次的中位数比较两臂。中位数由 4 个热样本决定，把冷格的差值掩盖了。同一批次「关」臂的首次是 3.054 s。按合并审阅自己提出的四格设计（§5.2）读同一份数据：冷格 +2.81 s，热格 0。所以本文**不接受**这次撤回的结论，只接受它暴露出的问题：此前的单点对照没有区分冷热状态。原始读数全部保留。
- **仍未闭合的部分**：开关关闭时，快照和切段一起被关掉。所以「多出的一遍来自 D3 切段」仍是机制层面的假设，要靠两样东西闭合：
  - 逐段记录切段原因。
  - 「只关切段、保留快照」的 E1-R008。

  E1-R008 的冷格与热格要分开报告，每格独立重建状态并重复；同进程连续的热请求不能当作独立的冷样本。
- E0-R009（每个轮次边界都切一段时，Agent 轮次首 token 为 23 / 21.4 / 2.73 s）与「多切一段就多搬一遍」方向一致，但它也不单独构成因果证据。

### 6.5 机制一：每轮只搬一遍（D12）

- **第一步**：先用 E1-R008 验证额外的一遍是否由切段触发，再去掉可避免的那一遍。
  - **情景推算**（不是验收承诺）：如果第二档全部来自可移除的切段，且快照能力不退化，T1 均值从 3.46 s 降到约 2.71 s，最大值从 5.31 s 降到约 2.82 s。
  - 第 6.4 节的开关四格支持冷请求上存在这一遍；机制归因待 E1-R008。
  - 若 E1-R008 不支持切段归因，就撤去这条收益假设；H0 不因此失效。
  - 这一步是修我们自己引入的回退，不算论文贡献。
- **第二步**：在一遍之内取多个锚点快照。
  - 上游已能从 GDN 分块扫描里取每请求 1 个 ×64 边界（`linear.py:110-122`），本文的增量是「多锚点」加「主存状态库」。
  - #577 的 host bank 在层优先下确实生效：T2 倒序真冷趟，臂 C（层优先 + 32 个主存槽）12 轮中 5 轮命中、合计 83.61 s；单变量对照臂 D（层优先、0 槽）0 轮命中、合计 126.39 s〔E1-R003-v4/v5〕。所以 D3 改为以 #577 为存储层，只需自写触发点。

### 6.6 #577 的收益在哪种轨迹形状上

T2 三种回放的 12 轮合计〔E1-R003-v4/v5，同树 c721c74，窗口 49,152〕：

| 回放 | A 分块 + 32 槽 | B 分块 + 0 槽 | C 层优先 + 32 槽 | D 层优先 + 0 槽 |
|---|---|---|---|---|
| 倒序真冷，首 token 合计 | **66.57 s** | 211.15 s | 83.61 s | 126.39 s |
| 倒序真冷，命中轮数 | 11/12 | 0/12 | 5/12 | 0/12 |
| 升序热，首 token 合计 | 32.35 s | 34.90 s | 32.31 s | 39.16 s |
| 编辑，首 token 合计 | 48.36 s | 48.12 s | **45.69 s** | 48.71 s |

**口径**：「倒序真冷」是沿用的标签，含义是新进程先计算最长一轮，然后测试它的各个前缀（回滚形状）的复用。它不表示每个请求都没有任何已算前缀。纯追加、回滚、编辑三种形状分开报告。

**噪声**：同配置复跑的合计差为 +2.0%（A 对 A2：66.57 对 67.87 s）和 +0.12%（B 对 B2：211.15 对 211.40 s），逐轮命中量完全相同〔E1-R003-v5〕。这是倒序趟上每对一个样本的估计。

- **回滚形状**：#577 有效。A 比 B 快 3.17 倍，重算量减少 82.9%；C 比 D 少用 33.8% 的时间。差异远大于噪声，但只来自一条轨迹，不能推广到所有轨迹。
- **纯追加**：主存状态库无事可做。
- **编辑趟**：A 对 B 为 48.36 对 48.12 s，差 0.5%，落在噪声内，而且启用 bank 的 A 还略慢。C 对 D 为 45.69 对 48.71 s，差 6.2%，只有一个样本，需要重复测量才能下结论。
- **不拼接**：C、D 不含 #578，第 5.2 节含 #578。两组数字分别报告，不拼成一台已验收的系统。
- **全量重算轮**：层优先 12.11 s，分块 23.36 / 23.01 s。
- C 和 D 都不含 #578，所以首 token 的绝对值高于第 5.2 节。

### 6.7 机制四：短后缀按路由搬运（D13）

后缀只有 $n$ 个 token 时，在路由**独立且均匀**的假设下，一层里被用到的专家比例约为：

$$
f(n)=1-(1-10/512)^n
$$

这是简化模型的对照值，不是实测。真实路由偏离这个假设时，误差有界：

- **无条件的界**：真实比例总落在 $[\,10/512,\ \min(1,10n/512)\,]$ 之内。下界对应所有 token 选同一组专家，上界对应各 token 的专家互不重叠。
- **token 独立同分布时**：设每个专家被选中的概率为 $p_i$，$\sum p_i=10$。用到的专家数期望为 $\sum_i\big[1-(1-p_i)^n\big]$。$g(p)=1-(1-p)^n$ 是凹函数，由 Jensen 不等式，均匀分布时这个和最大。所以在这个条件下，热专家只会让 $f(n)$ 变小，D13 收益变大。
- **其他情形**：token 之间分布不同（例如路由随位置或内容系统变化），或者 token 之间负相关，都可能让用到的专家超过 $f(n)$，直到上面的上界。正相关则让它变小。

所以偏差的方向确实不固定，但有界：在独立同分布下只会偏小，一般情形下不超过 $\min(1,10n/512)$。

实际值由 E1-R007 的路由轨迹直接测量。

| n | 1 | 19 | 32 | 64 | 128 | ≥ 256 |
|---|---|---|---|---|---|---|
| $f(n)$ | 2.0% | 31% | 47% | 72% | 92% | ≥ 99% |
| 推算一遍（s） | ≈ 0.1（含约 0.06 s 固定开销） | 0.9 | 1.3 | 2.0 | 2.6 | 2.8 |

**适用面要按真实后缀判断，不能按热回放判断。**

- 热回放的重算量只有几十 token。按热回放推算，D13 能把 T2 臂 C 的均值从 2.69 s 降到约 1.3–1.4 s（随固定开销常数的取法而变），但这个数字**不代表真实循环**，因为热回放重放的是已算过的轨迹。
- 真实循环里，新后缀是模型输出加工具结果。T2 相邻两轮的提示增量为 39–4,897 token（中位数 330），11 个增量里只有 1 个低于 64。但提示增量不等于实际的 `recomputed_tokens`：上下文编辑和已缓存的生成内容都会改变两者的关系。所以有效后缀分布要由 E1-R007 在线回放直接统计。

所以 D13 的真实收益集中在两类情形：一是重发、重试、短追问（n 为 1 到几十）；二是第 6.3 节的地板。

代价有三：

1. 路由要等本层注意力算完才知道，按需搬运无法提前预取下一层，搬运落在关键路径上。
2. 预填 GEMM 假设位置等于专家号（`moe.py:418-421`），需要改用 slot 视图或退回解码 GEMV。
3. 按需搬运会挤占解码的缓存。

D13 定为补充分支，先由 E1-R007 导出真实后缀长度分布，再决定是否做。

- uid=8 缺少完成捐赠记录，作为独立缺陷归因，不与无损性判定混在一起。

## 7. 多会话机制（设计、推算与代价）

### 7.1 基线测量（E1-R005，待测）

- **两路不同上下文同时解码**：推算每路 21–23 tok/s。同提示对照为 31.7 tok/s，只用来暴露同提示陷阱。
- **停顿**：冷 32K 预填期间，其他会话的最长停顿，按第 1 代预填时长推算约 6.1–6.6 s。第 0 代实测为 16.69 s（层优先）和 20.37 s（分块），见 `RESULTS_DEV_D1`。Agent 轮次预填期间为 2.7 或 5.3 s。
- **两个短后缀轮次同时到达**：核实它们合进同一遍（第 2.2 节）。
- **H1 附带测量**：只用一个解码请求 A 和一个预填请求 B，比较三个条件：不插入 B、等时长空等、真实执行 B。诊断量为：

$$
\Delta_H=\sum_{i=1}^{H}t_i^{\text{真实预填后}}-\sum_{i=1}^{H}t_i^{\text{等时长空等后}},\qquad H\in\{1,8,32\}
$$

同时记录额外 H2D、缺失数、状态占用和 GPU 时钟；仅凭耗时差不能证明缓存被冲掉。上游的预填双缓冲借用 LRU 缓存的前 $2E$ 个槽，并把它们标为首选牺牲者（`offload_cache.py:611-616、635-643`），这是 $\Delta_H>0$ 的一个具体来源。

### 7.2 机制二：多请求共用一遍（D7）

- **上游已有**：同一调度时刻排队的请求合进同一遍。
- **本文可加**：一个短的突发等待窗口（几十到几百毫秒），只针对子 Agent 并发这类突发到达。按第 4.5 节的一阶分析，它对泊松到达、只计首 token 的目标几乎无益；如果把省下的一遍还给解码，评价目标就变了，需要另算。
- **代价**：2–3 人日（`scheduler.py:870-880`、`prefill.py:292-346`）。
- 不能在一遍中途加入，新请求必须从第 0 层开始。

### 7.3 机制三：遍内插解码（D6）

- **目标**：在一遍预填的层边界插入其他会话的解码步，替代按 token 切块，因为按 token 切块每切一刀就多一遍。
- **停顿与干扰期速度要一起看**：「最长停顿 ≤ 1 s、预填只多约 0.2 s」只在其他会话几乎停住（约 1 tok/s）时成立。干扰期要让其他会话每秒前进 $r$ 个解码步（单路时即 $r$ tok/s；批内多路时每步产出多个 token），每步约 26 ms。在「固定步长、整步串行插入、忽略切换成本」的假设下，预填时间放大为下式。这是情景估计，不是无条件上界：冷长预填时 PCIe 约有 55% 空闲，插入步的搬运部分可能被吸收，使实际放大更小；缓存扰动、图切换和恢复成本又可能使它更大。

$$
T'_{prefill}\approx\frac{T_{prefill}}{1-r\,t_{step}}
$$

| $r$（步/s） | 1 | 5 | 10 | 20 | 30 |
|---|---|---|---|---|---|
| 放大倍数 | 1.03 | 1.15 | 1.35 | 2.08 | 4.55 |

  所以 D6 的验收必须同时报告最长停顿和干扰期的输出速度。预填正在算时 PCIe 空闲，并不等于解码可以免费插入。
- **代价最高（15–25 人日）**：
  1. 层循环要改成可让出的生成器，突破 `Context.forward_batch` 不可嵌套的限制。
  2. 解码 CUDA Graph 是整模型一张图，只能整步插入。
  3. 预填双缓冲槽可能被解码的 `ensure_experts` 覆盖，必须先把缓存分区。
  4. 插入的解码未命中要与整层搬运争 PCIe，需要关键传输优先。
- **一个有利条件**：冷长预填受计算限制，每层计算 131 ms，而搬运只需 59 ms，PCIe 约有 55% 的空闲。解码未命中可以用这部分空闲；短后缀遍则受搬运限制，插入的解码会直接拉长这一遍。

### 7.4 按遍数和 PCIe 预算准入

新请求到达时，用第 4.4 节的预算决定加入当前这一遍还是等下一遍，判据包括「还要搬几遍」、各请求的首 token 时限，以及其他会话的解码余量。这是 H2、H3 的入口。

### 7.5 候选机制：两路错相位重叠解码（D14，新增）

- **思路**：两路解码错开半步。A 的未命中拷贝与 B 的计算重叠，反之亦然。理想步长从串行的 43.4 ms 降到 24.0–28.2 ms，每路约 35–42 tok/s（第 4.4 节 (3)，假设见该处）。
- **与 H0 的关系**：它不减少字节，只是重排 PCIe 时间。这正是「以 PCIe 时间预算为调度单位」的另一种用法，不需要 CPU 路径和新的数值路径。
- **代价**：
  - 当前解码是整步一张 CUDA Graph，批内同步推进。要改成两路分别成图、交错发射，或者在图内按层拆分两路的流依赖。
  - 两路的缺失拷贝要排进同一条拷贝流，不能互相阻塞。
  - PCIe 接近占满后，预填几乎没有余量，要与第 7.4 节的准入一起设计。
- **前置测量**：在 E1-R005 中记录两路解码每层的「搬运 / 计算」时间线，估计实际可重叠的比例和气泡大小，再决定是否立项。

## 9. 负结果与方法论教训

### 9.1 hybrid（当前 CPU 执行器）

**实测**〔E1-R002，工件判 rejected，轮次库误写为 planned，待修〕：

- 解码 4.84 / 4.86 / 4.86 / 4.75 tok/s；offload 为 36.61 / 38.15 tok/s；下降 87%。
- 每 token 206 ms，offload 为 26.2 ms，每层多约 3.75 ms。
- CPU 分支确实生效：每层每步 CPU 算 2.43 个专家，经 PCIe 搬 0.62 个；失误率从 21.93% 升到 30.47%，因为 CPU 算过的专家不进 GPU 缓存。

**机理**：

- 每层交给 CPU 的字节只有约 2.43 × 2.77 = 6.7 MB，多出的 3.75 ms 折合等效带宽约 1.8 GB/s。机理假设（待服务时间分解验证）：耗时由固定延迟主导，而不是带宽。这个低等效带宽本身不能唯一识别原因。
- 读码看到的固定开销：执行器每个任务有 2 次自旋屏障（`cpu_moe_ext.cpp:1568-1580、1850、1860`），另有条件变量唤醒、D2H/H2D 握手。
- 执行器把 23 个线程绑在 0..22 号核，而 0、2 号核被一个常驻的 ollama `llama-server` 占用（约 119% CPU）。
- 自旋屏障只要等到一个被抢占的线程，就要等一个调度时间片（毫秒级），这与每层 3.75 ms 同一量级。**这是推断，不是证明。**

**能否定的范围**：只能否定「当前执行器加当前绑核方式」，不能否定 hybrid 在本机可行。

**复测 E1-R002b 的设计**：

- 变体 A：避开 0、2 号核。
- 变体 B：只用 node1 的物理核。
- 增设变体 C：专家池 `--membind` 到 node1，前提是 node1 容量放得下专家池加 PLE，约 111 GiB。理由是交错放置时约一半专家要跨 UPI 读；这是假设，要靠对照验证。

**定位**：E1-R002b 是受控诊断支线，不进入核心验收；w4a8 不是冻结的数值路径。

**判定**：不能用单独测得的 CPU 带宽当充分门。要测三样东西：

- CPU 与 PCIe **同时运行**时两路各自的完成率。
- 每层的服务时间分解：CPU 计算、交接、屏障。
- 两路端到端的解码速度。

18 GB/s 只是串行模型给出的参考量级。之后先用服务时间分解和绑核对照定位问题，再决定要不要改执行器。

**推算为什么偏差 87%**：推算用的交接开销来自一次很可能没走 CPU 分支的旧测试（没有带宽档时退回固定搬运上限）。计划文档中所有 hybrid 推算行作废。

### 9.3 方法论教训

- **判卷器漂移**：同一批 60 题的响应，9/30 判 88.33%，10/03 判 78.33%，生成逐字一致〔E0-R000〕。质量门必须固定判卷器版本。
- **输出层一致性门在长上下文上不可用**：见第 6.8 节。
- **回放顺序**：`replay --rounds "11,10,…"` 不会倒序执行，「冷进程首趟」被同进程前几轮预热了。改用倒序轨迹文件后才拿到真冷参照。
- **只看两轮就下结论**：v4 一度依据第 0 轮和第 11 轮写下「#577 无收益」，补齐 12 轮合计后结论反转。之后规定：先看整趟汇总，再下结论。
- **测错树**：曾有一批误从 #578 分支起服务。之后起服务前必须断言 `freetoken.__file__`。
- **自由文本进论文**：轮次库的自由文本字段曾把错误结论（「64K 属架构限制」）带进论文。论文只引用数值和判定。
- **单点开关对照与冷热状态混杂**：batch16 每格只有 1 个读数，没有区分「提示首次出现」与「重复命中」。
- **撤回也要按配对设计读**：19:22 的撤回只比较了「开」臂内部的冷与热，再用 5 次中位数比较两臂；中位数由热样本决定，掩盖了冷格差值。正确的读法是四格配对，冷、热分开报告（第 6.4 节）。
- **结论行的标签要与比较对象一致**：batch19 结尾把「B 对 B2」的结果写成了「恢复与重算一致」（第 6.8 节）。
- **容差不能来自被检验的路径**：用恢复路径自己的实测偏差标定容差，检验必然通过（第 3.5 节）。
- **工装缺陷三连**：新属性在热路径上被无条件读取，没有开关保护（`PrefillManager.layer_major`、`d3_extra_anchor_ids` 等）。导致 `tests/scheduler` 中 2 例 abort_inflight 测试失败。

## 10. 多卡：每卡驻留分析与协议（不含性能）

### 10.1 为什么先算显存账

如果 TP4 下每张卡几乎能驻留全部专家，卸载区间就基本消失，多卡部分的研究问题也随之改变。

### 10.2 估算（按检查点文件头，未经分配器核实）

**口径**：

- 每卡可用约 20.3 GiB（空闲 23.11 GiB × `--memory-ratio 0.88`）。
- KV 按实测分配反推，每 token 约 25.4 KB。TP4 时 2 个 KV 头要复制给两张卡。
- 区间两端分别对应「视觉加载、超连接整份复制」和「视觉不加载、超连接也切分」。

| 配置 | 1 路 48K | 2 路 64K | 8 路 32K |
|---|---|---|---|
| 单卡 | 12–14% | 9–11% | 4–6% |
| TP2 | 41–46% | 38–43% | 33–38% |
| TP4 | 97–100% | 91–100% | 81–92% |

校验：同一口径在单卡上算出 12%，实测 3149 个槽，即 12.8%。

### 10.3 含义

- **TP4 在容量上有望驻留 81–100% 的专家**。但覆盖率不等于收益：覆盖 95% 的专家，不意味着未命中流量只剩 5%，访问偏斜、保留策略和请求状态都会改变两者的关系。G0 容量核算之后，还要记录实际缺失字节、通信量和图与临时峰值。在这些测出来之前，「峰值 8 路每路 > 30 只有 TP4 有希望」只是候选判断。
- P2P、NCCL 的传输路径和 PCIe/NUMA 方向，要在将来的目标节点上实测确认。
- 「主存卸载多卡协同」的研究问题只存在于三种情形：
  - 2×TP2：每组仍有一半以上专家要卸载。
  - TP4 在高状态压力下。
  - 4 个单卡实例共享主存带宽：四卡同时整池预填约需 97 GB/s 主存读，本机交错 STREAM 只有 46.6 GB/s。
- **工程约束**：
  - `qwen4_exp` 只支持 TP=1。
  - `o_proj`、`out_proj` 现为复制，需要行并行加 all-reduce。
  - 超连接、PLE、QSA indexer 的分片还没有设计。
  - 离线专家库没有 TP 逻辑。
  - 4090 不支持 P2P，NCCL 经主存中转，与专家搬运争同一条 PCIe 和同一份主存带宽。
- 估计工作量 15–30 人日。

### 10.4 门与协议

- **G0**：按实际加载路径逐卡核算权重分片、复制项、KV、GDN 状态、CUDA Graph、工作区和安全余量。
  - TP4 常态驻留 ≥ 95% 时，多卡部分改为研究「TP4 消除卸载后的剩余瓶颈」，或集中在 2×TP2 和高状态压力区间。
  - 明显更低时，按总纲推进。
- **TP 数值门**：
  1. TP-n 同配置两次运行逐位一致（必须通过）。
  2. 相对单卡，首个分歧位置上前两名 token 的 logit 差低于阈值；阈值用单卡自身「批形状不同」造成的分歧来标定。
  3. 60 题质量差距在噪声范围内。
  - 第 2、3 项一起判定。
  - 这是**将来的候选验收标准**，第一阶段不采纳。top-2 logit 差很小并不排除其他数值错误，60 题也不是完整的质量边界。采纳前要单独评审。
- **顺序**：先实现并测量调优后的普通 TP2，再对照新策略，随后扩展 TP4。普通 TP 已能满足业务时，直接承认其效果。

## 12. 局限与效度威胁

1. **埋点开**：第 1 代数字都开着 D0。「约贵 7%」是跨代比较得到的（E1-R000 的 vs_epoch0），没有同一棵树上开关埋点的对照。生产口径数字待测。
2. **样本量**：首 token 每条件 2 次，只够支持大效应，例如两档首 token（2 倍）、4.24 倍内核提速。「两轮取慢」是保守的工程验收口径，不是 P95；ABAB 四次也不自动足够。小效应要按实测波动决定重复次数，并给出区间。
3. **拟合**：冷预填模型的非 MoE 项自由度为 0（第 4.2 节）。解码模型的系数来自第 0 代，$t_{req}$ 尚未分解。所以串行模型给出的「每路 21–23」只是条件预测。
4. **路由假设**：$f(n)$、$R_B$ 假设路由独立且均匀，偏差范围见第 6.7 节；多会话上界假设 $m$ 不随会话数变化。
5. **字节计量**：$L^\*$ 和 83 tok/s 用的是固定的每 token 未命中字节，不同负载和策略下要按实测 H2D 字节重算（第 4.4 节）。
6. **跨进程不确定性**：同配置回放的正文不一致尚未定位（第 3.5、6.8 节）。
7. **轨迹**：只有两条 Agent 轨迹，来自同一个生成工装。
8. **冷热状态混杂**：两倍量级的差异同样会被「首次出现 / 已命中」状态混杂；「两轮取慢」不构成因果证据。因果判断以配对的四格设计为准，冷格每格样本仍然很少（各 1 个，三组复现）。
9. **单机**：结论限于本机拓扑（PCIe 4.0、双路无 AMX）。原文在 PCIe 5.0 上每遍约 1.2 s，是本机的约 1/2.3。同样的分析在那里给出：$L^\*$ 不变（若失误率相同），遍时缩短。

## 13. 结论

在主存卸载 MoE 上，预填的成本单位是「专家池被搬了几遍」，而不是 token 数。这一点 FreeToken 原文已经观察到。本文把它推到 Agent 服务的后果上：

- 在当前整层加载路径、短后缀、传输主导的条件下，重算 token 数不足以解释首 token；实现地板是一遍（约 2.7 s）。
- 开启锚点检查点时，含未缓存锚点的首次请求多付约一遍，已命中的重复请求不付（三组冷配对，热格为 0）。这一遍是否来自 D3 切段，要由 E1-R008 闭合。
- #577 的存储与搬运逐位正确，但恢复后续算与整段重算不逐位相等，而整段重算的跨进程基线为 0。它是否可接受，要用独立标定的容差和 logits 检查判定。
- 多会话时，预填遍和解码未命中共用一份 PCIe 时间预算。在当前每 token 未命中字节下，一遍约等于 233 个解码 token，链路给出的解码总量条件上界约 83 tok/s。这个上界不足以单独判定两路每路 30 tok/s 不可达。

因此：

- 遍数和 PCIe 时间预算是值得检验的调度成本单位，候选机制包括每轮一遍、突发合批、遍内插解码、错相位重叠解码。它们是否优于调优后的强基线，要在不同内容多会话、有限资源的条件下实测，并且要连同控制开销一起比较。
- 本文不把上游内核提速、修复我们自己的回退、或多卡估算算作已完成的新调度贡献。

第一阶段手稿作为测量与建模报告成立，机制验证还在进行中。优先闭合四件事：E1-R008、E1-R005 加 E1-R007、跨进程不确定性的定位，以及同树 D0 开关对照加留出点。
