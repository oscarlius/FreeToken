## 自检行为

G3 先以默认环境启动动态 loopback 端口服务，再以 `FT_DEV_ROUTE_TRACE` 和 `FT_DEV_PAUSE_ENDPOINT` 启动第二个动态端口服务。两臂调用相同的候选 `cold_eq.py` 冷请求（同一 cold id、32052、128），比较全文 UTF-8 字节；没有使用 8095。

`cold_eq.py` 本身没有 URL 参数，启动器只在进程内预载 sealed `probe_ft_cold32k.py`，将其 URL 注入为该动态端口后执行原 `cold_eq.py`；请求构造与流读取仍由原客户端负责。CPU 测试证明 raw cold 脚本后续插入 live scripts path 时仍解析到预载的 sealed module，因而不会默默回连 8095。

G4 对 trace 臂运行 `agent_trace.py --route-evidence generate --rounds 2 --max-tokens 128`，再运行：

```bash
scripts/route_analyze.py ROUTES --traces trace.json --serve-log serve.log --out summary.json
```

分析器会拒绝没有 `#route-reqs: UID:n` 的 `#new-token` 记录、行内总数不符、所有 UID 汇总不符、未路由的业务 UID、ACK UID 变化、非连续 ACK、实际 completion 与 ACK/预算不符。因此 G4 不是仅比较总 token 数，而是将 route 的逐 UID suffix、服务日志逐 UID `#new-token` 与真实响应 ACK/UID 绑定在同一结果中。

trace 模式必须在 `g3_on/serve.log` 出现 `CUDA graph disabled for development route trace`；没有该标记即失败。由于它关闭 CUDA graph，所有时间字段都被明确排除，不能作性能数据。

每 token 每 MoE 层原始轨迹为 20 B；48 层约 960 B/token，启用前须预留相应磁盘空间。
