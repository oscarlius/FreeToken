用户批准：2 个服务，串行并发 1，约 30 分钟。GPU 顺序严格为 T16 batch163 kept → T17 终态 → R067e 最后一次重试终态 → 本轮 → 恢复 481 98K 与 SDK 冒烟 → 一次生产冷 32K。推送未批准，ollama 保持停止。

候选 481d3a7074818b0b41f27d90a5cb0de6c6f2cfb9，生产配方，D0 关闭。W98K 为 98,304 token / 2,700 槽；W128K 为 131,072 token，槽数取唯一 --moe-cache-auto resolved 日志，预期 2,401，不用预期值代替实测。

A 两臂均重放 E2-R046g 的 seed_real 原 8 轮，逐文件 SHA 绑定，温度和 max_tokens 不变。第一处原生输出 token ID 不一致立即 not_met，停止 B 与冷请求。B 仅在 W128K：冻结的第 9 轮，实际 frontend 100,223 token；沿原生产者工具和 FOLLOW_UPS 规则继续，最多共 4 轮（9–12）。后续达到 128K 容量边界则记录边界，不发出越界请求。独立冷请求约 126 Ki token，max_tokens=256，frontend / Worker / API 三方输入绑定，cached_tokens=0，记录 TTFT 与 1Hz 采样的最低空闲显存；OOM 判缺陷并停止。

每轮记录网络 monotonic 派发到终态时间、首非空输出到终态解码区间、(输出 token 数−1)/解码区间、解码占整轮比例。预填另记录异步 CUDA event 的 Engine.forward_batch 流区间，包含该调用中的采样/拷贝入队及 CPU 等待，不能称纯内核计算时间。两个窗口使用相同观测。跨环境变化的历史比较统一标注“环境不同”。每次测量记录 uptime 与 R 态线程数；本轮同批 A/B 环境相同。

主要速度比较按 8 轮合并：(总输出 token 数−8)/(总解码区间)，降幅=1−W128K/W98K。预期降幅约 4.0%。≤6%：模型斜率成立、128K 发布配置候选；>6%且≤12%：斜率更陡、需替换策略并提出论文 §4.7 修正；>12%或 B/冷请求 OOM：128K 暂不可行。与逐轮结果一起报告，不以 TTFT 代替解码速度。

失误率仅引用 CPU review_r4：2700 槽 38.59%，2401 槽 41.38%；固定 LRFU H=384 在 2401 槽为 39.708889%（214428/540000），降低 1.673148 个百分点。没有授权任何 D15 策略 GPU 测量。
