# E2-R057 OOM diagnostic preparation

R057 is a diagnostic-only four-arm experiment on `effb9969706922ddad9e59b96377e46469ebe97f`: 98,304 window, 0.88 memory ratio, and one 32,064-token cold request per independent service. It never decides `kept`.

`r057_oom_diagnostic_prepare.py --run` is the owned controller. It reserves an owned child, verifies one Linux FILEDRY receipt plus the R sign-off, checks only the read-only E2-R056 round/manifest/D04-history metadata, then takes its own lock and runs the four independent arms. It freezes its three runtime sources and writes a manifest. A diagnostic OOM is retained with its snapshot directory and the controller continues to later arms; any other service or harness error preserves its raw files and stops.

Arm A enables trace only; B enables pause only; C enables both; D enables neither and sets the verified ServerArgs flag `--cuda-graph-max-bs 0`. The static `serve_args_diff.json` is written for every arm and the launch controller must compare actual parsed ServerArgs against it after startup. Only A/C (pause) and B/C (trace) are controlled one-variable contrasts. D is a graph-off mechanism reference; it is not a controlled comparison with R056.

`r057_memory_history_startup.py` uses the FreeToken `__mp_main__` spawn entry. That entry only installs hooks: tokenizer children do not import torch, create snapshot directories, or enable CUDA history. The actual `Engine.__init__` model worker creates the directory and enables `torch.cuda.memory._record_memory_history(enabled="all", context="all", stacks="all", max_entries=200000)` before constructing the engine, then registers exit handling. It records UserMsg request-start markers and pre/post `mem_get_info`; forward errors first record failure samples with the batch request UIDs, then snapshot and re-raise. The bounded history may roll over; this is recorded and must never be presented as an unlimited trace. The controller saves the exact urllib request bytes and SHA before `urlopen`, so an OOM preserves the cold input, and requires an event-bound real snapshot pickle for every completed/OOM arm. It cleans only the exact owned PID/birth/process group.

CPU evidence and the Linux FILEDRY receipt are preparation evidence only. No GPU result, OOM conclusion, or queue movement has been produced by this package.

The CPU command is `python development/r057_oom_diagnostic_prepare.py --self-test`, followed by `python -m pytest -q development/tests/test_r057_prepare.py`. For the root-owned Linux stage, set `R057_D07_SOURCE` and `R057_FILE_PREP_SOURCE` to the existing read-only R056/D07 sources, stage the two R057 sources plus test, and invoke `--file-dry-run` under `/data2/FreeToken/venv/bin/python` from `/data2/FreeToken`. The FILEDRY archives its exact four-source map (entry, wrapper, D07 and file prep) and probes all formal arm paths using the same file-preparation code. The sole accepted review path is `/data2/FreeToken/runs/dev_R057/reviews/E2-R057_startup_review_v1.json` with schema `ft_r057_startup_review/v1`, `approved=true`, `verdict=PASS`, the exact source map, FILEDRY path and SHA. Only then may root use `--run`; FILEDRY itself must not add `--run`, create a RID, or start a service.
