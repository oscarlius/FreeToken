## 二、时间花在哪里（511 步遥测）

1. **步长与搬运量无关。** 第 1–4 步每步 407 次失误，耗时 172 ms；第 100–200 步每步 254 次失误，耗时 182 ms。失误少了 38%，步长反而略长。
2. **CPU 是关键路径。** 每步 CPU 派发 180.8 ms（p50），GPU 在派发结束后 2.1 ms 就完成。GPU 一直在等 CPU 下发工作。
3. **链路利用率只有 16%。** 每步搬运 761 MB，按 B_P=24.3 GB/s 只需 31.3 ms，而步长是 190.8 ms；实际平均 H2D 为 3.99 GB/s。
4. **代码层面的原因：D10 走 eager 路径。** `engine.py:1059` 为 `use_graph = ... and not use_d10`；`layers/moe.py` 的 decode_prepare 注明 "not graph-capturable … eager D10 path"。发布路径是"整步一张图"，D10 是 2 路 × 48 层、由 Python 逐个闭包派发的 kernel。搬运本身用设备端索引拷贝（`fast_index_copy_multi_jit`），没有主机同步，所以瓶颈在派发开销，不在同步等待。
5. **D10 首步耗时 44.3 s**（Triton JIT 及首次全失误加载）。旧轮次输出只有 46/58 token，这一步就占了大部分时间：batch155 的 0.87/6.97 和 v10 的 5.86/1.06 tok/s 都主要被它拖低，与机制无关。
6. **环境混杂。** batch162 在 13:06–13:13 运行，ollama 当时有 24 个线程处于 R 态（20:35 已停）。CPU 受限的 eager 路径对这种争用敏感，影响多大目前无法量化。

## 三、设计层面：每路只有一半缓存，理想上限也低于串行

- `offload_cache.py:make_d10_lane_caches` 把 2700 槽切成两路各 1350 槽的私有分区，两路之间不共享。
- 每路失误率因此大约翻倍。实测 lane1 为 52.2%，发布路径单路 2K 为 26.7%。模拟器 seed_real 的 LRU 在 1350 槽为 54.5%，2700 槽为 38.6%。
- 论文的重叠上界受链路限制：R = 1000 / (Σ m_i × 54.77)。按 m≈0.52 计算，每路约 17.5 tok/s，低于串行的 21.5。
- 预注册的预测 33.1–40.0 是按共享缓存的 m≈24% 推出的，实现改变了这个前提，预测因此失效。主会话和 Codex 的审查都没有发现这一点。

## 四、负载不具代表性

## 八、主会话自我更正（真实写入 2026-10-10T22:36:39+08:00）：第三节和第七节的诊断设计作废

用户追问"为什么要到 09:00""这份指令有没有认真分析过"。复核后发现，原诊断设计有五个问题：

1. **重犯了前提错误。** "共享缓存理想上界 35.6–37.8"沿用了单路的 m≈24%。两路内容不同时，两者共用 2700 槽，每路分到的有效容量接近一半。
   - 实测：G_two 是发布路径上两路的真实 D0 遥测，失误率 42.6%（去重口径）。
   - 模拟（`development/d10_reanalysis_20261010/two_lane_share_sim.py`），每路等效 m 与链路上界：

     | 方式 | m | 上界（tok/s/路） |
     |---|---:|---:|
     | 串行批处理 | 40.5–43.0% | 21.3–22.5 |
     | 错相位共享缓存 | 40.4–42.9% | 21.3–22.6 |
     | 分区缓存 | 54.5–55.0% | 16.6–16.7 |

   - 结论：即使完美实现，错相位重叠每路也只有约 22，达不到 30（需要 m ≤ 30.4%）。G_two 在 3600 槽时去重口径 m 为 32.65%，仍然达不到。
2. **GPU 三臂对决策没有价值。** b162 已经证明瓶颈在 CPU 派发；被测的是一个要废弃的原型，开发方案本来就要去掉 eager。A 臂又和窗口 A/B 的 W98K 臂重复。
3. **该自己算的被外包了。** CPU 模拟主会话 2 分钟就能算完，却安排给 Codex 在测试服务器上跑，还可能和 GPU 测速同时进行，等于重新引入 CPU 争用这个混杂因素。
4. **09:00 是套用旧模板的截止时间**，不是从工作量推出来的。
5. **理想重叠模型漏了两点：** 错相位失去了批处理（两次 bs=1 计算约 26.2 ms，批处理是 18.4 ms）；搬运用的是占 SM 的 UVA 拷贝核函数，不是 DMA 引擎。这两点都会让上界更难达到。

**论文层面的影响（待闭环后修订）：** v5.3 中两路的理论值都是用单路 m 算的（串行 21.5/21.8，重叠 37.8，"m≤30.4% 已满足"）。按两路 m≈40–43% 重算，串行约 15.9–16.4，重叠上界约 21–23。R045 的 103–105% 很可能是因为两条提示几乎一样（同一模板，b162 前 7 步两路输出完全相同），两路共享的专家多，m 偏低。这个解释还需要实测确认。
