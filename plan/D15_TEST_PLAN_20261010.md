# 卡D15 自适应专家缓存：提升空间测量方案（2026-10-10 17:30，主会话）

用户要求："制定 D15 自适应专家缓存测试方案，看看我们可以提升多少。"

## 一、出发点（已核实）

- **发布配置下 Agent 负载的解码失误率远高于单次 32K。** R046g 录制路由轨迹时就是发布配置：2,700 个专家槽、1,536 页。各组 D0 实测解码失误率：

  | 轨迹组 | 解码步数 | 失误率 |
  |---|---|---|
  | seed12k | 3,219 | 37.53% |
  | seed_45k | 3,929 | 35.54% |
  | seed_real | 1,125 | 38.59% |
  | G_two（其中 70 步为 bs=2） | 85 | 42.62% |

  单次 32K 冷请求的稳态失误率只有约 24%（b163）。差别在于：Agent 每轮都要预填，预填会占用并清零 [0, 2E) 共 1,024 个槽，约占缓存的 38%；随后的解码只有两三百个 token，缓存来不及热起来。
  > **20:20 更正（主会话）**：上面"差别在于预填清空"的推断已被阶段 0 的 NOINV 结果否定。预填不清空时失误率只降 0.06–0.13 个百分点。缓存每 5–6 步就全部周转一遍，预填清空只影响每轮开头几步。Agent 负载失误率高，原因在路由内容本身，见第四节。
- **按论文 §4.7 公式推算（主会话推算，不是实测速度）**，每 token 每单位失误率对应 54.77 ms 的搬运时间。在 16K 上下文下，失误率与速度的关系如下：

  | 失误率 | 单路（tok/s） | 两路每路（tok/s） |
  |---|---|---|
  | 37% | 29.3 | 16.7 |
  | 30% | 33.3 | 19.3 |
  | 25% | 36.6 | 21.6 |
  | 20% | 40.7 | 24.5 |
  | 15% | 45.8 | 28.3 |
  | 10% | 52.4 | 33.5 |

- **D15 现有实现。** 候选 8256553（含 R049c 之后修复的 481aa4d），默认关闭门 R050a kept，但没跑过 T21。三种策略：
  - `lru`：现状。
  - `profile`：开局时把画像预置进 [2E, cache_size)，之后仍按全局 LRU 淘汰，预置的专家也会被挤掉。
  - `profile+adapt`：在线置换，参数为 every 和 swaps。
- **D15 能把失误率降多少，至今没有测过。** T21 的 4 轮里 3 轮工装失败，R049c 判不达标，原因是第一个负载上开在线置换的臂输出不一致。

## 二、方案

### 阶段 0（CPU，不占 GPU，今晚开始，与 GPU 队列并行）

**A. 缓存回放模拟器**

- 定位：自研薄适配，约 200 行以内。理由：专家缓存的替换行为在引擎内部，没有开源工具能覆盖。
- 输入：E2-R046g 四组的 route/*.npz，按 seq 顺序读取，包含预填和解码事件。只读，不复制，不改原件。
- 语义：逐行对齐 8256553 的 `offload_cache.py` 和 `offload_kernels.py`，包括：
  - 容量 2,700 槽、E = 512、48 层；
  - 全局 LRU 选淘汰对象（按 usage、slot 取最小）；
  - 预填占用 [0, 2E) 并清零 usage；
  - 画像预置到稳定区；
  - 在线置换的计划与发布规则。
- 校准门：用 LRU 模拟每组的解码失误率，与该组 `d0_decode.json` 的精确值比较，每组偏差都不超过 1.0 个百分点才可使用。不满足就先报差异原因，不出策略结论。

**B. 策略与容量扫描**

除第 8 项外，容量都取 2,700 槽。

1. L：LRU（现状）。
2. P：画像预置（`seed12k_only.strp`）。
3. PA：画像 + 在线置换。参数网格为 every ∈ {1, 4, 16, 64} × swaps ∈ {1, 4, 16}，只在 seed12k 上选参数。
4. PA-lag1：在 PA 基础上，置换延迟一步生效（Strata `ADAPT_LAG` 的做法）。
5. 按层固定分配：按画像把稳定区分给各层并钉住，不参与 LRU 淘汰，只在 [0, 2E) 内做 LRU（Strata `expert_cache.cpp` 的做法）。
6. 不清空假设：预填不占用解码槽。只作上限参考，不是可以直接实现的方案。
7. Belady 最优替换：离线知道未来，是任何淘汰策略的上限。仍保留预填清空 [0, 2E) 这一约束。
8. 容量敏感性：L 和最好的可实现策略，分别在 2,700、3,149、3,600 槽下测。

训练与验证的划分：画像和参数只用 seed12k。seed_45k、seed_real、G_two 作为留出集；seed12k 的结果单列，标为样本内。在线置换产生的搬运字节计入成本。

**C. 产物**

- 每个策略 × 每组轨迹，给出：解码失误率、相对 LRU 的变化、置换字节数。
- 按 §4.7 公式换算单路和两路每路的速度：R = 1000 / (t0 + kL + t_req(B−1) + B·(m·54.77 + 每步置换搬运时间))，L 取各组实际上下文的中位数。
- 一页结论：可实现的策略最多能把失误率降多少，离 Belady 上限还有多远。
- 产物放在 `development/d15_sim_20261010/`，由非作者独审。

**阶段 0b（CPU，与阶段 0 并行；在 8256553 之上新开分支，默认关闭）**

1. 实现"置换延迟一步生效"：拷贝在辅助流上推进，下一步才发布新映射。
2. 审查在线置换的发布顺序：
   - 拷贝流事件完成前，不得发布新映射；
   - 不得替换本步 top-k 正在使用的槽；
   - 补上相应的 CPU 回归测试。
3. D0 开启时，逐步记录置换回执：步号、层、专家、槽号、拷贝开始与完成时间、发布时刻、字节数。
4. 跑 D15 的 CPU 全套测试加新测试，过独审。不上 GPU。

## 四、阶段 0 / 0b 结果复核（2026-10-10 20:20，主会话）

证据：`development/d15_sim_20261010/review_r4/`（corrected_results_r4.json，SHA-256 9d7e7482…）、`phase0b_7eba574/`，以及主会话快速核查 `main_session_check_20261010_2018/`（未独审，只用来定方向）。

1. **Codex 的执行合格。** 四组 LRU 校准偏差均为 0.000 pp，主会话独立复现也一致；阶段 0 和 0b 都通过了非作者独审。适配器超出 200 行预算（239 + 455 行），已登记。
2. **D15 现有机制没有可用的收益。** 留出集上，P 最多降 0.239 pp，PA e64/s1 与 P 同量级，折合速度约 +0.1 tok/s。画像钉死和均分层配额反而让失误率升高 11.5–16.0 pp，说明专家热度随会话变化，静态画像不适用。
   - 决定：P、PA、PA-lag 不进阶段 1 GPU。
   - 7eba574 冻结，不合入；它在开启时会退回 eager 执行，本身也有性能风险。
3. **预填清空不是主因。** NOINV 只降 0.06–0.13 pp，17:30 的推断作废（第一节已标更正）。
4. **替换策略：理论空间大，可实现部分小。**
   - Belady 上界比 LRU 低 17–22 pp。
   - 主会话核查的两种可实现策略：
     - 层循环感知平局规则：降 0.74–0.78 pp，two 组降 2.38 pp；
     - 衰减频率 LRFU（半衰期 8 步，只在 seed12k 上选参）：留出集降 1.55–1.86 pp，约 +0.7–0.8 tok/s 单路，约 +3%。
   - 两种都只拿到 Belady 空间的一成左右。剩下的九成需要预知下一步路由，属于预测类研究，暂不立项。
5. **容量才是大杠杆，但不能靠缩窗口白拿。**
   - 49,152 / 73,792 / 98,304 窗口分别对应 3,149 / 2,924 / 2,700 槽（T12）。
   - Codex 表里的 3,600 槽在单卡上做不到：48K 窗口的全部 KV 只折合约 450 槽。
   - seed_real 的上下文中位数为 91K，48K 窗口装不下。
   - 可行的方向是**弹性专家槽**：把闲置 KV 页借给专家缓存。22K 会话在 98K 窗口下约可借 690 槽，即 3,390 槽：
     - 模拟失误率：LRU 31.3% / 29.7%，再加 LRFU 为 30.1% / 28.5%（seed12k / 45k）；
     - 推算单路速度：32.3–34.1 tok/s，比现状高 11–13%；
     - 长上下文（91K）几乎借不到。
6. **下一步只做 CPU**（见当日回复中的指令）：
   - LRFU 类策略的正式扫描，加 kernel 改动设计；
   - 弹性专家槽可行性：预算算法、冲突点、用逐轮上下文计算可借槽数后模拟。
   - 阶段 1 GPU 暂不申请。

## 五、20:20 指令的自我复核（2026-10-10 20:30，主会话；用户要求"认真反思"）

结论：20:20 的指令解决不了问题，已作废，由当日 20:30 回复中的修订版取代。原因如下。

1. **代理指标与速度之间的关系没有闭合。**
   - §4.7 只在单次 32K、m≈24% 的工况下校准过；Agent 负载（m≈37%）下的速度从来没有实测。
   - 唯一的自然实验是 R040（2,924 槽，38.3 tok/s）对比 R056（2,700 槽，34.33 tok/s）：少了 224 个槽，慢了 10.4%。按模型反推，这相当于失误率降了约 5 pp。而在 Agent 模拟中，多出 449 个槽也只降 4.2 pp。两个提交不同，存在混杂，原因不明。
   - 模拟器与 D0 精确一致，所以失误率已经不需要 GPU 去测。GPU 只需测"失误率 → 速度"这一段，而且这一段应该排在任何工程开发之前。
2. **留出集不独立。**
   - seed_45k 实际提示约 1.2 万 token（R046g 结果卡），和 seed12k 是同一来源。
   - G_two 卡上已注明"不充当 32K 并发或性能证据"：输入 659/613 token，只有 85 步。
   - 真正独立的只有 seed_real，一个会话、8 轮。两路的结论没有证据支撑。
3. **弹性槽的收益落在短会话上。**
   - 真实会话 seed_real 的上下文是 87K→95K，可借的 KV 页约为 0。
   - 如果目标负载是短会话，按负载选窗口档（48K = 3,149 槽）不需要改代码。直接设计动态显存池违反 KISS。
4. **LRFU 不够稳健**（逐轮核查，见 main_session_check_20261010_2018/per_turn_outputs.txt）：
   - 32 轮中有 24 轮改善，平均降 1.1–1.65 pp，最差的一轮升 1.37 pp；短轮次常常变差。
   - seed_real 上半衰期翻倍（768）后为 38.68%，比 LRU 还差。固定半衰期存在悬崖，需要 ARC 一类的自适应策略。
5. **方向排序可能反了。**
   - Belady 有 17–22 pp 的空间，九成需要预知下一步路由，而这同时也是 M4 重叠的前提。可以先用现有轨迹在 CPU 上量化可预测性。
   - 串行结构下，即使达到 Belady（m≈20%），两路每路也只有约 24.5 tok/s（推算）。缓存方向本身达不到两路目标。
6. **没有预先登记判据。** 20:20 的指令要的是"出一页结论"，没有给停止条件，容易再次堆砌证据链。
7. **终点指标选错了。** 用户感受到的是每轮 Agent 响应时间（预填加解码）。真实会话每轮只解码 87–325 步，解码在每轮时间里占多少还没量过。
