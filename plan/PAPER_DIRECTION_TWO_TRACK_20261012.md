# 论文方向：两条线并行，代码按门槛放行（2026-10-12 00:10，op 会话，用户同意）

## 1. 为什么转向

**初衷。** 公司买不起 H100，几张 4090 要给全公司用。用户对比过 vLLM、SGLang、KT、llama.cpp、Strata、EXL3，认为"多用户 + 多卡 + 模型大于显存"三者交集上没有能用的开源框架，所以才做 FreeToken。

**v5.8 的问题。** 论文偏离了这个初衷，转而在单卡上做细节机制，比较对象也是 FreeToken 的上一版。结果 M1–M6、G1–G5 没有一项测出收益（§11）。正文也没有把 vLLM、SGLang、llama.cpp、EXL3 当作对照来测。

**10-11 晚查证：** "没有框架能做到"不能写进论文。

- **KTransformers（SGLang-KT）**
  - 服务器上已安装 kt-kernel 0.7.0.post4。
  - 官方 GLM-5.3-Flash 教程写明：支持 RTX 40、TP1/2/4/8、CPU 算专家、Layerwise Prefill、SGLang 批处理，并给出四卡启动命令。
  - **更正（10-12 凌晨，freetoken-06 核查，op 复核源码）：在本机配置上，两个目标模型 KT 都跑不了。**
    - GLM 的 KT 专家卸载只接受 `--kt-method FP8`（server_args.py 约 1619 行，否则直接报错）。FP8 权重约 306 GiB，需要 ≥350 GB 内存；现机 251 GiB、新机 256 GB 都不够。本文初稿写的"新机只能走 INT4 GGUF"这条路，在当前 KT 代码里不存在。
    - KT 自带的 SGLang 没有 qwen4_exp 架构。09-29 的 KT"Qwen3.8"运行是把 config 改成 qwen3_next 后硬启动的，架构错误，FINAL_REPORT 里 KT 的 33.76 tok/s 作废。
    - 详见 `/data2/KTransformers/bench_20261012/KT_FEASIBILITY_20261012.md`（ff44a4210526…）。
- **ExLlamaV3（d3739fd）**
  - Qwen4Exp 和 GLM5Next 都支持 TP（native 后端，不需要 P2P），也支持批处理。
  - 开 TP 时禁止 CPU 专家，专家必须全部进显存。
  - Qwen 4.05bpw 推算放得下；GLM 要 ≤2.05bpw 才放得下。
- **vLLM（10-02 main）**
  - Qwen4Exp 的 PLE 表默认放主存。
  - TP4 每卡约 19–21 GiB，推算能起服务，但 KV 只剩约几万 token。

**检索结果。** 截至 10-12，没有找到"消费级多卡、多用户、几家框架公平对照"的公开测量。这是新方向的空白。

## 11. 用户决定（2026-10-12 15:1x，op 会话提出，用户选"按四步走"）：线 B 改为按类别比较、限时裁决

**起因。** 用户担心"最好的对手"名单没有边界：框架会不断更新、不断出现，比较做不完，开发迟迟不能开工，变成没完没了的自我证明。op 的判断：门槛本身没问题，问题出在名单没有边界。办法是加两条边界——按类别比，不按框架逐个比；到截止日期就停。

**决定（四步）：**

1. **纸面，本周约 2–3 天。**
   - 对手按机制分类：专家放在哪里（显存/主存）、在哪里算（GPU/CPU），预填和解码分阶段归类（例：llama.cpp 大批量预填时把专家搬到 GPU 上算，预填阶段归第三类）。三类为：全部放进显存；放在主存、CPU 算；放在主存、搬到 GPU 算。每类只测一个最强代表，作用是检验该类上限公式算得准不准，不是枚举。
   - 名单按截止日期冻结，写明版本 SHA；截止日之后出现的框架不进本文，写进"后续工作"。由主会话以门槛补充文件下发（门槛原文不改）。
   - 三类上限在两个模型上各算一遍（op 负责）。
2. **同时做一件不管门槛结果都要做的事：FreeToken 单卡把 GLM NVFP4 加载跑通、跑对。** 理由：GLM 的质量参照只有它能给；B 线要用；公司如需 GLM 也要用。属单卡代码，不违反"门槛通过前不写四卡代码"；用户已同意为此改代码。
3. **新机到货后 5 个工作日**：校准硬件参数 → 封存点预测 → 名单内各家实测。到期就停，不再加对手、不改判据。
4. **到货后第 7 天裁决**：过门槛就开始写四卡代码；不过就部署胜出的框架，论文按 A 线写。

**第 2 步的范围（op 只读核查，2026-10-12 15:1x）：**

- 根因 09-30 已定位（`_shared/runs/run_20260930_retest/report.md` §6）：GLM 前 3 层 dense MLP 以 ModelOpt NVFP4 存储（weight / weight_scale / weight_scale_2 / input_scale），`glm5_next/weight.py` 的 `_proj` 只处理 bf16 和块状 fp8，没有给出 `weight_scale` 等，所以 `Glm5NextGatedMLP` 加载时报 `KeyError 'model.layers.0.mlp.gate_proj.weight_scale'`。当时在副本上做过模块级修复验证（12/12 张量匹配，反量化与 CPU 参考最大差 0.000209），没有做整模型端到端。

## 12. 用户澄清目标与分步决定（2026-10-12 晚，op 会话；主会话已关闭）

**用户澄清（原话大意）**：基于伯克利已发布的论文做两件事——单卡调优、支持多卡，形成我们自己的论文。单卡已有速度突破；多卡目前代码不支持，需要开发。

**op 评估：方向成立，但有两处要改。**
1. **单卡不能当主角。** 相对上游，真正成立的单卡收益只有冷 32K 首 token 13.0 → 6.1–6.6 s。这项收益来自层优先（我们）与 #578（上游，未合并）叠加，两者单独都不提速；层优先已有前人工作（Layered Prefill）。任务 B 的 −47% 是相对我们自己的配置。所以单卡在新论文中定位为"标定 + 一项工程收益"。
2. **多卡的贡献不是"让它支持"。** 贡献是：在无卡间直连的消费级多卡机上，用成本模型事先选出主存卸载 MoE 的并行方式，按选定方式实现，再在同机同负载上与 llama.cpp、EXL3、vLLM 及上游单卡对照。三种做法：
   - 每卡独立引擎、共享主存专家池；
   - 按层切分；
   - 张量并行。

   它们的开发量和效果差别很大，单人冷 64K 首 token 只有张量并行能改善，GLM 在四卡上约 7–10 s，处在边缘（粗算，未封存）。

**用户决定（AskUserQuestion）："两者都要，分两步"。**
- **第一步**：多人同时用、能跑 GLM。由成本模型在"每卡独立引擎"与"按层切分"之间选一种。论文先发。
- **第二步**：张量并行，目标是单人冷 64K 首 token 进 10 s。按模型预测再决定做不做。

**与门槛的关系（不变）**：第一步的代码仍在到货后第 7 天裁决后开工；在此之前做纸面设计，包括并行方式的选择、接口、测试方案和预测。若用户要提前开工，属修改门槛，须用户明确决定。

**补充 2 的拟定口径（op 起草，用户无异议后封存，须在任何测量之前）：**
- 冷 64K 到达计入第 2 项，对所有系统测量并报告。它是第二步的目标，第一步不以它为放行依据。
- 首 token 的技术口径沿用主会话所定：从发出请求到第一个非空增量，取 L 内全部事件的最大值。
- 到达时刻表：冷到达固定间隔 60 s；另设"两人同时冷到达"作观察项，不作判据。
