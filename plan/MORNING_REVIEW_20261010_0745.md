## 二、主会话核查结论

### 1. R067d-retry1 是混杂的结果，不能说明 C3 被否定

- 热种子的 prefill 日志是 `#new-token 512` 加 `#new-token 7681` 两段；冷参照是 `#new-token 8193` 一段，schedule 中 donor 为 `[0,8193)`，按 layer-major `[4096,4096,1]` 计算。
- 状态转储比对：
  - 热路径 donate@8192 与热路径 resume 后的 dst 槽**逐位相同**，说明恢复本身是忠实的；
  - 热 donate@8192 与冷 donate@8192 在 **36 层上全部不同**：conv 最大绝对差 1.39（相对 4.6%），recurrent 最大绝对差 0.267（相对 1.1%）。PLE 槽相同。
- 分叉在尾段计算开始之前就已经存在，所以被测的短尾机制（恢复加 ≤64 尾段）实际上没有被检验到。
- 生产中，同一提示的冷请求同样会在锚点 512 处切分。D20 文档里 "same final request structure" 的冷参照漏掉了种子阶段的切分，这是参照设计的缺陷。
- 附带的产品层面观察：同一提示只因 prefill 切分几何不同，贪心解码的首 token 就从 `H` 变成了 `<|im_end|>`。这是 D19（批不变性）在真实对话输入上的直接表现，可以作为 D19 决策的证据。

### 2. D10 原型的 5.9/1.1 tok/s 是实现缺陷，不能作为 D10 机制的负证据

`wt/d10-staggered-v1/python/freetoken/engine/engine.py` 的 `_forward_d10_staggered_decode` 每一步都会：

- 对两个 lane 执行 `lane_cache.reset()`（注释写的是 "routed rows are repopulated from shared host banks"）；
- 在结尾执行 `self.moe_offload_cache.reset()`。

结果是每个 token 都从主机重新拉取全部激活专家，缓存命中率为 0。另外 `actual_can_use_d10_staggered=false` 是探针读错了属性（独审已经指出）。

论文 V7、README、CLAIM_EVIDENCE_MAP 把这组数写成了 "D10 observational negative"，**必须更正**：写明它来自"每步清空 lane 缓存的原型"，不代表错相位重叠这一机制本身。

### 3. R047 的根因是锚点快照被 64 页对齐拒绝

- 诊断计数器：`anchor_hit` 共 6 次（全部是 extra anchor，即 `</think>`/`<|im_end|>`），`anchor_set=3`，`cached_len_mismatch=60` 都发生在锚点之前，`unaligned=3`。
- 服务日志显示 hybrid 缓存的 `page_size=64`；`cache.py:snapshot_toolcall_anchor` 要求 `align_down(a, page_size) == a`。`</think>` 的位置是任意的，因此对齐的概率只有 1/64。
- 这就是第 2、3 轮只命中 64/192 token（提示长度为 211/318）的原因。

### 4. R044-retry2 本可以在 CPU 上拦下来

`--max-prefill-length` 在 ServerArgs 里的键名是 `max_extend_tokens`，R047 的 serve.log 里本来就有这一行。§11 要求"真实日志回放后才能准入 GPU"，这一条没有执行到位。
