# 补充交接：对外部审阅报告的核实结论（2026-10-04 夜）

> 起因：用户转来一份外部审阅报告，主要论点是「同一判卷器下质量从 78.33% 掉到 63.33%，是真实回归」，另有 D0 解码开销、编号体系、交付位置三点。以下逐条用服务器原始工件只读核实。本文件优先于 `CODEX_HANDOFF_20261004b.md` 第 2.4 条。

## 1. 质量「回归」不成立：78.33% 是另一个判卷器的重判分数

| 证据 | 结果 |
|---|---|
| 服务器 `/data2/_shared/evaluator.py` | sha256 `250e197f…`（9/30 12:02） |
| 本地 `_shared/evaluator.py` | sha256 `39f10fa8…`（9/30 13:01，较新），**与服务器不同**（`plan/README.md` 中的 Q6 早已登记） |
| 第 0 代原始判卷 `_e0/paper_headroom_20261003/quality60/` 与 `quality60_4096/` | **38/60**；中文抽取 14/15、结构化工具 15/15、代码自动测试 1/15、长多轮 8/15；`finish_reason` 中 stop 49、length 11 |
| E2-R004、E2-R009 的同名文件 | **38/60**，分类分数完全相同；按 `question_id` 逐题比对，60/60 题号一致，通过与否逐题相同，思考和正文 token 数最多相差 1 |
| `_shared/runs/run_paper_headroom_20261003_regrade.jsonl`（10-03 02:38） | 由 `regrade_paper_headroom.py` 用**本地** `evaluator.py` 对第 0 代原始回答重判得到，**47/60 = 78.33%**，这就是轮次库 E0-R000 `quality60.pass_rate=0.7833` 的来源 |

结论：

- 第 0 代与第 2 代的模型输出几乎相同。两个分数的差异完全来自判卷器版本（重判脚本 + 本地较新的 evaluator），不是模型或配置的回归。
- 外部报告核对了服务器判卷器的 sha，却没有发现 78.33% 是用另一个判卷器重判出来的。
- 「代码自动测试 1/15」在两代里相同。主因是输出上限导致截断：5 题在思考阶段就被截断，另有若干题 `length` 截断，属于测试配置问题，不是回归。

**Codex 执行：**

1. 选定**一个**规范判卷器（建议取较新的本地 `39f10fa8…`，先读 diff 确认它修的是判卷逻辑），同步到服务器，记入 `00_规则`。
2. 用规范判卷器重判 E0 原始回答、E2-R004、E2-R009，结果存为新的分析轮次（只读输入，不动原始工件）。
3. 轮次库 E0-R000 的 `quality60` 追加更正：注明 0.7833 来自用 `39f10fa8` 重判的结果，服务器判卷器下为 0.6333。只追加，不改写原值。
4. 今后每个质量轮次的 `round.json` 都记录 `evaluator_sha256`。分数只在同 sha 之间比较。
5. 代码题的截断问题，另开一张配置调研卡：在同一判卷器下比较 `max_tokens` 与思考预算，不进入当前主线。

## 2. D0 解码开销：存在两个不一致的测量，需要对账

- 外部报告说「T07 只量了 TTFT，没量解码」，**这一点不对**。T07（E2-R003）测了解码：在 8K–48K 四个长度上，D0 开启时解码少 1.27–1.39 tok/s，约 −3.5%。
- 但 `E2-R022-gate-D14/gate_batch50.json` 中，D0 臂为 32.41 / 32.35 tok/s，生产臂为 36.04 / 36.03 tok/s，约 **−10%**。两组数据不一致，需要对账。

**Codex 执行（不占新 GPU，先读工件）：**

- 比较 T07 与 R022 的 D0 臂环境变量，尤其是 D02 新增的 `FT_DEV_D0_TIMELINE_STEPS` 等、样本数和是否为首枪。给出差异来源。
- 在对账结论出来之前，**门轮次中带 D0 的解码数字一律不作性能数**（规则已有，重申）。论文 v4.1 中的「D0 开销」暂时只写 TTFT（+53–65 ms），解码开销写「−3.5% 至 −10%，待对账」。
