## 二、决定 1：hybrid 的定性

**事实。**
- offload 在热服务和全新服务上，单路、两路的输出都逐字相同。
- hybrid 与 offload 的输出在全文约 70% 处开始分叉：单路在第 872 个字符，两路在第 871 和 806 个字符。
- 作为对照，offload 自身从单路改为两路，在第 454 个字符就开始分叉，这是批效应，论文 §12 已经披露。
- 证据：`development/d08_hybrid_review_20261011/output_compare.py`。

**定性。** hybrid 属于**精确计算**，不丢弃也不近似任何专家，所以符合用户"先只走无损路线"的决定。它和 offload 的差别只在 CPU 与 GPU 的舍入方式不同，偏差量级小于论文已经接受的批效应。

**由此带来的验收变化。** hybrid 配置的正确性门槛，从"与 offload 逐位相等"改为下面三条：
1. **自身复现性。** 同一服务里重复请求、冷服务与热服务、两路重复运行，输出是否逐字相同。
2. **质量等价。** 用 quality60 标准评分器，hybrid 的得分不低于 offload 得分减 3 题。
3. **论文披露。** 写明"hybrid 与 offload 不逐位一致"。

如果第 1 条不成立，即 hybrid 的输出受缓存或时序状态影响，那么在 hybrid 下 T17 意义上的"续算逐位等价"不成立。届时 hybrid 只能作为可选的性能模式，是否进入发布路径交给用户裁定。

## 三、决定 2：测试拓扑与 WSL2 的角色

**依据。** 服务默认只监听 127.0.0.1，CORS 白名单是本机 Tauri 客户端（`tauri://localhost`、`localhost:1420`）。主要使用场景是同机访问，所以**性能以服务器本机测量为准**。

| 类别 | 测什么 | 在哪里跑 | 说明 |
|---|---|---|---|
| S：本机性能 | AIPerf 吞吐、TTFT、ITL | 9 号机本机，回环地址 | 论文与所有历史基线都用这个口径，不变 |
| F：功能与质量 | OpenAI SDK + pytest、quality60、API 兼容 | 办公电脑 WSL2 远程访问，经 SSH 隧道 | 网络不影响正确性；做 A/B 时两臂必须用同一个客户端 |
| N：网络体验 | 局域网客户端看到的 TTFT/ITL | 办公电脑 WSL2 | 只在确认有"局域网共享服务"这种部署场景时才做。单独建基线，永远不与 S 类混用。网络故障注入工具（Toxiproxy）需要另行批准 |
| 开发 | 代码修改、CPU 单测、静态检查 | 办公电脑 WSL2 | 工具版本与 `evaluation/toolchain` 的 freeze 文件一致 |

**WSL2 不跑模型。** 原因有三：
- 模型需要约 121 GB 锁页主存（PLE 47.7 GB + 专家 73.4 GB），而 WSL2 虚拟机默认只能拿到主机内存的一半，NVIDIA 的 WSL 文档也注明锁页内存受限；
- hybrid 依赖 NUMA 和绑核，在 WSL2 中无法控制；
- 硬件不同，结果无法与论文基线比较。

## 四、决定 3：门与顺序

1. **T16 两次，分开跑。** 这是用户的裁定。
   - D05 候选 `730b58c9` 对比 481d3a7；
   - D09 候选 `7d8d389e` 对比 481d3a7。
   - 两项都用 481d3a7 作对照，证明各自关闭开关时与发布版逐位一致。
   - 协议与 batch163 相同。属于压力测试。
2. **hybrid 验证（GPU）。** 包括自身复现性、quality60，以及同一窗口内的速度 A/B（1.2K 与 32K，单路与两路），判据预先登记。见 `PHASE2_DIRECTIVE_20261011.md`。
3. **版本登记表（CPU）。** 服务器上有 70 个工作树。为每个候选记录 commit、基线、开关、T16 状态和实测效果，未登记的版本不得进入组合测试。
4. **集成分支。** 基于 481d3a7，合入 T16 通过的 D05 与 D09。合并后再跑一次 T16，与 481d3a7 对比所有开关关闭时的逐位一致性，防止合并引入相互影响。
5. **组合测试。**
   - 因素：{offload, hybrid} × D05 × D09，共 8 种组合；
   - 负载：单路 1.2K、两路 1.2K、32K、seed_real 多轮 agent；
   - 顺序：先逐项单独测，再测有相互影响的组合（D05 与 D09 改的是同一段完成捐赠代码；hybrid 与 D09 都涉及预填路径）；
   - 最后用候选组合对 481 基线，交替成对至少 3 轮；
   - 每一步都要预先登记判据。

## 五、更正（2026-10-11T02:21:12+08:00，主会话核实后）

1. **部署拓扑。** 第三节写的"服务默认只监听 127.0.0.1、以同机访问为主"有误。生产服务的实际启动参数是 `--host 172.16.108.9 --port 8095`（见 `/data2/FreeToken/run/production.active.json`），也就是在局域网上提供服务。因此：
   - **N 类（局域网体验）测试有实际意义**，可以在办公电脑的 WSL2 中直接访问 8095 端口进行；
   - S 类（本机性能）仍然是论文和引擎基线的口径；
   - 两类结果永远分开报告，不能混用。
2. **32K 负载。** `probe_cold32k.py` 生成的 32K 文本，以及 R048b 的 `dec32k_s3A/B`，都是同一段约 100 字的"模型验收记录"重复几百遍拼成的合成文本，s3A 和 s3B 只有开头一行不同。b163、R048b、Strata S1 中的 32K 数字都来自这种高度重复的文本。论文要补一条局限：这些 32K 结果不代表真实的长文本。今后的长上下文验证改用 R046g 的真实 agent 负载（`G_seed_real/round-01`，约 87K token；`G_seed12k/round-01`）。
3. **执行者与时间。** 改由 KIMI 执行，并分成两个阶段，中间设审核门。阶段 1 只在 CPU 上准备和演练；阶段 2 使用 GPU，开始时间不早于 09:00。见 `KIMI_RUNBOOK_PHASE2_20261011.md`。
4. **quality60 的时间。** 每题上限 768 token，跑一遍约 25 分钟。hybrid 验证的总预算因此改为 120 分钟以内，hybrid 运行期间 CPU 满载约 40 分钟。

> **更正（2026-10-11T14:24:22+08:00，主会话）**：上文"hybrid 属于精确计算……符合无损路线"有误。代码调研发现，本机 CPU 路径走 W4A8：由 CPU 计算的专家，其激活会先量化为每 16 个元素一组的 int8（cpu_moe_ext.cpp 中的 quant_i8_pg16），属于数值近似。hybrid 是否符合"先只走无损路线"，交用户重新裁定。见论文 v5.7 §7.7。
