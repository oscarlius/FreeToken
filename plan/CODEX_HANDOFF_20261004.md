### 1.3 【新发现，P0】层优先路径捐赠的 PLE n-gram 上下文不一致

本人只读复核了 `E2-R002` 的落盘数据（`R4096` 对 `RLM`，取各长度最后一条 donate 记录）：

| 长度 | `slot:ple_ngram_ctx`，形状 (1,1,2) int32 | R4096（与历史整段重算逐位一致） | RLM（层优先，生产配置） |
|---|---|---|---|
| 12416 | 前两个上下文 token ID | [1469, 17] | **[109990, 9616]** |
| 18944 | 同上 | [11, 4093] | **[16, 20]** |
| 12736 | 同上 | 相同 | 相同 |

- 这是 token 身份，不是浮点数。两条路径对「位置 L 之前的两个 token」给出了不同答案，至少有一条是错的。
- R4096 与历史 B 逐位一致，**嫌疑在层优先路径**（我们的 D1，生产在用）。
- 后果：如果捐赠的 n-gram 上下文错了，层优先预填之后的每一次前缀命中，续算开头的 PLE 嵌入都会用错。这可能解释 T10 中「冷对热 33/36 不一致」的一部分，以及 T04 中 PLE 角色超界的现象。
- 注意：E1 和 E2 的逐位一致门都只检查了冷请求的全文，**从来没有覆盖「层优先预填 → 前缀命中 → 续算」这条路径**，所以这个问题一直没被门拦下来。
