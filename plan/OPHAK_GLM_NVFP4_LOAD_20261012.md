## 0. 背景（op 只读核查，数字可复核）

1. **加载 bug**：检查点 `/data2/model/GLM-5.3-Flash-NVFP4`（modelopt 0.47）第 0–2 层 dense MLP 为 ModelOpt NVFP4（weight u8 / weight_scale fp8 / weight_scale_2 / input_scale，共 9 个投影）。`glm5_next/weight.py::_proj` 只处理 bf16 与块状 fp8，不给出 `weight_scale`，因此 09-30 报 `KeyError 'model.layers.0.mlp.gate_proj.weight_scale'`。self_attn、mlp.gate、shared_experts 都在 exclude_modules 里，是 bf16。上游 main（95ac86f）仍未修；上游 `glm4_moe/weight.py::_iter_nvfp4_resident` 是现成的同类实现。
2. **显存账（推算，单位 GiB，按 safetensors 头逐张量求和）**：

   | 部分 | 大小 | 位置 |
   |---|---:|---|
   | 路由专家（42 层 × 288 专家，NVFP4） | 159.47 | 主存，按层流式 |
   | 第 45 层 MTP | 13.84 | 不读取 |
   | self_attn（bf16） | 11.29 | 显存常驻 |
   | shared_experts（bf16） | 1.97 | 显存常驻 |
   | lm_head / embed_tokens | 1.18 / 1.18 | 显存常驻（embed 可能在主存） |
   | router + dense MLP + norms/hc | 0.40 | 显存常驻 |
   | vision | 1.05 | `--text-model-only` 时不构建 |

   - 常驻合计（text-only）约 **16.0 GiB**（embed 若放主存则 14.8）。
   - 每个 MoE 层的专家约 **3.80 GiB**（159.47 / 42）。预填默认"两层双缓冲"需 7.59 GiB。
   - 4090 空闲约 23.5 GiB（09-30 实测 gpu_free 24,077 MiB），`--memory-ratio` 默认 0.9 → 预算约 21.2 GiB。
   - 推论：默认（开重叠）需 16.0 + 7.6 = 23.6 GiB，超过预算；关闭重叠需 16.0 + 3.8 = 19.8 GiB，放得下但余量很小。所以本测试用关闭重叠的配置。
3. 上游推荐的 RedHatAI 检查点同样把注意力留在 bf16（只有第 3–44 层路由专家是 4 bit），换检查点不能改善显存账，本次不换。

## 1. P0（不占 GPU、不停服，现在开始）

1.1 **分支与 worktree**：从 9db0ee77 建分支 `glm/nvfp4-dense-20261012`，worktree `/data2/FreeToken/wt/glm-nvfp4-dense-20261012`，构建方式与 e3 相同，产物独立，不覆盖 e3。

1.2 **代码**：在 `python/freetoken/models/glm5_next/weight.py::_proj` 增加 ModelOpt NVFP4 分支。条件：`weight` 为 uint8 且存在 `weight_scale`。行为与上游 `glm4_moe/weight.py::_iter_nvfp4_resident` 相同：
- `weight` 与 `weight_scale` 逐字给出；
- `weight_scale_2` 广播成逐行 fp16 `weight_global`（形状 [OUT]）；
- 存在 `input_scale` 时给出 fp32 标量。

另外两种情况一律显式报错，不得静默：
- KDA 融合投影遇到 NVFP4 时抛 NotImplementedError，与现有 fp8 处理一致；
- compressed-tensors 形式（`weight_packed`）的 dense NVFP4。

1.3 **单元测试（CPU）**：
- a. 用假 reader 构造 ModelOpt NVFP4 投影，四个输出逐位等于输入，形状与 dtype 正确。
- b. 回归：bf16 投影、块状 fp8 投影的输出与改动前逐位相同。
- c. 反向对照：换回旧 `_proj` 时，测试 a 必须失败（附失败输出）。
- d. 原有 `tests/models/test_glm5_next_*.py` 中能在 CPU 上跑的全部通过；报告通过数与跳过数。

1.4 **真实检查点键集核对（只读 safetensors 头，不读张量）**：按 09-30 已验证的模块契约（每层 3 投影 × 4 个张量 = 12 个），第 0–2 层共 36 个键全部能从检查点得到，0 缺失、0 多余。

1.5 **e3 恢复路径就绪（停服前必须完成）**：
- 用已有的受控停服/恢复工装，准备"停 e3 → 测试 → 恢复 e3"所需的包与审批。
- 对 e3 恢复入口做一次真实入口演练，跑到取 GPU 锁之前；附反向对照（例如缺审批时演练必须拦下）。

1.6 **GLM 启动 argv（预登记，P0 内写定）**：

## 3. 判据（预登记）

| 编号 | 内容 | 通过 |
|---|---|---|
| L1 加载 | 服务就绪，无 WeightLoadError，无缺失/多余键 | 是 / 否 |
| L2 运行 | S、N 组全部返回 200，无 CUDA 错误；输出中替换字符与不可打印字符 < 1% | 是 / 否 |
| L3 粗判正确 | S 组 ≥ 7/10，且 N 组 2/2 | 三档见下 |

- **L3 三档**：S ≥ 7 且 N = 2 为"能跑（粗判）"；S = 0 为"实现有错"；其余（S 在 1–6，或 N < 2）为"异常、待诊断"。"待诊断"不登记为能跑，也不登记为不能跑。
- **合理性下限**：反量化或注意力实现出错时，输出通常是乱码，S 组接近 0/10，与 7/10 相距很大。
- **显存账预测（op 推算，封存于本指令，W3 日志核对）**：
  - 常驻权重 14.8–17.1 GiB；
  - 每层专家缓冲 3.75–3.85 GiB；
  - argv B 能启动。

  若常驻权重落在区间外，或 argv B 因显存不足失败，就判"推算有误"，原样写进结果，不改预测。
- **本测试只回答"能加载、能生成、粗判正确"。** "算得对"需要一个独立对照（例如与 llama.cpp UD-Q4_K_XL 在同一题集上比较，或逐层数值对照），另行预登记，不在本窗口做。
