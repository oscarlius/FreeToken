## 目标

让 D0 记录能回答「哪个请求、因为什么、在这一段/这一步搬了多少、缺了多少、搬运与计算在时间上怎么排」。

## 范围

1. **预填（`d0_prefill.jsonl`）**：
   - 新增 `seg_reason`、`reqs: [{rid, new_tokens, cached_tokens}]`（与 D01 同名同义）；
   - 新增 `t_start`、`t_end`（`time.time()` 墙钟，便于与客户端时间对齐）；
   - 修复：**进程内最后一段不落盘**（规划阶段只读核实：每个进程 D0 记录数 = `Prefill batch` 行数 − 1，因为落盘由下一段 `begin_prefill` 触发，`moe/offload_cache.py:781-782`）。**只允许**改为「段结束即落盘」（在本段计算完成处同步写出）。不得依赖空闲回调或退出钩子：批次脚本用 SIGTERM 再 SIGKILL 停服，退出钩子不保证执行，T16 的 `n_new == n_parent + 1` 会随机失败。
2. **解码（新文件 `d0_decode_steps.jsonl`，仅 `FT_DEV_D0=1`）**：每个解码步一行：`step, t, bs, rids, missing_per_layer（列表）, missing_total, h2d_bytes, cpu_experts（hybrid 时）`。现有 `d0_decode.json`（2 秒一次的聚合，`offload_cache.py:333-353`）保留不动。
3. **解码时间线（仅 `FT_DEV_D0_TIMELINE=1`，另需 `FT_DEV_D0=1`）**：前 `FT_DEV_D0_TIMELINE_STEPS`（默认 200）个解码步，每层记录「缺失拷贝开始/结束」「专家计算开始/结束」的 GPU 时间戳（CUDA event），写 `d0_decode_timeline.jsonl`。附带一个只读分析脚本 `scripts/d0_timeline_summary.py <jsonl>`：输出每层拷贝与计算时间的中位数 / P90、同一步内「拷贝与计算可重叠时间占比」、步内气泡。
4. **GPU 时钟**：`FT_DEV_D0=1` 时，在 `d0_decode.json` 的周期记录里加 `sm_clock_mhz`（`pynvml` 或 `nvidia-smi` 查询；失败则写 null，不报错）。

## 非目标

- 不改调度策略、不改任何数值路径。
- 不在 CUDA Graph 里插「图内事件」作为第一版：时间线模式允许**关闭 CUDA Graph**（只在 `FT_DEV_D0_TIMELINE=1` 时），但必须在 `serve.log` 打印 `D0 TIMELINE: cuda graph disabled`，且该模式下的吞吐**不得**作为性能数（T05 已据此写明）。若能做到图内事件节点而不关图，作为可选增强在交付记录中说明。

## 设计约束

- 所有新功能默认关；`FT_DEV_D0` 不设时与父树逐位一致（T16）。
- `FT_DEV_D0=1` 时**输出数值仍逐位一致**（埋点不改计算）；T16 两臂都开 D0，已覆盖。
- 逐步记录的开销：在 T05 中标注；`FT_DEV_D0=1` 下解码 tok/s 相对不开 D0 的下降要在开发自检里测一次（同树、ABAB 各 2 次），写进交付记录，供 T07 对照。
- 文件追加写，进程崩溃不丢已写记录（行缓冲 + 定期 flush）。
