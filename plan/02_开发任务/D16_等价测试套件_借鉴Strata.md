## 为什么要做

卡D14 的缺陷 K1 之所以一直没被发现，是因为所有等价门都只比较**冷请求**，没有任何门覆盖「命中前缀 → 续算」和「多会话批内各槽」这两类路径。Strata 用三类测试专门覆盖这些路径，我们照它的设计做，但用我们自己的模型、数值路径和工装：

| Strata 工具（MIT，仅参考设计，不复制代码） | 它验证的性质 | 我们的对应用例 |
|---|---|---|
| `tools/batch_test.py` | 批内每个槽的贪心输出等于该提示单独运行的输出 | **S-批槽**：两路、四路不同内容，批内对单独运行 |
| `tools/parking_test.py` | 会话状态停靠后恢复，续写与一直在线时相同 | **S-停靠**：#577 主存槽恢复对不恢复 |
| `tools/batch_interleave_test.py` | 长提示读入期间其他槽在解码，各自输出与单独运行相同 | **S-交错**：一路长预填加一路解码 |
| `bench/results/2026-09-27-cache-parity` | 专家缓存命中与否不改变输出 | **S-缓存**：不同缓存初态（冷缓存、预热缓存）下输出相同 |

在此基础上，再加上我们自己的两类：

- **S-续算短**：命中前缀后剩余少于 4096 token 的续算。
- **S-续算长**：命中前缀后剩余超过 4096 token 的续算，**覆盖子块边界附近的多个长度**，包括恰好在边界、边界前 1、边界后 1、8193 等短尾块。

## 判据（与 PLAN §4.1 一致）

- **S-续算短、S-续算长**：与「同结构冷参照」（分段边界、子块网格、每段预填模式都与供体 + 续算的实际执行相同的全冷计算，经 `FT_DEV_PREFILL_SCHEDULE` 注入，见 PLAN §4.1）预期**逐位相等**。参照臂须先跨进程重复两次逐位相同。不等时判 `not_met` 并输出按层、按算子的首个差异位置；改判只由总负责人决定。此外记录与普通全冷的差异，不作判据。
- **S-批槽、S-交错**：按项目现有的数值规则，批形状改变本来就可能改变归约顺序。所以先测「同批形状重复两次」必须逐位相同；再报告批内对单独运行的首个分叉位置和 top-2 logit 差。**不预设逐位相等**，偏差记录进合法重排包络。
- **S-停靠、S-缓存**：恢复的四类状态逐位相同；输出逐位相同（缓存路径与搬运路径使用同一个 GPU 内核，理论上不应改变数值；一旦出现差异，按缺陷处理）。

## 范围

- 工具放 `freetoken/scripts/equiv_suite/`，同步到远端 `/data2/FreeToken/scripts/`。复用卡D06 的多会话客户端、卡D03 的落盘与 logits 工具，以及共用 T16 运行器的服务启停与门禁。
- 每个用例都输出机器可读结果，并附带输入 token ID 的 sha、实际 `cached_tokens`、段原因、首子块状态标志。
- **T17 批次脚本**：`plan/01_测试与调研/batches/batchNN_T17.sh`，RID 从第 1 个命令行参数读取（不写死，T17 首轮 E2-R033、重跑 E2-R034），按 PLAN §4.1 跑命中路径 1 进程、参照臂 2 进程，并输出三层判定；先用 R023 原始数据只读重放自检。
- **结构核验（判定前置条件）**：参照臂自己的 D0 段记录必须与注入清单逐段一致（起止、模式、子块网格）；不一致报「工装错误」，不得继续比较。
- **调度生成器**：从命中路径两次请求的 D0 段记录（卡D14 新增的 `start,end,mode,subchunks` 字段）生成 `FT_DEV_PREFILL_SCHEDULE` 清单（段起止、模式、子块网格），供 T17 的同结构冷参照使用。
- 夹具与期望结论：
  - R019、R021：工装错误样本。期望工具判「事件计数一致（父、新均为 13），无判定冲突」，不得误报为不等价。
  - R023：只有状态交接与原判据下的分叉，没有同结构参照臂。期望工具报「状态交接 PASS；同结构参照缺失 → 无法判定」，**不得给出 PASS**。
