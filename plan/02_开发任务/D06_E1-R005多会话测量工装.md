## 目标

交付一个客户端工装，让 01 用固定命令测出 T05 的 a–d 子项；并提供 H1「等时长空等」条件所需的服务端开发钩子。

## 接口约定（01 卡 T05 直接按此调用；**不得更改**，需要改先找总负责人改卡）

```
multisession_probe.py two-decode --ctx <tokens> --max-tokens <n> --same-prompt {0,1} --reps <k> --out <json>
multisession_probe.py stall --decode-ctx <tokens> --decode-max-tokens <n> --prefill-kind {cold32k,agent_turn}
                            [--prefill-target <tokens>] [--trace <trace.json> --round <i>] --delay <s> --reps <k> --out <json>
multisession_probe.py pair-short --trace <trace.json> --rounds <i,j> --reps <k> --out <json>
multisession_probe.py h1 --H <1,8,32> --reps <k> --prefill-target <tokens> --out <json>
公共参数：--base-url（默认 http://127.0.0.1:8095/v1） --model（默认 Qwen3.8-Flash-Next-NVFP4） --timeout
```

输出 JSON 字段（最少）：

| 子命令 | 字段 |
|---|---|
| two-decode | `per_way[].{ttft_s, decode_tps, completion_tokens, t_first, t_last}`、`common_window_s`、`common_window_tokens`、`common_window_tps`、每路逐 token 时间戳文件路径 |
| stall | `max_gap_s`（解码会话最长字间隔）、`interference_tps`（预填会话从发出到首 token 期间解码会话的 tok/s）、`prefill_ttft_s`、`prefill_new_tokens` |
| pair-short | 两请求 `ttft_s`、两请求发出时间差、`same_prefill_batch`（工具从服务端 D0 `reqs` 或 `serve.log` 判断，判断不了写 null） |
| h1 | 三条件 `none/idle/prefill` 下，事件后前 H 步的步时之和、`delta_H = prefill − idle`、事件期间额外 H2D 与缺失数（取 D02 `d0_decode_steps.jsonl`） |

内容要求：两路「不同内容」必须是**不同文本**（不同种子、不同前缀），并在输出中给出两路提示的 sha256 与前缀重合 token 数（应为模板长度级别）；`--same-prompt 1` 只作对照。

## 服务端钩子（仅开发用，默认关）

- `FT_DEV_PAUSE_ENDPOINT=1` 时，增加一个开发端点（例如 `POST /dev/pause {"seconds": x}`），让调度主循环在下一步前空转 x 秒、不调度任何批次（不预填、不解码、不动缓存），用来构造 H1 的「等时长空等」条件。挂点：调度主循环 `scheduler/scheduler.py:870-880`（`prefill.schedule_next_batch(...) or decode.schedule_next_batch()`，上游 d3512b4 核实）；HTTP 层在 `server/` 下（读码确定文件）。
- 未设置时端点不存在（404），代码路径不进入。

## 非目标

不改任何调度策略；不做多于两路的负载（四路扩展留给后续）。

## 设计约束

- 时间全部用 `time.perf_counter()` 记录相对时间，并另存一次 `time.time()` 锚点，便于与 D02 的墙钟字段对齐。
- 首 token 只用 `first_real`（首个带内容的增量），不用首个 SSE 事件（论文 §6.3 探针教训）；`[DONE]` 后不计时。
- 失败关闭：任一路请求失败、被拒或超时，子命令非 0 退出，输出 JSON 中写明原因。
