## P0 诊断计数并发修正（待新 CPU stage）

R 在 `e58d5f0` 的复核指出两处 P0：worker 在运行中递增
`worker_service_count[tid]` 时，host enqueue 后的 trace 可读取该值；coordinator
递增 `flag_served[L]` 时，watchdog 可同时读取该值。`decode_sync` 只向 GPU stream
提交 wait，不能把这种 host 并发读取当作已经同步完成。后续提交将这两个数组改为
`std::atomic`：worker/coordinator 使用 `fetch_add`，诊断/watchdog 使用 `load`；不加入
stream synchronize，也不改 NVFP4 或任何专家计算。

新增 native CPU fixture 在 GIL 已释放的 `run_task` 循环期间反复采样服务计数；另以
CPU Q4_0 packed tensor 走第二个 preparation phase、全部无效路由制造零专家/不均衡
工作量，并用 subprocess timeout 验证 idle destructor 可退出。这是新提交的待编译
验证范围；上节 `e58d5f0` 的 7 PASS 是修正前证据，保留供追溯，不能作为本 P0 修正
的成功证据。flag coordinator 依赖 GPU mapped flags，CPU-only fixture 无法驱动该
协议，因此 `flag_served` 的范围是原子读写静态审计；不宣称消除所有并发风险。
