# FreeToken 改动地图 · 效果台账（exhibit）

回答两个问题：

1. **我们改的方法论，在推理框架里主要改了哪几部分** —— 每一项列出机制、开关、以及实际动了哪些文件与函数。
2. **测完的项提升了多少** —— 每一条指标给基线值、候选值、差值、验收门与判定，不过门的也列出来。

## 怎么看

本地直接开 `index.html` 即可（自包含单文件，无外部依赖、无 CDN）。

远端起服务：

```bash
/data2/FreeToken/exhibit/serve.sh          # 起在 8100
curl -s localhost:8100/index.html | head -5
```

## 文件

| 文件 | 作用 |
|---|---|
| `ledger.json` | **唯一数据源。** 从 `freetoken/RESULTS_*.md` 人工誊录。要改内容改这里。 |
| `build_exhibit.py` | 编译 `ledger.json` → `index.html`，并**核验**证据路径与 commit 是否真实存在。 |
| `index.html` | 生成物，不要手改。 |
| `serve.sh` | 起一个静态服务在 8100。 |

## 重新生成

```bash
cd /data2/FreeToken/exhibit && /data2/FreeToken/venv/bin/python build_exhibit.py
```

输出末尾会报核验结果。**核验不过不要忽略**——它意味着台账里的证据路径或 commit 已经失效（分支被 rebase、文件被清理），此时页面上的数字虽然还在，但已不可追溯。本地跑会自动降级为「未核验」。

## 与 8099 监控的关系

8099（`/data2/_shared/run_monitor/`，Codex 维护）渲染的是 E1/E2 轮次体系。本目录**独立**，不读写 8099 的任何文件，因此可以并行改而不冲突。

需要并入 8099 时：把本目录整体搬过去，`ledger.json` 可直接作为 `run_monitor` 的一个数据源接入（结构是 `ft_exhibit/ledger/v1`）；或者反过来，把 `ledger.json` 的条目按 8099 的卡结构喂进它的 `/api/devtest`。

两条血脉的卡号体系不同（本线 D0/D1/D3 对 Codex 的 D00–D13），合并时建议保留前缀区分，不要混编。

## 口径纪律

台账里每条指标都带 `protocol` 字段，写明这次数是怎么测的。已知的三个易混口径：

- **基线 21.52 s** 是 20261002 的两轮慢轮；21.32 是快轮。
- **D1 的 12.66/12.98 s** 是无仪表的最终值；13.14/13.91 是开着 `FT_DEV_D0` 的两轮。8098 面板上记的 13.91 取自仪表轮。
- **解码 37.52 tok/s** 是冷 32K 的均值（37.13/37.91）；短上下文 C1 的 38.28 是另一口径，不可混用。

改动量展示另有坑：仓库里有两个 `.bak` 被提交进了版本库，且部分文件行尾在提交间不一致，导致 `git show --stat` 严重失真（加 8 行显示成改了 1299 行）。本台账不按 diffstat 统计，改为逐文件列「改了什么」。
