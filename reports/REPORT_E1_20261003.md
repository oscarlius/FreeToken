## 0. 结论

1. **#578 成立，收益全部来自 MoE 计算。** 冷 32K 层优先首 token 从 13.68 s 降到 6.07–6.60 s，输出与父轮逐位一致。D0 逐层计时显示，MoE 计算从 9.42 s 降到 2.22 s（4.24 倍），非 MoE 部分约 4.2–4.4 s，基本没变。冷 32K ≤10 s 这条线达成了。
2. **64K 已经实测，不是「架构限制」。** 窗口放宽到 73,728 后，65,412 token 冷启首 token 为 12.43 s 和 14.08 s，解码 36.4 和 37.1 tok/s。冷启 ≤10 s 的上限约 49–53K token。64K 时非 MoE 占 63–67%，所以长上下文冷启下一步该压的是注意力、GDN 和 PLE，而不是 MoE。
3. **hybrid 不进生产，这一点同意；但否决理由要改。** 4.84 tok/s 的直接原因是 CPU 执行器：每层每 token 多花 3.75 ms，等效 CPU 带宽只有内存带宽的几个百分点。最强的嫌疑是绑核冲突：执行器把线程绑在 0..22 号核，其中 0、2 号核被一个常驻的 ollama `llama-server` 占着。所以这次结果不能证明「这台机器上 hybrid 不可行」。我对 E1-R002 的推算（38–44 tok/s）偏差 87%，原因见第 4.3 节。
4. **真实 Agent 轨迹暴露了新的头号瓶颈。** 12 轮回放带工具调用和思考，提示从 659 token 增长到 4,268 token。前缀命中工作正常，但每轮首 token 只落在两个档位：约 2.66 s 或约 5.3 s。原因是每个预填段都要把 68 GB 专家池完整搬一遍，搬一遍约 2.6 s，跟后缀长短无关；有的轮次被切成两段，就要搬两遍。切成两段几乎可以确定来自我们自己 D3 的「预填锚封顶」：它挂在生产命令带着的 `--enable-special-token-ckpt` 上，所以任何含 D3 提交的树（包括整个第 1 代）只要用生产参数起服务，它就是开着的。这一项是 Agent 体验下一步最大的杠杆，而且第一步验证几乎不用写代码（第 8 节第 5 步）。
5. **面板数据有 7 处要修**，其中一处已经把错误文字带进了论文（第 6 节）。
6. **编辑器 M1 的接口层验收通过**：9 个接口都返回 200，论文里 43 处引用全部解析成功。界面相关的验收项还没有人工点过（第 7 节）。

## 2. E1-R001：上游 #578（NVFP4 预填反量化）

### 2.1 实测和推算对照

| 指标 | 推算 | 实测 | 判断 |
|---|---|---|---|
| 冷 32K 层优先首 token | 7.7 s（区间 6.5–9.7） | 6.07–6.60 s | 低于推算区间下沿，比点估计低 16–21% |
| 4096 分块首 token（第二枪） | 不变 | 21.14 s，父轮 21.61 s（−2.2%） | 符合 |
| 解码 | 不变 | 37.8–39.8 tok/s，父轮 37.8–39.6 | 符合 |
| temp0 输出 | 逐位一致 | 四个样本逐字符全等；`det_seed7` 为 BIT_EXACT_MATCH | 符合 |

32K 推算偏乐观方向的误差来自 MoE 提速倍数：推算按 1.5–3.0 倍取区间，实测是 4.24 倍。

### 2.2 提速来自哪里（D0 逐层计时）

| 项目 | #578 之前（E1-R000b） | #578 之后（E1-R001） | 倍数 |
|---|---|---|---|
| 层优先 32K，MoE 计算合计（48 层 × 8 个子块） | 9.42 s | 2.22 s | 4.24 倍 |
| 4096 分块，每层 MoE 计算（中位数） | 25.3 ms | 6.2 ms | 4.1 倍 |
| 专家搬运，每搬一遍 | 2.86 s（每层 59 ms） | 2.86 s | 不变 |
| 非 MoE（首 token 减去 MoE 计算） | 约 4.4 s | 约 4.2 s（64K 那次服务里为 3.85 s） | 基本不变 |

- #578 也改了 `nvfp4_linear.py`，但非 MoE 时间没有变化，所以收益可以全部记在 MoE 内核上。
- MoE 的等效算力从约 16 TFLOPS 升到约 68 TFLOPS（32K 共 151 TFLOP，用时 2.22 s）。这是 BF16 峰值的 41%。
- 层优先模式下，每层 MoE 计算（46 ms）已经比每层搬运（59 ms）快。但加上非 MoE（每层约 85 ms）后，每层计算约 131 ms，仍然比搬运慢，所以整体还是计算受限。
- 这意味着即使 MoE 内核再快，32K 最多也只能再省 2.2 s；**非 MoE 已经是预填的大头**。

### 2.3 为什么分块模式不受益

4096 分块下，每个块都要把整个专家池搬一遍：每块 H2D 63.46 GiB，耗时 2.86 s，而计算只占每块 0.3 s。8 块合计约 22.9 s，与实测 21.1–21.4 s 吻合。这个结果确认了：分块模式受搬运限制，层优先模式受计算限制。

生产 8095 现在用 8192 分块，冷 32K 约 13.0 s。换成层优先加 #578 后约为 6.1–6.6 s（埋点开时的数字）。

## 3. 64K 补测

- **配置**：E1-R001 的树，层优先，`--max-seq-len-override` 和 `--kv-reserve-tokens` 都设为 73,728，其余是生产参数。KV 实际分配 73,792 token（1.74 GiB）。
- **结果**：
  - 冷 64K（65,412 token）：首 token 12.43 s（第二枪）和 14.08 s（第一枪）；解码 37.1 和 36.4 tok/s。MoE 计算 4.34 s。
  - 同一服务进程里，冷 32K 首 token 6.07 s 和 6.07 s，解码 36.8 和 36.6。
- **和推算对照**：
  - 计划文档写的 64K 是 19.4 s（按 2.2 倍提速）。用实测的 4.24 倍重算是 15.2 s。
  - 实测 12.4–14.1 s，比重算值还低 7–18%。
  - 原因是旧模型的平方项（0.00181·N²）是在第 0 代树上拟合的。第 0 代 64K 时非 MoE 约 11.1 s，第 1 代只有 8.1–9.7 s。这与第 1 代树并入的上游 QSA 稀疏注意力提速（5031e3d）一致，具体还要等 D0 按层类型分项后确认。
- **第 1 代重拟合**（埋点开，层优先加 #578，N 以千 token 计，单位秒）：

  \[ T(N) \approx 0.068N + 0.107N + 0.0002N^2 + 0.2 \]

  - 第一项是 MoE，后两项是非 MoE。
  - 按这个式子，48K 约 9.3–9.9 s，冷启 ≤10 s 的上限约 49–53K token。
- **64K 冷启要进 10 s，必须压非 MoE。** 64K 时非 MoE 约 8.1–9.7 s，占 63–67%；MoE 总共才 4.34 s，靠它省不出 2.4–4.1 s。
  - 不过冷 64K 对 Agent 来说是少见路径。会话是一轮一轮长大的，平时靠前缀命中；冷启主要出现在会话被挤出之后重新进入，这由 D8 主存会话层负责，推算约 3 s。
  - 所以冷 64K 先不列为主攻，只排一次非 MoE 按层类型的分项测量。
- **窗口**：64K 可以跑，没有 OOM，64K 下解码也正常。生产窗口可以从 49152 提到 65536。两路 64K 同时驻留时专家槽会降到约 2399 个，这个情形还没测（E1-R006）。
- **第一枪偏慢**：64K 第一枪比第二枪慢 13%，4096 组第一枪也慢 16%。跨轮比较继续丢掉第一枪。对生产来说，这意味着重启后的第一个长请求要多付这部分时间，优先级低。

## 4. E1-R002：hybrid（CPU 分担未命中专家）

### 4.1 实测

- 解码 4.84、4.86、4.86、4.75 tok/s，offload 为 36.6–38.2，下降 87%。
- 每 token 206 ms，offload 是 26.2 ms，多出约 180 ms。按 48 层平均，**每层多 3.75 ms**。
- CPU 分支确实生效：每层每步激活 10 个专家，未命中 3.05 个，其中 0.62 个走 PCIe 搬运，2.43 个在 CPU 上算。失误率从 21.9% 升到 30.5%：CPU 算过的专家不进 GPU 缓存，这在推算时已经预期到。
- CPU 执行器日志：`threads=23 (pinned to cores 0..22) isa=avx512f+avx512vnni(nvfp4-w4a8)`，同时 `torch intra-op threads: 24 -> 1`。
- **预填对照写错了**：hybrid 这批实际用的是 8192 分块（每个请求 4 个 D0 块，日志里是 `#new-token: 8192`），而不是记录里写的 4096。它的首 token 12.94–13.05 s 应该和第 1 代 8192 组的 12.95–13.03 s 比，结论是预填没有变化，而不是「快了 40%」。
- 输出不逐位一致，这是 w4a8 内核的预期行为。60 题质量门没跑，因为性能门已经失败，不跑是对的。

### 4.2 4.84 tok/s 的原因

- **CPU 侧太慢，问题在执行器，不在机器。**
  - 每 token 交给 CPU 计算的专家约 323 MB。实际多出的 180 ms 折算下来，CPU 路径的等效带宽约 1.8 GB/s。
  - 开发 agent 引用的带宽档是 3.61 和 12.69 GB/s，即使按这个算，CPU 计算也只解释 25–90 ms，剩下 90–155 ms（每层约 1.9–3.2 ms）都是交接和同步开销。
  - 这台机器实测的 STREAM 内存带宽是 46.6–110.8 GB/s。3.6–12.7 GB/s 只是其中的 3–27%。
- **最强嫌疑：绑核冲突。**
  - 这台机器的 NUMA 编号是交错的：node0 是偶数号 CPU，node1 是奇数号 CPU，GPU 挂在 node1 上。
  - 执行器绑的 0..22 号核横跨两个节点，其中包括 0 号和 2 号。
  - 服务器上有一个 ollama 容器（`cpuset=0,2`），里面的 `llama-server` 已连续运行 1 天 21 小时，平均占用约 119% CPU，也就是两个核都有大约一半时间在忙。
  - 执行器每层都要等所有线程到齐，只要有一个线程落在被占用的核上，整层就要等它。
  - `modelscope/README.md` 记录过同一种机制：「ollama（cpuset=0,2）与测试核集合重叠，加上逐层屏障，可造成约 7 倍波动（3.9 对 28 tok/s）」。这次是 7.9 倍。
  - 生产推荐命令用 `taskset -c 1,3-47` 避开 0、2 号核，而 E1 各轮的启动命令没有带这一项。
- **结论**：这次只能证明「当前执行器加当前绑核方式」不能用，不能证明 hybrid 在这台机器上不可行。

### 4.3 我的推算为什么偏差 87%

- 推算里用的每层交接开销 0.14 ms，是从 10/02 那次「offload → hybrid + 12% 缓存」（短上下文 38.3，约 3K 上下文 37.2）反推出来的。
- 那次测试很可能根本没在 CPU 上算专家：没有 `ft bench bw` 的带宽档时，代码会退回固定搬运上限，可能把未命中全部搬走，实际上等同于 offload。这次有带宽档（搬运 27.7%），CPU 分支才真正生效。
- 那次没开 D0，无法核实。但不管是哪种情况，这个参数都不成立。
- 因此计划文档 §4.4 和 §4.8 里所有 hybrid 行作废，等第 8 节第 3 步的复测结果再重算。

## 5. E1-R003：上游 #577 和真实 Agent 回放

### 5.1 已有结论

- 测试门：`tests/scheduler` 加 `tests/kvcache` 为 2 failed / 370 passed / 1 skipped。#577 自带的 host bank 测试通过。剩下 2 例失败在父轮就已存在，已归因到 D3：`scheduler.py` 在解码热路径上无条件读 `d3_extra_anchor_ids`。
- 运行期风险已证实：#577 的快照归档只在 `ChunkedReq` 分支里触发，而层优先模式不产生 `ChunkedReq`，所以层优先下它不会生效。这次 warm 回放的归档计数是 0，也就是说回放测到的是基线行为，不是 #577 的效果。
- 「编辑后首 token ≤4 s」这个门还没测，因为回放没带 `--edit-at-idx`。

### 5.2 回放数据（12 轮，9 轮有工具调用，12 轮都有思考段）

回放有两种口径。「热进程」是在已经跑过一遍的服务里重放，每轮都能命中上一轮留下的前缀。「冷进程」是新起一个服务再重放：第 0 轮是真正的全量计算，之后的轮次在同一进程里仍然会命中前面轮次留下的前缀，只是命中点不同。

| 轮次 | 提示 token | 热进程：重算 token / 首 token | 冷进程：重算 token / 首 token |
|---|---|---|---|
| 1 | 896 | 64 / 2.66 s | 256 / 2.61 s |
| 2 | 956 | 60 / 2.66 s | 124 / 2.61 s |
| 3 | 1,268 | 52 / 2.66 s | 372 / 5.22 s |
| 4 | 1,453 | 45 / 2.66 s | 237 / 5.19 s |
| 5 | 1,584 | 48 / 3.50 s | 176 / 5.19 s |
| 6 | 2,169 | 633 / 5.31 s | 633 / 5.21 s |
| 7 | 3,021 | 909 / 5.31 s | 909 / 5.21 s |
| 8 | 3,671 | 663 / 2.69 s | 663 / 2.62 s |
| 9 | 4,177 | 529 / 5.31 s | 529 / 5.21 s |
| 10 | 4,222 | 62 / 2.68 s | 62 / 2.63 s |
| 11 | 4,268 | 108 / 2.68 s | 108 / 2.62 s |

热进程首 token 均值 3.46 s，最大 5.31 s。

### 5.3 解读

- **首 token 只有两档：约 2.6 s 和约 5.2 s。** D0 显示，每个预填段不论多少 token，都要搬 57.7–63.5 GiB 专家，约 2.6 s。例如有一段计算中位数只有 2.2 ms，但整段耗时 2.79 s，全花在搬运上。首 token 5.2 s 就是搬了两遍。
- **决定首 token 的是被切成几段，而不是重算多少 token。** 重算 663 token 只要 2.62–2.69 s（第 8 轮），重算 176 token 却要 5.19 s（冷进程第 5 轮）。
- **切成两段的原因几乎可以确定是我们自己 D3 的「预填锚封顶」**（提交 e92fdf5 / cd450be，在第 1 代树里）。它挂在 `--enable-special-token-ckpt` 上，而生产命令带着这个开关，所以第 1 代树用生产参数起服务时它是开着的。生产 8095 现在跑的是哪棵树没有核实；如果含 D3，生产也受影响。证据有两条：
  - 所有重算段都远小于 4096，排除了 `--max-prefill-length` 块长上限这个原因。
  - 同一轮在热进程里只需重算 45–52 token 时是一段，在冷进程里重算 176–372 token 时变成两段。更长的那段包含了锚点，于是在锚点处被切开。
- **在 offload 模式下，锚封顶对短后缀是净亏损。** 切一刀固定多付一遍搬运，约 2.6 s。不切的代价是下一轮可能要多重算一些 token，但同一遍预填里多算几千 token 只多约 0.2 s/千 token。粗算下来，只有当锚点之后的内容超过约 13K token 时，切开才划算。
- **推算**：
  - 每轮只搬一遍时，这条轨迹的均值从 3.46 s 降到约 2.75 s，最坏一轮从 5.3 s 降到约 2.7 s。
  - 如果再让短后缀只搬它路由到的专家，均值可以到约 2.0 s。按每个 token 激活 10/512 个专家估算：64 token 的后缀约用到 72% 的专家，约 1.8 s；19 token 约 31%，约 0.9 s；300 token 以上基本用到全部专家，没有收益。这条轨迹的热进程里，约一半轮次只需要重算 ≤64 token。
- **确定性门 NOT MET**：第 0、2、3 轮，热进程和冷进程回放的前 32 个 token 不一致。分歧全部在思考段，正文前缀一致。这可能是数值路径不同（快照恢复的 GDN 状态和一次算完的结果在浮点上有微小差别），也可能是状态缺陷。要先测「重算对重算」是否稳定，再看分歧位置前两名 token 的 logit 差（第 8 节第 7 步）。
